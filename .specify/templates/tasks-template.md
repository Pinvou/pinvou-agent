# 任务：[FEATURE NAME]

**输入**：`/specs/[###-feature-name]/` 下的设计文档

**前置条件**：plan.md（必需）、spec.md（用户故事必需）、research.md、data-model.md、contracts/

**测试**：任务必须包含与风险匹配的验证方式。若规格明确要求测试，测试任务应先于实现任务，并在实现前失败。

**组织方式**：任务按用户故事分组，保证每个故事可以独立实现和验证。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**：可并行执行，前提是修改不同文件且没有依赖关系。
- **[Story]**：任务对应的用户故事，例如 US1、US2、US3。
- 描述中必须包含精确文件路径。
- 文档、任务描述和验收说明默认使用中文；英文仅保留必要命令、路径、API 字段或原文。

## 路径约定

- **Tauri 桌面应用**：`pinvou3-app/src/`、`pinvou3-app/src-tauri/`
- **底座 fork**：`DeepSeek-TUI/`
- **文档**：`docs/`、`specs/[###-feature-name]/`
- **工作流**：`workflows/`、`pinvou3-app/src-tauri/resources/bundle/workflow/`
- **测试**：Rust 测试位于相关 crate；脚本或文档验证任务需写明命令

## 依赖与执行顺序

- 准备阶段无依赖。
- 基础任务阻塞所有用户故事。
- 用户故事按优先级推进，也可在基础任务完成后并行。
- 每个故事必须能独立验证后再视为完成。

## 并行机会

- 标记 `[P]` 且修改不同文件的任务可并行。
- 不同用户故事可由不同人员并行推进，但必须避免同文件冲突。

## 实施策略

1. 先完成 P1 用户故事作为 MVP。
2. 每完成一个故事就独立验证，不把所有验证堆到最后。
3. 高风险改动必须先明确验证方式，再实施。
4. 任何偏离宪章的任务都必须在任务描述中写明原因和缓解措施。
5. 合并冲突先保留双方可共存功能；不能证明等价或存在取舍时停止执行并请求用户决策。
