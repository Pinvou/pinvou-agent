# 研究：修复大模型状态监控显示

## 决策 1：监控目标必须来自实际推理配置

**Decision**：大模型监控使用与实际聊天推理一致的 base URL、模型名和 provider 推导规则，优先复用或提取 `Pinvou3Bridge::base_url()`、`model()`、`provider()` 形成统一的“模型监控目标”。

**Rationale**：当前监控侧独立读取环境变量和 `settings.json.custom_base_url`，但实际推理侧还会根据模型预设、官方 DeepSeek 地址规范化、环境变量覆盖等规则决定最终目标。两套逻辑会造成监控页检查一个地址，而聊天使用另一个地址。

**Alternatives considered**：
- 继续在 `monitor.rs` 复制配置规则：拒绝。重复逻辑会继续漂移。
- 只修前端展示文案：拒绝。后端状态来源仍错误，无法解决根因。

## 决策 2：远端模型检测远端状态，不套用本地 VLLM 指标语义

**Decision**：当当前目标为远端模型时，监控只判断远端目标的基础可用性、鉴权、模型信息和模型匹配情况；队列、KV 命中率、TTFT、吞吐和 token 统计标记为“不适用”或空缺原因，而不是当作本地指标异常。

**Rationale**：远端商业模型通常不会暴露本地 vLLM `/metrics`，把这些字段显示为一组空值会误导用户。用户真正关心的是当前远端模型是否可用，以及配置是否正确。

**Alternatives considered**：
- 对所有 OpenAI-compatible endpoint 都请求 `/metrics`：拒绝。远端服务通常无该接口，且会制造噪声或无意义请求。
- 远端模型一律显示为离线：拒绝。远端模型可能是当前真实可用的推理目标。

## 决策 3：本地模型继续保留本地指标能力

**Decision**：当当前目标为本地模型时，保留现有本地模型探测和 metrics 解析能力；`/v1/models` 可用代表基础在线，`/metrics` 缺失只影响指标展示，不影响基础状态。

**Rationale**：本地 GB10 + vLLM 是项目核心场景，系统监控页仍需要展示本地运行指标。但指标缺失不能把可推理服务误判为离线。

**Alternatives considered**：
- 删除本地指标，只显示统一在线/离线：拒绝。会丢失本地算力场景的重要可观测性。

## 决策 4：状态诊断作为快照契约的一部分

**Decision**：大模型状态快照需要携带稳定诊断信息，至少区分配置无效、连接失败、鉴权失败、响应异常、模型不匹配、远端指标不适用和本地指标缺失。

**Rationale**：单一 `OFFLINE` 无法解释远端鉴权失败、本地端口被其他服务占用、地址格式错误、模型名不匹配等不同原因。诊断信息能让用户直接判断下一步该改配置、启动服务还是检查密钥。

**Alternatives considered**：
- 只在日志输出诊断：不足。用户问题发生在系统监控页，页面本身需要给出可理解状态。

## 决策 5：不自动启动或切换模型服务

**Decision**：本 feature 不自动启动本地模型、不停止占用端口的服务、不自动把远端配置切回本地；只反映当前配置目标的状态。

**Rationale**：启动模型服务涉及模型路径、GPU、端口、权限和用户意图；自动改配置会破坏可预测性。本次修复聚焦状态监控准确性。

**Alternatives considered**：
- 发现本地端口异常后自动寻找其他端口并切换：拒绝。会造成监控目标与实际推理目标再次漂移。
