# 功能规格：Windows MSI 安装包构建

**功能分支**：`002-windows-msi-package`

**创建日期**：2026-06-15

**状态**：Draft

**输入**：用户描述：“我需要在尽量不改变当前项目代码的前提下，将当前项目构建并打包为Windows msi安装包，请帮我完成这个操作”

## 用户场景与测试 *(必填)*

### 用户故事 1 - 生成可安装的 Windows MSI 包 (Priority: P1)

作为 Windows 应用开发工程师，我希望在当前项目基础上生成一个 Windows MSI 安装包，以便可以把 pinvou3 作为桌面应用安装到 Windows 机器上，而不是只能停留在源码运行或 Linux 打包形态。

**为什么是此优先级**：MSI 安装包是本 feature 的核心交付物；没有可安装产物，后续安装验证、用户数据保留和发布流程都无法成立。

**独立测试**：在准备好的 Windows 构建环境中执行构建流程，能在约定输出目录获得一个 `.msi` 文件，并能在 Windows 机器上完成安装。

**验收场景**：

1. **Given** 当前仓库已准备好必要依赖和 submodule，**When** 工程师执行 Windows 打包流程，**Then** 系统生成一个与当前应用版本匹配的 `.msi` 安装包。
2. **Given** 已生成 `.msi` 安装包，**When** 工程师在 Windows 机器上运行安装包，**Then** 安装流程完成且开始菜单或安装目录中能找到 pinvou3 应用入口。

---

### 用户故事 2 - 保持现有代码行为最小变更 (Priority: P2)

作为项目维护者，我希望 Windows MSI 打包只引入打包和启动所必需的最小变更，避免为了打包而重写聊天、agent、session、工具执行或工作流逻辑。

**为什么是此优先级**：项目已有明确宪章要求复用 DeepSeek-TUI 底座，并且用户特别强调“尽量不改变当前项目代码”。打包工作必须优先保护既有行为。

**独立测试**：审查变更清单，确认变更集中在 Windows 打包配置、构建说明、必要的跨平台启动兼容或验证脚本；聊天主链路和底座 agent 能力没有被重写。

**验收场景**：

1. **Given** Windows MSI 打包变更已完成，**When** 维护者审查变更范围，**Then** 能清楚区分“打包必要变更”和“未触碰的业务/agent 行为”。
2. **Given** 应用完成 Windows 安装，**When** 用户启动应用并配置可用模型服务，**Then** 基础聊天入口和已有 session 机制保持与当前设计一致。

---

### 用户故事 3 - 形成可重复的 Windows 打包交接路径 (Priority: P3)

作为后续维护工程师，我希望仓库中有清晰的 Windows MSI 构建前提、执行步骤和验收记录，以便未来版本可以重复生成安装包，而不是依赖一次性的本机操作。

**为什么是此优先级**：一次性打包只能解决当前交付；可重复流程才能支撑后续版本发布、缺陷修复和交接维护。

**独立测试**：另一名工程师按文档在 Windows 构建环境中复现构建流程，并能得到同类型安装包或明确知道阻塞点。

**验收场景**：

1. **Given** 维护者拿到仓库和 Windows 构建说明，**When** 按步骤准备环境并执行打包，**Then** 能复现 `.msi` 产物或得到明确、可定位的失败原因。
2. **Given** Windows MSI 构建完成，**When** 维护者查看验收记录，**Then** 能看到安装、启动、卸载、用户数据目录和模型配置入口的验证结果。

### 边界情况

- 当前机器缺少 Windows MSI 构建所需依赖时，必须给出明确缺失项和补齐方式，不应静默失败。
- `DeepSeek-TUI/` submodule 未初始化时，构建流程必须提前暴露该问题。
- 如果 Linux `.deb` 打包、应用内 `.deb` 更新或 `apt/pkexec` 依赖安装无法在 Windows MSI 阶段完整迁移，应标注为暂不纳入本 feature，而不是伪装成可用能力。
- Windows 上首次启动时如果本地或远程模型服务不可用，应用应能进入可配置状态或给出清晰提示，不能把模型服务不可用误判为安装失败。
- 安装、卸载或重复安装不得默认删除用户已有 session、settings、artifact 或自定义资源。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统 MUST 能在 Windows 构建环境中生成 `.msi` 安装包，且产物名称、版本和应用标识可追溯到当前项目版本。
- **FR-002**: 系统 MUST 保留当前桌面应用的核心入口，安装后用户能够从 Windows 常规入口启动 pinvou3。
- **FR-003**: 系统 MUST 在构建前或构建失败时明确报告关键前置条件缺失，包括源码依赖、submodule、Windows 构建工具和安装包生成依赖。
- **FR-004**: 系统 MUST 将 Windows MSI 打包与 Linux `.deb` 打包区分开，避免让 Windows 包依赖 Linux-only 的安装、提权或更新机制。
- **FR-005**: 系统 MUST 保护现有 agent 底座边界，不得为 MSI 打包重新实现 DeepSeek-TUI 已提供的 Engine、ToolRegistry、流式 SSE、Session、SkillRegistry、Commands 路由、MCP client、Hooks、Cycle 或 Compaction。
- **FR-006**: 系统 MUST 将代码变更控制在 MSI 打包、Windows 启动兼容、构建说明或验证所必需的范围内；任何超出范围的行为变更都必须单独记录理由和风险。
- **FR-007**: 系统 MUST 提供 Windows 安装验收步骤，至少覆盖安装、启动、基础配置入口、卸载和用户数据保留预期。
- **FR-008**: 系统 SHOULD 提供可重复执行的构建命令或脚本说明，使后续维护者能在相同前提下重新生成 MSI。
- **FR-009**: 系统 SHOULD 在文档中列出本 feature 暂不解决的 Windows 迁移项，例如附件外部工具完整适配、Windows 原生更新器、代码签名或自动依赖安装。
- **FR-010**: 系统 SHOULD 在构建或验收记录中标明是否实际生成了 MSI 产物；如果未生成，必须记录阻塞原因和下一步补齐路径。

### 关键实体 *(涉及数据或文档结构时填写)*

- **Windows MSI 安装包**：本 feature 的主要交付产物，包含应用可安装文件、版本信息和 Windows 安装入口。
- **Windows 构建环境**：用于生成 MSI 的机器状态和依赖集合，包括源码、submodule、构建工具、系统组件和可用命令。
- **安装验收记录**：对 MSI 安装、启动、配置、卸载、数据保留和已知限制的验证结果。
- **最小变更清单**：说明本 feature 实际修改了哪些文件、为什么需要修改、哪些现有能力明确未触碰。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**: 在满足前置条件的 Windows 构建环境中，工程师能在 30 分钟内从源码生成一个 `.msi` 安装包，或在同等时间内得到明确阻塞原因。
- **SC-002**: 生成的 MSI 在至少 1 台 Windows 机器上完成安装并能启动应用主窗口。
- **SC-003**: 变更审查中，非打包/启动/文档/验证相关的项目代码改动为 0；如必须修改，必须逐项说明必要性。
- **SC-004**: 安装验收记录覆盖安装、启动、配置入口、卸载、用户数据保留预期 5 类检查项。
- **SC-005**: 后续维护者按文档复现构建时，不需要阅读历史对话即可定位构建命令、产物位置、前置依赖和已知限制。

## 假设

- 本 feature 的目标是先获得可安装的 Windows MSI 产物，不要求一次性完成完整 Windows 产品化迁移。
- 允许修改打包配置、构建脚本、文档和少量 Windows 启动兼容代码；不允许为了打包重写 agent 底座或聊天主链路。
- Windows 原生自动更新、代码签名、企业分发策略、外部附件工具全量 Windows 安装体验可作为后续 feature 处理。
- 模型服务可以由用户在 Windows 本机、WSL、远程 GB10 或其他 OpenAI-compatible endpoint 提供；MSI 本身不内置大模型。
- 若当前执行环境缺少生成 MSI 的系统级工具，本 feature 仍应产出可复现说明和阻塞记录，并在补齐环境后继续生成产物。
