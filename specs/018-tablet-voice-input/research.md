# 研究：平板语音输入强化

## Decision: 在触屏/平板体验中新增主语音按钮，而不是替换现有小麦克风

**Rationale**：规格要求保持现有 UI 不变并另外增加更醒目的语音输入按钮。当前 `ChatView` 已有小型麦克风按钮和完整 `voiceInput` 状态机，新增主语音入口可以直接复用现有开始、结束、取消和写回流程，风险最小。主按钮应只强化入口和状态表达，不改变语音识别能力。

**Alternatives considered**：
- 替换现有麦克风按钮：会破坏桌面用户肌肉记忆，不符合“保持现有 UI 不变”。
- 重做整块输入区：会扩大回归面，影响附件、模型、工具菜单和发送流程。
- 只放大现有麦克风按钮：会挤占当前工具区，并且难以同时兼顾桌面和触屏布局。

## Decision: 触屏/平板模式使用“设备能力 + 视口尺寸”的保守判断

**Rationale**：Windows 二合一设备可能同时支持触摸、鼠标和键盘，仅用窗口宽度或仅用触摸能力都不够稳定。计划采用保守策略：当环境表现为触控友好或窗口接近平板尺寸时强化显示；桌面大窗口仍保持现有紧凑布局。这样既能服务平板，也避免桌面体验被突然改变。

**Alternatives considered**：
- 只使用屏幕宽度：桌面小窗口会误判为平板。
- 只使用触摸能力：带触摸屏的笔记本大窗口可能被过度强化。
- 提供设置开关作为唯一入口：增加用户负担，不能满足“平板上希望强调语音输入”的默认体验。

## Decision: 主语音按钮放在输入框附近的独立触控区

**Rationale**：语音输入是发起输入的动作，应靠近输入框而不是放到顶部导航或侧栏。独立触控区可以做到更大的点击面积、更明显的录音状态，同时不侵占现有输入框内部空间。按钮应与底部输入区一起参与高度测量，避免遮挡最后一条消息。

**Alternatives considered**：
- 固定悬浮在屏幕角落：容易遮挡消息或产物入口，且与输入上下文割裂。
- 放入输入框内部：会压缩文本区域，尤其在平板竖屏时不稳。
- 放在顶部 header：发现性尚可，但用户录音后视线仍需回到底部输入区处理文本。

## Decision: 有内容时显示发送和清除按钮，空内容时降低干扰

**Rationale**：语音识别文本写回输入框后，用户需要快速发送或清空。当前已有发送按钮，但空内容时仍占位且缺少清除草稿入口。本 feature 将输入框非空状态作为明确的操作状态：非空时显示可触控发送和清除，空白内容视为空；清除按钮只清本地草稿，不影响附件、语音入口或会话。

**Alternatives considered**：
- 始终显示清除按钮：空输入时会造成噪音和误触。
- 使用键盘删除作为清除方式：不适合平板触屏场景。
- 清除时弹出模态确认：会让高频输入闭环变慢；明确的清除按钮点击本身即可表达清除意图，后续如用户测试表明误触率高再加二次确认。

## Decision: 计划不更换或扩展语音识别引擎

**Rationale**：规格关注 UI 强化和触屏可用性。当前 `tauri-bridge.js` 已有录音、编码、超时、取消、错误分类和识别写回流程。更换 ASR、提升模型准确率或新增后端命令会改变 feature 范围，增加验证成本。

**Alternatives considered**：
- 同时优化 ASR 模型：价值不同，且会引入依赖和包体风险。
- 新增后端录音 API：当前 WebView 录音已可用，不需要扩大 Rust/Tauri 命令面。

## Decision: 验证以触屏手动 smoke + 聚焦静态检查为主

**Rationale**：当前项目没有独立前端测试框架，UI 位于单文件 React 中。实现期应通过手动平板/响应式视口验证发现性、按钮尺寸、状态切换和不遮挡；再用静态搜索和构建检查避免语法问题。如果后续引入浏览器自动化，可补充桌面/平板视口截图验证。

**Alternatives considered**：
- 只做代码审查：无法验证触控面积、遮挡和状态感知。
- 立即引入前端测试框架：超出本 feature 范围，且会增加构建复杂度。
