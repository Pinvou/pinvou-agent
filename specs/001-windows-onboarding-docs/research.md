# 研究记录：Windows 迁移与接手维护文档

## 决策：本 feature 定位为文档与规划交付

**理由**：用户要求认真、仔细、全面地梳理项目并输出文档。当前最直接的价值是降低 Windows 工程师接手成本，明确调用链、依赖、迁移风险和维护红线，而不是立即修改运行时代码。将本阶段限定为文档交付，可以避免在尚未形成迁移共识前引入行为变化。

**备选方案**：

- 立即实现 Windows 兼容代码：拒绝。当前代码中存在多个平台敏感点，包括 `.deb`、`apt/pkexec`、`which`、`HOME`、Bash 脚本和外部文档工具路径，直接实现容易遗漏边界。
- 只更新 README：拒绝。README 适合产品概览，不适合承载详细接手、迁移、维护和验证说明。

## 决策：主交付物放在 `docs/Windows迁移与维护接手手册.md`

**理由**：项目长期文档集中在 `docs/`。接手手册是长期维护入口，不应只存在于 `specs/` 这种流程产物目录中。单一、清晰命名的中文 Markdown 文档更容易被新工程师找到和更新。

**备选方案**：

- 只放在 `specs/001-windows-onboarding-docs/`：拒绝。Spec Kit 目录主要服务流程，长期接手资料需要进入项目文档区。
- 立刻拆成多份小文档：拒绝。目标读者是新接手工程师，第一版应提供连续阅读路径；后续可以再按主题拆分。

## 决策：以正式项目宪章作为后续门禁

**理由**：项目宪章已更新为 `1.0.0`，明确中文文档优先、DeepSeek-TUI 底座优先、本地算力边界、小步高质量变更、可测试性和可维护性。当前文档 feature 应以该宪章作为计划、任务和验收的治理基线。

**备选方案**：

- 继续只引用 `AGENTS.md`：拒绝。`AGENTS.md` 仍是重要运行指导，但正式 Spec Kit 计划应引用宪章门禁。
- 为本 feature 单独定义临时治理规则：拒绝。临时规则会造成后续 feature 不一致。

## 决策：Windows 迁移以风险分类表达，不预先指定全部实现方案

**理由**：Windows 迁移涉及安装器、外部工具分发、vLLM 拓扑、用户目录、网络策略、WebView2、代码签名等部署决策。当前阶段应把已知风险定位到模块和优先级，并给出处理方向，而不是提前锁死每项技术选型。

**备选方案**：

- 在文档中为所有风险选择固定实现：拒绝。部署环境和分发策略尚未明确。
- 只用散文描述风险：拒绝。规格要求读者能列出至少 10 个迁移风险及影响模块，表格化更可验证。

## 决策：定义文档契约，而不是运行时 API 契约

**理由**：本 feature 不新增服务、CLI、Tauri command 或 MCP 接口。它的对外接口是文档本身，契约应约束文档必须覆盖的章节、风险表字段、维护边界和验证方式。

**备选方案**：

- 跳过 contracts：拒绝。文档契约能让未来更新可验收，避免接手手册漂移。
- 创建 OpenAPI 或 command schema：拒绝。本 feature 没有新增运行时 API。

## 决策：实际 Windows 兼容改造留给后续任务或新 feature

**理由**：当前目标是接手梳理和文档交付。Windows 兼容代码改造应在风险清单稳定后，通过新的规格、计划和任务拆分执行，避免把文档交付和代码迁移混成一个不可验证的大任务。

**备选方案**：

- 把 Windows 代码修改任务塞入本 tasks.md：拒绝。会扩大范围，且不符合当前规格的文档型交付目标。
- 完全不提后续实现：拒绝。接手手册必须为后续迁移排期提供入口。
