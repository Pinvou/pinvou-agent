# 研究：Windows 全功能测试参考清单

## 决策 1：以当前 UI 和 Tauri 命令注册作为功能事实来源

**决策**：测试参考清单以当前 Windows 应用可观察 UI、前端状态和 Tauri 命令入口为事实来源。

**理由**：测试人员需要验证用户能看到和操作的功能，而不是内部模块设计。命令注册能补充隐藏入口，例如升级反馈、依赖检查、系统打开、工作流门禁和市场安装状态。

**替代方案**：只按需求背景或更新功能编写。该方案会遗漏聊天、会话、附件、产物、工作流、专家卡、市场和监控等大量现有功能，因此不采用。

## 决策 2：按测试域组织功能，而不是按源码目录组织

**决策**：文档拆分为启动导航、聊天会话、设置模型、附件产物、Plan/工具、专家卡技能、工作流、监控市场、更新依赖九个测试域。

**理由**：测试执行通常按用户路径和风险域安排。按源码目录组织会让测试人员难以理解跨前后端状态，例如附件生成产物、专家卡绑定会话、工作流材料进入角色输出。

**替代方案**：按 `src`、`src-tauri`、`os/windows` 分章。该方案适合开发接手文档，不适合作为 QA 功能清单。

## 决策 3：Windows 专项风险必须独立列出

**决策**：将 Windows 路径、权限、UAC、MSI、WebView、系统打开、外部依赖和中文路径作为边界情况和成功标准的一部分。

**理由**：这些风险与 Linux/macOS 差异明显，且当前用户明确要求 Windows 测试参考。若不单列，测试容易只覆盖普通 UI 点击，遗漏平台集成失败。

**替代方案**：只写通用桌面功能。该方案不能指导测试人员验证 Windows 交付质量。

## 决策 4：更新功能保留为一个模块，而不是文档主题

**决策**：Windows 更新、MSI 安装、升级反馈和依赖检查保留在 P1/P2 测试域中，但不再作为整个文档的唯一主题。

**理由**：用户纠正了需求范围：目标是整个应用 Windows 全功能列表。更新仍是重要 P1 功能，但不能覆盖其他核心功能。

**替代方案**：继续完善升级专项。该方案与用户当前目标不一致。

## 决策 5：避免实现细节泄漏，保留可观察接口

**决策**：需求文档不要求测试人员理解 Rust 函数名、JavaScript 变量名或具体文件结构；仅在计划中列出源码参考路径。

**理由**：测试人员需要验收口径、状态、入口和结果。实现细节会降低文档可读性，也容易随着代码重构失效。

**替代方案**：在需求中直接列出所有命令函数。该方案适合开发自测，不适合面向测试人员。
