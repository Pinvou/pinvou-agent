# 头脑风暴:把想法变成设计与计划

通过自然的协作式对话,帮用户把模糊想法变成完整的设计和实现计划。先了解项目背景,再一次问一个问题逐步澄清;理解清楚要做什么之后,呈现设计并取得用户认可,最后产出一份可直接执行的实现计划文档。

<硬性门控>
在呈现设计**并取得用户明确认可之前**,不要写任何代码、不要搭建项目、不要采取任何实现动作。无论项目看起来多简单,这条都适用。
</硬性门控>

## 提问方式(贯穿全程)

本 skill 所有向用户提问、确认、二选一的地方,**一律用 `request_user_input` 工具**(GUI 会渲染成选择气泡),不要用纯文本提问。每次调用:
- **一次只问一个问题**(`questions` 数组放 1 个),别一口气压三个;按问题主题填简短 `header`
- 每题给 **2-3 个有代表性的选项**,每个选项配一句话说明它的含义 / 取舍
- 开放性问题(如"这功能要解决什么")也照给 2-3 个常见方向作选项——用户可以点气泡里自动带的「其他(自己写)」自由补充,不会被选项框死
- 设计 / 方案 / 计划的确认,就给「对,继续 / 这里要改 X / 换个方向」这类选项

## 反模式:"这个太简单,不需要设计"

每个项目都要走这个流程。待办清单、单个工具函数、改一行配置——全都要。"简单"项目恰恰是未经审视的假设造成最多无用功的地方。设计可以很短(真正简单的项目几句话即可),但你**必须**呈现它并取得认可。

## 检查清单

你**必须**为以下每一项各建一个任务,按顺序完成:

1. **探明项目背景** — 查看文件、文档、近期 commit
2. **用 `request_user_input` 一次问一个澄清问题** — 每题给 2-3 个选项,聚焦理解目的 / 约束 / 成功标准
3. **提出 2-3 个方案** — 用 `request_user_input` 让用户选(选项=各方案,说明里写权衡),先讲你的推荐项和理由
4. **分段呈现设计** — 每段按复杂度伸缩,每段用 `request_user_input` 问一次"这样对吗"再继续;覆盖架构、组件、数据流、错误处理、测试
5. **写设计文档** — 保存到 `docs/specs/<日期>-<主题>-design.md`
6. **设计自审** — 用新鲜眼光快速过一遍:有没有占位符(TBD/TODO)?前后矛盾?范围是否聚焦到能写一份计划?有没有能被两种解读的地方?当场修掉
7. **请用户审阅设计文档** — 用 `request_user_input` 问(选项:认可、继续 / 要改哪里),认可后再进入下一步
8. **产出实现计划文档** — 见下方「实现计划」一节

## 过程

**理解想法:**
- 先查看当前项目状态(文件、文档、近期 commit)
- 问详细问题前先评估范围:如果需求描述了多个独立子系统(如"做一个带聊天、文件存储、计费、分析的平台"),立即指出,别在一个需要先拆分的项目上耗问题
- 项目太大装不进单个 spec 时,帮用户拆成子项目:哪些是独立的、彼此怎么关联、什么顺序建,然后按正常流程对第一个子项目做设计;每个子项目各走一遍"设计 → 计划 → 实现"
- 范围合适的项目,用 `request_user_input` 一次问一个问题逐步澄清(每题 2-3 个选项)
- 一次只问一个,别压一堆;聚焦目的、约束、成功标准

**探索方案:**
- 提出 2-3 个不同方案及其权衡
- 用 `request_user_input` 让用户选(选项=各方案,说明里写各自权衡);先讲你的推荐项和理由

**呈现设计:**
- 你认为理解了要做什么之后,呈现设计
- 每段按复杂度伸缩:直接的几句话,微妙的可到 200-300 字
- 每段用 `request_user_input` 问一次是否对(选项如:对继续 / 这里要改 / 换个方向)
- 覆盖:架构、组件、数据流、错误处理、测试
- 有不通的地方随时回头澄清

**为隔离和清晰而设计:**
- 把系统拆成更小的单元,每个有一个清晰职责、通过定义良好的接口通信、能独立理解和测试
- 每个单元你都该能回答:它做什么、怎么用、依赖什么
- 别人不读内部实现能理解它做什么吗?改内部不破坏调用方吗?不能的话,边界还需打磨
- 更小、边界清晰的单元你也更好处理——你对能一次装进上下文的代码推理更准;文件变大往往是它做太多的信号

**在已有代码库里工作:**
- 改动前先探索现有结构,遵循已有模式
- 现有代码有影响本次工作的问题(文件过大、边界不清、职责纠缠),把针对性改进纳入设计——像好开发者改进自己正在动的代码那样
- 别提无关的重构,聚焦当前目标

## 实现计划

设计经用户认可后,**直接写一份 md 实现计划文档**(不调用任何其他 skill),保存到 `docs/specs/<日期>-<主题>-plan.md`。

把计划写给一个"对本代码库零上下文、对工具链和问题域几乎一无所知"的工程师看:他需要知道的都写清——每个任务要动哪些文件、写什么代码、要测什么、怎么测。遵循 **DRY / YAGNI / TDD / 频繁 commit**。

**计划文档结构:**

开头固定写:
- **目标**:一句话说明这建什么
- **架构**:2-3 句说明做法
- **技术栈**:关键技术 / 库
- **全局约束**:项目级要求(版本下限、依赖限制、命名规则、平台要求等),逐行一条,数值从设计文档照抄

**先规划文件结构**:列出要新建 / 修改哪些文件、各自一个清晰职责。职责相关的文件放一起,按职责拆分而非技术分层。

**再拆成 bite-sized 任务**:每个任务是"自带一轮测试周期、值得一次独立评审"的最小单元,以一个可独立测试的交付物结束。每一步是一个动作(2-5 分钟):
1. 写失败的测试
2. 跑一遍确认它失败
3. 写最小实现让测试通过
4. 跑测试确认通过
5. commit

每个任务标注:**涉及文件**(建 / 改 / 测哪些,带路径)、**接口**(用了前面任务的什么、给后面任务提供什么)。

写完计划做一次自审(占位符 / 矛盾 / 歧义),修掉后请用户审阅。用户认可后,这两份文档(设计 + 计划)就是后续实现的依据。

## 核心原则

- **一次一个问题** — 用 `request_user_input`,`questions` 放 1 个,别压一堆
- **结构化选项** — 每题给 2-3 个选项;开放问题也给代表方向,用户可走「其他(自己写)」补充
- **狠抓 YAGNI** — 从所有设计里砍掉不必要的功能
- **探索备选** — 定方案前总是先提 2-3 个
- **增量验证** — 呈现设计、取得认可再往下
- **保持灵活** — 有不通的地方回头澄清
