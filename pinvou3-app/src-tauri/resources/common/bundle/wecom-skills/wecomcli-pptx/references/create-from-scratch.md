# 从零构建PPT的教程

## 制定任务计划

> **任务命名约束（强约束）**：本表仅为内部执行参考。在创建 TODO / 任务（TaskCreate）或向用户汇报进度时，**必须使用面向用户的术语**（如「内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 检查页面 / 交付」），**禁止暴露任何内部实现字眼**（如 `JSX`、`DSL`、`*.jsx`、`docid`、`wecom-cli slide ...` 命令名、`is_success`、源码、组件文件名等）。**失败 / 排查 / 重试的对外话术同样受限**：只说「制作中 / 遇到问题正在重试 / 换个方式重新生成」，不贴错误码、不描述内部通道与排查过程、不引用技能规则原文。

| Step | 职责（内部）                                   | 产物（内部）                                 |
| ---- | ---------------------------------------------- | -------------------------------------------- |
| 1    | 信息收集（可选）                               | 背景资料 / 行业数据                          |
| 2    | 需求对齐（轻量确认 + 风格预览卡）              | 关键信息已确认 + 风格参数已锁定              |
| 3    | 依据主题+信息构建PPT的叙述逻辑                 | `STORY.md`                                   |
| 4    | 构建页面风格的设计逻辑                         | `DESIGN.md`                                  |
| 5    | 创建在线演示文稿并持久化设计契约               | `docid` 已拿到 + 设计契约已写入（写操作解锁）|
| 6    | 配图准备（材料图过上传口，无图位定版式替代）   | 全部图位已拿到上传口的 URL 或确定替代方案   |
| 7    | 逐页生成并插入（`page_index` 递增）            | 全部页面已在线成型                           |
| 8    | 核对结构                                       | 页数与顺序与大纲一致                         |
| 9    | 交付                                           | 在线文档链接已给到用户 |


## 各步骤要求
### Step1：信息收集 （Optional）
当模型的信息不足、数据过时或需要行业标杆案例时，主动调用网络搜索的工具进行信息的收集，挖掘有深度、有据可查的实时内容。
判断信号：
- 主题涉及 `数字 / 市场 / 行业 / 新闻 / 分析` 等具有时效性的信息时 → 需要最新统计数据。
- 主题含`陌生缩写 / 专业术语 / 生僻词组` → 先查清楚。
- 用户明确要求 或 用户需要"有说服力"但未提供素材 → 补充外部佐证。

若用户已提供完整参考材料（长文本、`.docx`、`.pdf` 等），本步可跳过或降级为只查陌生概念。

### Step2：需求对齐
按 [human-alignment.md](human-alignment.md) 执行。要点：
- 能推断就推断，文字提问 ≤ 3 个
- 风格预览卡按需触发（详见 human-alignment.md §2.3 的跳过条件）
- 无论预览卡是否触发，进入 Step3 前必须确保风格参数已确定（用户选定或 AI 推导）
- 对齐结果中的主题/目标 → 作为 Step3 构建叙事的输入
- 对齐结果中的风格参数（色板/字体/密度基线）→ 作为 Step4 设计阶段的硬约束

### Step3：构建叙事逻辑 （STORY.md）
阅读 [story-principle.md](story-principle.md)，最后生成一个STORY.md的文件。

### Step4：构建页面风格的逻辑 (DESIGN.md)

#### 风格匹配流程

收到用户需求后，执行以下推理判断是否命中预设风格：

**第一步：提取用户意图特征**
从用户 query 中识别：主题领域、目标受众、使用场合、调性倾向。

**第二步：与预设风格比对**

| 风格 | 核心调性 | 适用场景 |
| :--- | :--- | :--- |
| [学术风](designs/design-principle.academic.md) | 可信、证据驱动、蓝白克制 | 高校答辩、科研结题、教学课件（理工医）、学术会议、学科评估、临床/医学汇报、课题开题、实验室组会、科研申报 |
| [商务咨询](designs/design-principle.consulting.md) | 权威、数据密集、结构化分析 | 战略/行业研究、高管 review/董事会、投行/IPO 路演、咨询交付物、企业转型/组织变革、私募/风投/行研、尽职调查 |
| [红金政务风](designs/design-principle.redgold.md) | 庄重、红金热烈、中文优先 | 党政机关汇报、政务/公共部门、国企央企汇报、党课/学习宣讲、周年庆典/红色文化、表彰大会、纪检巡察 |

**第三步：做出判断**

判断标准：用户的场景是否**明确属于**上表某风格所服务的特定领域和受众。

- **命中**：用户场景明确落在某风格的适用场景内 → 使用该预设风格；
- **不命中**（默认路线）：用户场景不属于上述三类特定领域，或场景模糊/泛化/跨领域 → 走通用设计原则；

> ⚠️ **重要原则**：预设风格是为特定垂直领域定制的，不应泛化使用。大量常见场景（如：产品介绍、项目提案、工作总结、培训课件、技术分享、营销方案、团队介绍、述职报告、年终总结等）都应走通用设计原则，由 AI 根据具体需求自由设计。只有当用户场景**明确且典型地**属于学术科研、专业咨询、或党政红色这三个垂直领域时，才使用预设风格。

**判断示例**：
- "做一个硕士毕业答辩PPT" → 明确属于学术场景 → 命中学术风 ✅
- "做一个麦肯锡风格的行业分析" → 明确属于咨询场景 → 命中商务咨询 ✅
- "做一个党支部年度工作汇报" → 明确属于党政场景 → 命中红金政务风 ✅
- "帮我做个述职报告" → 职场通用场景，不属于上述三类特定领域 → 走通用 ✅
- "做一个产品发布会PPT" → 产品/营销场景 → 走通用 ✅
- "做一个季度工作总结" → 职场通用场景 → 走通用 ✅
- "做一个AI技术分享" → 技术/科普场景 → 走通用 ✅

#### 匹配后的执行

- **命中预设风格**：读取对应风格文件，结合用户实际需求设计PPT，**禁止额外生成DESIGN.md**，可以显式声明哪些颜色、字体等内容需要结合用户需求微调；
- **不命中（默认路线）**：读取通用[设计原则](design-principle.md)，结合用户实际需求生成DESIGN.md；


### Step5：创建在线演示文稿并持久化设计契约
> **本步是硬约束，且两个动作不可拆分。**
>
> 1. **创建空的在线演示文稿**，拿到 `docid`。见 `pptx-api.md` §生成类接口（**不查 schema**）。
>    ⚠️ 新建文档**自带一页空白首页**（索引 0），**本步立即删除**（`slide pages delete`，见 `pptx-api.md` §生成类接口与 [pptx-edit.md](pptx-edit.md) 索引）。之后生成页从 `page_index=0` 起依次填入。
> 2. **立即把 `DESIGN.md` 持久化到该文档**。见 `pptx-api.md` §生成类接口。
>
> 🔴 **第 2 步不是可选增强，是写操作的前置门**：设计契约未写入时，后续所有插页、插图、改文字操作都会被服务端**直接拒绝**。跳过本步会导致 Step7 全量失败。
>
> 设计契约有效期 **24 小时**。因此 `DESIGN.md` / `STORY.md` / 每页源码**必须在本地保留副本**——既用于超时后重新写入，也用于页面改坏时整页重做（本链路**没有原生撤销**）。

### Step6：配图准备
> 图片**统一经上传口进 PPT**，三个来源到达出口的路径不同。完整命令见 `pptx-api.md` §配图接口。
>
> | 图片来源 | 获取路径 |
> |---|---|
> | **材料图**（用户上传、材料抽取、用户提供的品牌/产品图） | `media_id` 直传（或本地文件传 `file_path`）→ **上传口** → `url` |
>
> ⚠️ **当前环境没有生图工具，不提供 AI 配图**：不要尝试调用任何生图接口、不要反复重试。材料里没有可用图的图位改用 SVG / 色块 / 版式留白承载（见 `component-image.md` §P1）；**不主动向用户说明没有 AI 配图**，仅当用户明确要求 AI 生图 / 照片级配图时才告知不支持并给替代方案。
>
> 🔴 **所有图片都必经 `wecom-cli smartpage images upload` 上传口**（上传需要 `docid`，故本步在 Step5 建文档之后）：会话图片的 `media_id` 不进 PPT，本地文件不进 PPT。
>
> 拿到 `url` 后**同一条落法**：直接写进 JSX 里 `<Image>` 的 `src`，与文字、图表同页一次性插入。**Step6 要把每个图位的 URL 一次性备齐**（页号 → URL → 宽高），供 Step7 逐页取用。
>
> 🔴 **材料图一律原图直传、零重绘**——任何二次加工都会让数字 / 文字 / 细节走样。
>
> **配图前置**：用到的材料图必须在写该页内容前完成上传与核对，确认清晰、完整、符合上下文后方可使用。
>
> 建议在本步一次性清点全篇图位（依据 `DESIGN.md`），而非边写边想。

### Step7：逐页生成并插入（按大纲顺序）
> 动笔前的心智校准：每一页是一段 JSX 源码，但**它不是 React**——这是一套受限 DSL，由服务端编译成幻灯片。把它当 HTML + 内联 CSS 来写。禁止引入 React 生态任何概念（`import` / `export` / `module` / hooks / state / 函数组件定义），**禁止使用 `<View>` 组件**——容器一律用 `<Box>`；源码最后一个表达式必须是 `<Slide>`。
>
> 动笔前必读：
> - `STORY.md` - 当前PPT的叙事逻辑
> - `DESIGN.md` — 当前 PPT 的设计稿（画布、配色、字号、布局、元素、密度）
> - 相关组件规范 — 本页用到哪个组件，就读取 `component-*.md` 中对应文档
>
> **动笔前禁读**：本项目目录之外的任何 PPT 项目源码。本页 JSX 的全部依据应来自 `DESIGN.md` + 命中分支 `design-principle.<id>.md` + `component-*.md`，不得"借鉴"历史项目的写法或视觉选择。
>
> 严禁仅靠记忆动笔。

约束如下：
- 充分结合 `STORY.md` 和 `DESIGN.md`，按照大纲顺序从第 1 页生成到第 N 页；
- **每页两个动作，逐页闭环**（不要写完全部页面再统一提交）：
  1. 本地 `write_to_file` 保存该页 JSX 源码（文件命名照 `component-slide.md` §文件组织 的 `XX_{slug}.jsx`，与 `DESIGN.md` 页面映射表的「源码文件」列一致）（**这是"改坏了"唯一的回退依据，不可省**）；
  2. 提交该页 → `addjsx`（**单页异步命令**，N 页 = N 次调用）：**用 python 从第 1 步的文件读出源码**组装 payload（见 `pptx-api.md` §命令形态 的红线），**不要把刚写完的源码原文再贴一遍进命令**——那会让同一份内容在上下文里出现两次；图位 `src` 已写上传口 URL（Step6 备齐）。🔴 **`page_index` 必填**，传明确递增索引——第 N 页大纲对应 `page_index=N-1`（Step5 已删除空白首页，索引从 0 起排），**不得省略、不得传 `-1` 追加**。服务端编译成幻灯片，**无后置补图动作**。
- 逐页串行推进；**某页失败只重试该页**，不回滚已成功的页面；
- 动笔自检（每页提交前 9 条硬约束，逐项确认；任意不通过 → 当页返工） 
  - 母版区齐全：默认三区（A 标题块 0–120px / B 内容区 120–660px / C 页脚条 660–720px 含右下页码 NN/TOTAL）； 
  - 标题块右侧不得塞装饰小图（200×70 这种），全篇位置严格一致； 
  - 本页 L1 主视觉占 B 区面积 ≥ DESIGN.md 规定（默认 30%）；不得用 L3 角标顶替 L1 
  - 仅使用项目 DESIGN.md 列出的 ≤ 4 种 hex 与 ≤ 2 套字体家族 
  - 与上一页版式不重复；本页留白比例 ≤ DESIGN.md 上限（常规页 ≤ 35%） 
  - 本页有 ≥ 1 个视觉锚点（≥ 44px 元素 或 ≥ 40% B 区面积的图）；如无 → 必须补充巨型数字/大图/大色块 
  - 本页与上一页视觉重量有显著差异（最大元素面积比 > 1.5:1 或版式结构明显不同）；连续 ≥ 2 页等宽卡片横排 → 返工 
  - 本页色彩分配符合 DESIGN.md 页面映射表：强调色只出现在焦点元素上，主色/辅色/强调色面积比合规 
  - 本页的 role 与 STORY.md 一致：hero 页必须有 ≥ 40% B 区主视觉或 ≥ 48px 锚点数字；supporting 页不得使用 hero 级视觉投入

> **进度预期**：页数与耗时正相关（每页至少一次往返）。若用户要求的篇幅较大，先出大纲与风格确认再开工。

### Step8：核对结构
读回文档结构，确认**页数、页面顺序**与 `STORY.md` 大纲一致，画布尺寸符合 `DESIGN.md`。见 `pptx-api.md` §生成类接口。

发现缺页 / 顺序错位 → 用本地保存的该页源码补插（`page_index` 用目标位置的明确索引）或整页重做，不要重建整份文档。

### Step9：交付
**交付形态只有在线文档链接一种**：生成完成并核对结构无误后，把**在线文档链接**交付给用户。

- 🚨 **禁止导出**：不调用 `doc export`、不产出 `.pptx` 等任何本地文件。任何导出 / 下载诉求（包括用户事后补一句"顺便导一份文件"）→ 直接告知没有导出能力，**不要尝试调用导出命令或伪造下载路径**（见 `SKILL.md`「禁止导出」）。
- **失败收尾口径**：制作中途失败且重试无效时，只说「这次生成没有成功，我换个方式重试 / 稍后再试」；不贴错误码、不描述排查过程、不引用技能规则原文。
- `STORY.md` / `DESIGN.md` / 页面源码等中间产物一律不外发。
