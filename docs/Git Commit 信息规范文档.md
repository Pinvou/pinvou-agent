# Git Commit 信息规范文档

## 1\. 文档目的

为统一项目代码提交规范，规范 Git Commit 日志格式，让提交记录**清晰、标准化、可追溯、可自动化解析**，便于团队协作、代码复盘、版本迭代、自动生成更新日志（CHANGELOG）及语义化版本管理，特制定本规范。

本规范基于业界通用 **Conventional Commits 约定式提交标准** 简化适配，适配日常业务开发场景。

## 2\. 规范适用范围

项目所有分支、所有开发人员的代码提交（git commit）均需遵守本规范，禁止随意编写、无意义、不规范的提交信息。

## 3\. 标准提交格式

### 3\.1 基础格式（必填）

```Plain Text
<type>[可选作用域]: <简短描述>
```

### 3\.2 完整格式（推荐复杂改动使用）

```Plain Text
<type>[可选作用域]: <简短描述>

【可选详细正文：描述改动原因、解决方案、影响范围】

【可选脚注：关联任务ID、BUG编号、破坏性变更说明】
```

### 3\.3 格式说明

- **type（必填）**：提交类型，固定取值，见下文完整类型列表

- **作用域（可选）**：标注改动模块/页面/功能，如 user、order、login、dashboard，用于快速定位代码范围

- **简短描述（必填）**：一句话说明改动内容，简洁精准，不超过 50 字，使用中文、陈述句、无句号

- **详细正文（可选）**：复杂功能、bug 修复、重构优化时补充，说明改动逻辑、解决的问题、注意事项

- **脚注（可选）**：关联任务工单、BUG 链接、版本变更标记

## 4\. 完整 Commit 类型对照表（核心规范）

|类型|全称|使用场景|版本影响|
|---|---|---|---|
|**feat**|Feature|新增业务功能、新增页面、新增接口、新增交互能力、新增配置项|次版本号升级|
|**fix**|Bug Fix|修复测试/线上 Bug、逻辑错误、接口报错、页面异常、数据错误、兼容问题|补丁版本号升级|
|**refactor**|Refactor|代码重构、结构优化、抽离公共方法、调整代码逻辑，**无新功能、无 Bug 修复**|无版本升级|
|**perf**|Performance|性能优化，如接口提速、渲染优化、缓存优化、资源压缩、查询优化|无版本升级|
|**docs**|Documentation|仅修改文档、注释、README、接口文档、使用说明，**无业务代码变更**|无版本升级|
|**style**|Style|代码格式调整、缩进、空格、换行、分号、格式化，**无代码逻辑变更**|无版本升级|
|**test**|Test|新增、修改、删除单元测试、集成测试、测试用例|无版本升级|
|**build**|Build|修改打包配置、构建脚本、Webpack/Vite 配置、升级项目依赖、环境配置|无版本升级|
|**ci**|CI/CD|修改持续集成、自动化部署配置（GitHub Actions、GitLab CI、Jenkins）|无版本升级|
|**chore**|Chore|杂项修改：清理无效代码、临时文件、调整项目目录、修改工具脚本，上述类型外的改动|无版本升级|
|**revert**|Revert|回滚某次历史提交，撤销已合并/提交的代码改动|按需升级|

## 5\. 破坏性变更标记

若本次提交为**不兼容改动、废弃旧接口、修改核心逻辑、影响原有功能使用**，在类型后加 `!` 标记，代表破坏性变更，触发主版本号升级。

格式：`<type>![: 描述]`

示例：

```Plain Text
feat!: 重构用户登录接口，废弃旧版登录参数
fix!: 调整订单状态逻辑，历史订单数据适配变更
```

## 6\. 规范示例（可直接参考复用）

### 6\.1 新增功能

```Plain Text
feat(user): 新增手机号验证码登录功能
feat(order): 新增订单批量导出Excel功能
```

### 6\.2 修复Bug

```Plain Text
fix(pay): 修复微信支付回调参数解析失败问题
fix(form): 解决表单重复提交、按钮未防抖问题
```

### 6\.3 代码重构/优化

```Plain Text
refactor(cart): 抽离商品价格计算公共逻辑
perf(list): 优化列表渲染卡顿、减少重复请求
```

### 6\.4 文档/格式/配置修改

```Plain Text
docs: 更新项目本地启动文档与接口说明
style: 统一全局代码缩进与格式规范
chore: 升级项目依赖版本、清理无用依赖
```

### 6\.5 回滚提交

```Plain Text
revert: 回滚本次订单状态修改提交
```

## 7\. 禁止提交的不规范写法

所有提交**严禁**出现以下情况，团队需严格自查：

- 无意义提交：`update`、`fix bug`、`修改代码`、`测试`

- 类型错误：新增功能用 fix、修复 bug 用 feat

- 描述模糊：不写具体改动内容，仅笼统概括

- 中英文混杂、语句不通、后缀带句号

- 一次提交混杂多种无关改动（需拆分提交，单一职责）

## 8\. 补充最佳实践

1. **单一职责提交**：一次提交只做一件事，避免多类型改动合并提交

2. **提交粒度细小**：功能拆分、迭代提交，避免大段代码一次性提交

3. **描述精准具体**：明确改动点、解决的问题，方便后续追溯排查

4. **关联任务**：重要提交可在正文末尾关联工单/BUG ID，如 `fix: 修复登录异常 #123`

## 9\. 规范价值

- 统一团队提交风格，降低协作沟通成本

- 快速区分新增、修复、优化、重构等改动类型

- 支持工具自动生成 CHANGELOG 版本日志

- 支持语义化版本自动迭代，规范版本发布

- 便于代码复盘、问题追溯、代码评审（CR）
