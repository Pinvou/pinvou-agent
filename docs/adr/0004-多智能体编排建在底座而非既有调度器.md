# 多智能体编排建在 CodeWhale 底座上，不复用既有 Python 调度器

> **2026-08-03 注**：下文「代码落点」等实现细节已由
> [ADR-0006](./0006-多智能体收缩为会话内主动委派模式.md) 取代——运行台账、审批拦截、
> `WORKFLOW_TOOL_NAME` 门禁与 `build_engine_config_for_workflow` 已随收缩退役或改形。
> 仍然有效的是本文的核心选型决策：**多智能体建在 CodeWhale 底座上，不复用既有
> Python 调度器**。下文按历史决策记录保留，不再随实现更新。

仓库里已有一套完整的 Python 工作流调度器（`workflows/_engine/scripts/`，含 Router 循环、状态机、并发扇出、重试回滚、hard 裁决），配套的前端入口 `WorkflowView` 已被下线。它成型于 CodeWhale 尚未提供编排能力的时期；底座此后长出了 `codewhale-workflow` / `codewhale-workflow-js` / `codewhale-lane`，提供编排图的编译期校验、规模上限、风险审批卡、无副作用沙箱、断点续跑、回执与并发控制，且已随 `codewhale-tui` 编译进本应用。

因此多智能体能力另起新入口，直接建在底座的工作流与 Fleet 之上：模型生成编排图、底座编译执行，pinvou3 只负责入口隔离、角色名册与图的展示编辑。既有 Python 调度器保持原样不动，也不做迁移或兼容——新入口与它没有数据交集，老入口本就已下线。

这样做的代价是仓库中会同时存在两套编排实现，其中一套无人调用；这是有意为之，避免为了消灭重复而承担一次无收益的迁移。何时移除旧实现另行决定。

## 代码落点

「无数据交集」在代码结构上同样成立，边界如下：

- `features/multiagent/`：领域层。运行台账（`~/.pinvou3/agent-runs/`，与老调度器的
  `workflows/` 目录分开）、审批拦截判定、终态映射，以及 `roster.rs`
  里的默认角色名册与专家卡入册。`WORKFLOW_TOOL_NAME` 也锚在这里——
  「编排能力只在多智能体入口出现」由 assistant 侧各漏斗引用此常量兜住。
- `app/commands/multiagent.rs`：Tauri 命令，与老调度器所在的 `workflows.rs` 分文件。
- assistant 侧只留装配与转发：`bridge.rs` 的 `build_engine_config_for_workflow`
  （放行工具 + 调 roster 装配名册）、`engine.rs` 的事件臂（落盘 + 广播）、
  `engine_pool.rs` 的禁用列表漏斗。

第一阶段只交付聊天内可达的桌面闭环。编排图模板库、角色独立选模型及其配置界面
不预埋隐藏命令，等出现真实入口时再按本 ADR 的边界补充；当前所有角色继承宿主会话模型。
