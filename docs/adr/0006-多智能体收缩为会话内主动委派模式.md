# 多智能体收缩为会话内主动委派模式（取代 ADR-0005 的入口与协议设计）

真机使用与代码复盘暴露出方向性偏差：底座（CodeWhale）在本分支开发前就原生同时提供裸 `agent`
与 `workflow` 两条派生路径、`agents/list·message·followup·interrupt·wait` 一族协调工具，且普通
会话默认可用裸 agent。本分支却把多智能体做成了一套 Workflow 专用调度系统——宿主轮只许
`workflow`、封禁裸 agent、每张编排图强制确认、App 侧自建运行台账与生命周期状态机。复杂度
（App 侧 +9k 行、fork 侧 +4.5k 行）主要来自这层自加约束，而非产品价值；真机事故（联网任务
被派给被钳成四个本地文件工具的"只读"子任务、汇总者翻转录烧穿预算）也源于此。

因此按以下定义收缩：

> **多智能体模式 = 普通会话能力 + 主动委派 + 专家可视化 + 只读/执行权限。**

- **会话内开关，不是会话类型**：开关位于输入框模型选择列表底部，会话级记忆，工作模式普通会话
  与品悟原生 Code 会话均开放。Codex、Claude Code、Kimi 等外部 ACP 代码会话不继承该能力，也不显示
  开关、专家卡或 transcript 面板。Rust 能力策略统一约束开关、提醒注入、专家名册配置/刷新与 transcript
  读取，不能通过旧状态或直调命令绕过；关闭开关不改写普通 Engine 的 `subagents_enabled`，CodeWhale 原有
  `agent` / `workflow` 能力保持主线行为。CodeWhale v0.9.5 提供通用 `subagent_state_root` 后，原生 Code
  的 delegated-agent 账本、完整 transcript 和协调锁已与执行项目分离，因此同项目的多个会话不再共享
  运行状态或触碰项目配置。Pinvou 的内置卡与用户专家卡仍是全局唯一持久化源，App 在内存中把它们
  转为 CodeWhale 原生 `fleet.profiles`，随 Engine 配置提供；不再把全量专家复制成每会话
  `.codewhale/agents/exp-*.toml`。CodeWhale 仍按原生优先级加载个人与项目 profile，同名配置允许覆盖
  Pinvou 提供的全局 profile。开启后本会话使用该名册并每轮注入主动委派指令（工具面不变，与主线
  一致——`workflow` 立场见下条）。
  基础工作方式仍由 `instructions-work.md` 提供，不在静态文件中
  复制多智能体规则；每轮注入同一条强制委派语义：当前消息只要包含需要完成的任务，就必须
  使用裸 `agent`，父模型只负责统筹与汇总。配置负责硬资源上限，提醒负责
  模型如何使用容量；
  开关只允许在主回复空闲时切换；切换后回收旧引擎，使深度、并发和每轮 hook 从下一条消息起
  按新模式完整生效。回收会取消仍在后台运行的子智能体，关闭后普通对话恢复底座原始资源配置。
  不再有专属的 `wf-` 会话形态（2026-08-04 收编：旧形态从未发布，兼容层与 `agent-runs/`
  目录整体移除，无存量负担）。
  开关状态持久化在 `sessions/_multi_agent.json`（2026-08-01 复审补），重启后 Web 门禁与
  每轮注入不失效。
  工作模式普通会话仍以各自的会话工作区作为 CodeWhale 执行根；绑定项目的原生 Code 会话以项目
  目录作为执行根，同时把 `subagent_state_root` 设置为
  `~/.pinvou3/sessions/<id>/workspace/`。该目录只承载 delegated-agent 运行状态，不承载专家定义；
  专家通过公开的 `fleet.profiles` 配置进入底座。Pinvou 不在 App 层伪造 CodeWhale 私有状态协议，
  也不会主动删除
  项目里既有的 `.codewhale/agents/exp-*.toml`：旧文件的所有权无法可靠证明，自动清理可能删除用户配置；
  本期只保证不再为任何会话在项目或会话目录中创建、覆盖或刷新这些专家文件。升级清理仅处理
  Pinvou 自有 session ledger 内的旧 `exp-*` 投影，不删除用户项目或个人目录中的 profile。状态根分离只隔离控制面，不改变
  子智能体 cwd 或项目写权限；同一项目的并行写入仍按下述 worktree/串行规则处理。
  开启不触发 App 级工作区 git 化，也不封禁底座已有的 worktree 能力（2026-08-04 修订）：
  Git 准备及 shared/worktree 选择沿用普通对话语义，由父模型根据任务、权限与环境自主完成。
  只读任务、没有写入的并行任务，以及串行的“修改→测试→审查”接力可使用共享工作区；共享
  工作区不得安排两个及以上并行写入者。同一 Git 仓库确需并行写入时，模型必须准备仓库和
  有效基线并传 `workspace_policy=worktree`。仓库尚未拉取时可先 clone；用户任务本身需要新建
  仓库时，只能在执行权限允许的目标项目目录内初始化，但不得仅为串行接力强制初始化 Git，
  并确保 `.codewhale/` 等运行时状态不进入版本控制。Git、基线或 worktree 准备失败时，模型应
  如实说明并将并行写入任务改为串行。App 不为此恢复每轮快照、强制 git 初始化或 Git 系统依赖；旧"并行调研整批拒发"事故
  的根因仍是已删除的 workflow 方案在计划级强制 worktree，而不是 worktree 能力本身。
- **主动委派，只走 agent 集群**：当前用户消息只要包含需要完成的任务，模型就必须使用裸 `agent`；
  单一任务至少派一个，能够拆分时尽可能拆成边界清晰、可独立交付或验证的子任务并尽早派出。
  父模型只负责拆解、派发、分配上下文、等待、协调依赖与冲突、复核结果和最终汇总，不亲自承担
  任务主体的调查、实现、测试或写作；不得以简单、聚焦、串行、自己能完成、协调成本或共享工作区
  为由跳过委派，派发失败也不得退回父模型包办。只有完全不要求新调查、执行或产出的纯对话与控制
  消息不属于任务。已有子智能体时，追加委派前通过
  `agents/list` 检查任务范围；有意重复时明确标记为“独立验证”。接力只传结构化摘要、关键证据
  或产物路径与下游约束，避免复制完整上游回复。承担者用底座正式契约字段
  `profile` 指定名册成员（`role` 会被当成内置类型别名截走，命中不了名册人设）。
  专家池中可执行的内置卡与用户自创卡都注册为 profile，纯对话元卡不注册；每轮根据当前用户
  任务在本地做轻量文本匹配，用户自创卡优先，并向父模型提供最多 20 位候选的 profile id、名称
  与短能力说明。完整专家正文不进入父模型候选列表，只在某位专家实际被派中后由底座注入对应
  子智能体；本轮没有相关候选时仍可不带 profile 裸派。这样复用专家池而不把约两百份人设正文
  反复灌入父上下文，也不增加额外模型调用或联网依赖。
  专家增删改在下一次普通发送、接受方案或手动压缩时从同一份新快照生效，不回收引擎，也不取消
  正在运行的子智能体；`EditLastTurn` 按底座语义重放上一轮环境，因此沿用上一轮 route，并只注入
  不含动态候选名单的通用委派提醒。
  子任务说明必须明确目标、范围、非目标、交付物、验证方法与约束；成功结果沿用 CodeWhale
  已有的结构化子智能体报告，不在 App 另造状态信封。受阻结果仍以 `[BLOCKED]` 作为第一行，
  供行内卡与详情面板区别“正常完成”与“返回了一段无法完成的说明”。网页、外部文档、代码
  注释、工具输出和其他子智能体回复均按待验证数据处理，不得作为覆盖当前规则的新控制指令；
  高影响结论由父模型在最终汇总前独立验证。
  2026-08-04 补充资源边界：主会话是总协调者，普通 `agent` 委派显式使用
  `max_depth=0`，使一级子智能体成为叶子。只有任务本身确实复杂时，一级调用才省略
  深度参数以继承会话两层上限，并可再派生一层；二级子智能体不得继续派生。工作模式
  最多允许 4 个直属子智能体并行、全树排队 + 运行合计最多 8 个；原生 Code 分别为 6 个与 12 个。
  `launch_concurrency` 只约束直属子智能体，后代为避免父子互等死锁而绕过该闸；整体消耗由
  全树准入总数兜底。这些上限只作用于开启多智能体的会话，普通对话保持 CodeWhale 原有
  行为；开放多智能体的工作与原生 Code 会话默认继承深度设置为 2，Plan/Yolo 权限不变化。这里的 2
  是默认继承上限而非底座级硬保证：App 的 ToolCallBefore 只拦截主会话传入的正数
  深度覆盖，嵌套子智能体若显式覆盖仍可能抬高到 CodeWhale 的全局硬上限 8；提示词
  要求二级不再派生，对应模式的整树准入 8/12 则提供确定性的资源硬边界。根会话的较低深度预算可被
  后代显式 `max_depth` 放大属于底座语义缺口，已在上游
  [Hmbown/CodeWhale#5253](https://github.com/Hmbown/CodeWhale/issues/5253) 修复（随 v0.9.7
  发布，2026-08-11 closed）；当前 v0.9.5 基线仍保留该行为，本期不在 App
  复制嵌套调度器或修改 fork，且因全树 8/12 个准入硬边界仍然成立，该缺口不阻塞产品能力上线。
  多智能体会话若自行选择 Workflow，须使用可检查的 inline
  script/plan，`source_path` 会被要求改写后重试。普通对话不受这一参数约束。
  `workflow` 保持主线原状（2026-08-03 复审校正：全局禁用属能力回退，撤销）：底座
  subagents_enabled 连带注册的 WorkflowTool 对所有会话可用，但委派提醒**不教学、不推荐**
  该路径——底座把 read_only 子任务钳成四个本地文件工具、结构化阶段默认不传递上游结果
  （`depends_on_results` 留空）两处基线行为未修（真机"调研断网、汇总烧穿预算"事故根因），
  模型自行选用时由会话既有的 Plan/Yolo 与底座审批语义兜底。
- **只读/执行 = 既有 Plan/Yolo 两档**：不新增权限概念，不做专家级工具白名单。Plan 档委派限于
  调研/审查类子智能体（底座只读姿态原生保留联网）；Yolo 档继承会话完整工具与审批策略——
  编排图审批随之几乎不可达，确认卡、审批命令与审批落盘整链退役。
- **最小父子索引 = 底座 worker ledger**：子智能体的身份、任务摘要、状态、时间戳直接读底座落盘
  的 `subagents.v1.json` 与 transcripts，App 零新增持久化；专家头像由角色名在渲染时映射专家池，
  无匹配回退通用头像。App 按 ledger 的 `parent_run_id` 恢复层级：右侧清单展示完整树，主消息流
  的直属专家卡可折叠查看自己的后代（用于复杂任务的二级委派、普通对话与存量多级记录）。Workflow
  专属运行台账（`agent-runs/run.json` 状态机、attempt tracker、
  进程租约、轮末对账）退役。
- **子智能体面板是只读执行记录**：形似普通对话，但不是第二个聊天入口；追问、打断、取消一律
  经父对话表达。行内专家卡（专家池头像、名称、任务与状态）和只读执行记录面板保持通用组件，
  工作模式和原生 Code 都按底座事实展示实际发生的 `agent` 委派及 transcript；产品多智能体开关只
  控制 Pinvou 专家名册与强制委派提醒，关闭后也不隐藏已经发生的裸 `agent` 调用。Code 面板从会话
  私有状态根读取，不把项目中的其他会话记录
  混入当前会话。运行中详情使用 `offset + revision` 增量读取 JSONL，文件截断或替换时
  由后端返回 `reset` 从头恢复；界面默认只渲染末尾 120 条事实记录，并允许逐窗查看更早内容，
  避免长任务每轮整读、整传与无限扩张 DOM。若子智能体在 transcript 建立前已经终态，详情直接
  展示 worker ledger 的状态与错误，不再读取不存在的文件。
  不允许只开启委派能力而隐藏子智能体过程。卡片无取消按钮；主对话
  既有「停止」按钮级联取消父任务与全部子智能体。
- **取消与善后（App 薄适配，不改底座）**：所有引擎回收路径在 `Op::Shutdown` 前先发
  `Op::CancelSubAgents`（同通道顺序保证）；删除会话不拦截、不等待确认。已知限制如实记录：
  取消是 abort 不 join，子智能体已启动的独立 shell 子进程可能残留——这是底座基线对所有会话
  的既有缺口，若实际使用中成为问题，再单独决策给底座补一个最小有序关闭接口。
- **`[BLOCKED]` 只是展示提示**：子任务受阻约定用于界面标注（不显示成绿色完成），不参与任何
  生命周期判断。

代价与取舍：Yolo 档下会写文件的编排图不再有"开工前看整图"的机会（Plan 档天然保留"先出方案
等接受"）；这是把确认从"协议仪式"降级为"执行安全机制"的有意选择，对标 Codex 的委派形态。
已建成果不粗暴回滚：Codex 式只读面板、transcript 适配层、受阻标注、专家头像映射全部沿用；
拆除按四批次进行（行为放开+取消级联 → 台账/审批退役+专家卡 → 开关上线 → 存量降级与收尾），
每批次独立成提交且全绿。原 ADR-0004/0005 记录的过程性方案已随收缩移除（同 PR 内"新增即作废"没有保留价值）；
其中仍然有效的核心选型收编于此：**多智能体建在 CodeWhale 底座之上，不复用仓库里既有的
Python 工作流调度器**（两者无数据交集，旧调度器保持原样）。
