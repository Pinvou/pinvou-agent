# 多智能体入口迁入聊天（Codex 式），会话即运行档案

> **已被取代**：入口形态、"宿主轮只允许 workflow"与每图必停的决策由
> [ADR-0006 多智能体收缩为会话内主动委派模式](0006-多智能体收缩为会话内主动委派模式.md) 取代（2026-07-31）。
> 本文保留作历史记录。

独立的「工作流」功能页作为第一版入口上线后，真机使用暴露出交互硬伤：运行状态与实际执行脱节（宿主轮次阻塞时界面一直显示"编排中"）、并行子任务全部 spawn 失败而界面毫无表示、结果产物无处可看、子智能体是黑盒。用户明确要求按 Codex 桌面版的形态重做：入口放进普通对话，子智能体可以点开看完整对话。

因此入口整体迁入聊天，独立页删除：

- **发起**：聊天输入框的「多智能体」按钮。按下后新开一场多智能体对话（宿主会话）并直接切过去；从既有对话中途发起时，自动携带近几轮摘要作背景（新会话不失忆）。刻意**不**在当前会话就地起跑——那要求把整套按 `wf-` 前缀建立的隔离（工具放行、审批拦截、台账、名册装配、广播漏斗）重写成按会话标记，而 Codex 的参照形态本就是"一个任务=一场对话"。
- **可见性**：宿主会话以「多智能体对话」徽标进入会话列表，标题即用户诉求；删除该对话级联删除运行目录（台账、工作区、产物）。原「运行记录」界面概念随之消失——会话列表就是运行历史。
- **两阶段闸门**：编排 → 执行之间**每次必停**（工作流会话把底座 `workflow.auto_start_read_only` 固定为 false、`workflow.require_approval_for_writes` 固定为 true，并通过底座公开的 `ToolCallBefore → ask` Hook 把 `workflow` 调用送入标准 `ApprovalRequired` 通道），确认卡上看图、改图、批准、拒绝；宿主轮只允许调用 `workflow`，并以拒绝其它审批作纵深，所有实际工具动作都必须进入图中的子任务，不能由宿主绕过编排。第一阶段不预埋只读免确认开关：当前一场宿主会话只维护一条权威运行关联，在并发运行关联模型完善前开放免确认会引入第二张图抢跑与台账串线风险。单槽运行依赖一条明确的跨层契约：底座在执行工具前先经同一 FIFO 事件通道发送本轮全部 `ToolCallStarted`，随后才发送各自的 `ApprovalRequired`；上一张图尚未终态时，应用会在处理新启动的开始事件时把它标记为拒绝，并在对应审批到达时拒绝放行，因此并发的第二张图不能先于审批台账被执行。「单槽」不等于「单轮单次」：上一张图已收到终态（含编译被底座拒收）后，同一宿主轮允许模型修正后重新提交（有次数上限），每张新图仍必经确认卡——真机验证过模型能读错误自行纠正，一刀切拒绝只会把可自愈的失败变成死局。应用侧拦截（并发第二张、重试超限、台账写失败）必须以真实理由呈现在界面上，不得伪装成用户的拒绝操作——底座把 deny 一律回给模型为 "denied by user"，界面若不解释，用户和模型都会误判是谁拒绝了谁。
- **子智能体透明**：底座本就把每个子智能体的完整对话落盘（`.codewhale/state/subagent-transcripts/*.jsonl`），运行面板的 chip 点开右侧抽屉直接读它，运行结束、进程重启后依然可查。
- **专家池串联（数据通路版）**：专家池的用户自创卡自动入册为只读专家角色（上限 8 张，`exp-` 前缀，经 toml 序列化防止卡片正文炸开格式）；主 agent 的入口消息只带每专家一行的名单，完整人设由底座在派工时叠加给被派中的子智能体。内置面具卡不自动入册，选择性入册留给以后的界面。
- **平台范围**：第一阶段仅开放 Tauri 桌面宿主；Web 不加入 capability、命令白名单或事件桥接，也不读取或续写桌面创建的 `wf-` 会话；完整 Web 支持另行设计和验证。

代价与取舍：宿主会话进入列表后，「工作流运行不是 Session」的旧约定作废（术语表已改：会话是运行的入口与档案，运行还包括工作区与产物）；每次必停在只读调研场景多一次点击，这是调试期换取信任与成本可控的有意选择。本决定只改入口形态，不动 ADR-0004——编排仍建在底座 Workflow/Fleet 上，与既有 Python 调度器无数据交集。
