# Headless agentic single-task CLI (`pinvou agent run`)

`pinvou agent run` executes **one product-equivalent agentic turn** inside a windowed Tauri host: the same send path as GUI chat (Yolo mode, product tool allowlist, real Bash / File (write/edit) / Git / Web execution), with the session execution root bound to a caller-provided task directory. It targets external benchmark harnesses (Terminal-Bench/Harbor) that install Pinvou Agent into a task container to perform real terminal work. It does not go through the eval backend (`HeadlessAgentBackend`) and never touches any eval tool policy — the read-only isolation semantics of GAIA-style evaluation are unaffected.

Relationship with `pinvou benchmark ...`: the benchmark subcommand family runs batch evaluation over fixed datasets, with a read-only tool policy and a privacy output pipeline; `agent run` performs full agentic execution of a single task instruction and returns its output (assistant text, tool events, usage) directly to the caller. Both share the same windowless host bootstrap.

## Build and run

```bash
cargo build --manifest-path pinvou-cli/Cargo.toml --bin pinvou
PINVOU3_HOME=/path/to/sandbox pinvou agent run \
    --prompt-file task.txt \
    --workspace /path/to/task-dir \
    --timeout-secs 600 \
    --output json
```

- `--prompt-file` (required): task instruction file; its content enters the product send path verbatim, without any eval envelope.
- `--workspace` (optional): task working directory. When provided, the directory must already exist; it is canonicalized to an absolute path and becomes the engine cwd and the shell execution directory (same mechanism as the project binding of native code sessions; the `ExecutionRootResolver` only applies to this run's session id — fresh or caller-provided). For a fresh session the workspace is also persisted as the session's durable workspace binding, so reopening the session in the desktop app keeps working in that directory; a caller-provided `session_id` keeps its own binding (the run-scoped resolver overrides this run only, and attachment references are rendered absolute in that combination so they resolve against the staging root, not the run cwd). When omitted, a session-private directory is used (the same isolated scratch as eval sessions).
- `--session <ID>` (optional): continue an existing chat session instead of creating one. The session must exist in the sandbox's session store and must be an ordinary chat session — unknown ids fail with `agent_session_not_found`, non-chat (e.g. scheduled-run) sessions with `agent_session_not_chat`. A caller-provided session is never auto-deleted by the run (see the session lifecycle below), and `--workspace` applies to this run only as described above.
- `--mode plan` (optional): submit the read-only plan turn the GUI produces in Plan mode instead of the default full-write Agent turn. The requested mode is also persisted on the session (a persistence failure fails the run before submit), so reopening it in the desktop app restores Plan. Note the mode is per-request: a Plan-mode GUI session continued without `--mode` receives a full-write Agent turn.
- `--model <ID>` (optional): pin the session's model like the GUI per-session model switch; the id must exist in the configured model list (unknown ids fail with `agent_model_not_found`). The chip-switch binding persists on the session — it is written during setup, so it stays in force even if the run later fails or times out.
- `--attach <PATH>` (optional, repeatable): attach files to the prompt through the GUI attachment pipeline — staged into the session's `attachments/` directory, ingested like GUI chip uploads, and referenced from the prompt by path. Source files are kept after ingest (the CLI never deletes caller files). Limits: at most 16 files, 20 MiB each, 100 MiB total; missing paths and over-limit batches fail before the session is created.
- `--timeout-secs` (default 600, capped at 604800 = 7 days): task timeout. The deadline covers the whole task, including session prepare/submit — a hang in either phase still produces a `timeout` report instead of hanging forever. On timeout the turn is cancelled first; if it has not settled within the 30s settle window, the report is emitted immediately and the process never waits unboundedly. The cap is enforced at parse time — an unbounded `u64` would overflow the internal `Instant + Duration` and panic; the library clamps to the same cap (`MAX_TIMEOUT_SECS`) for direct API callers.
- `--output human|json`: `human` prints a session/status line plus the assistant text; `json` prints the full report as a single-line JSON.
- Session lifecycle: sessions persist after the run (GUI parity — engine resources are reclaimed, and the transcript/artifacts/timeline stay under `$PINVOU3_HOME/sessions/<session_id>`, subject to the same 50-session retention cap as the desktop app). A run that fails before producing a report (exit 1) deletes the session it just created, best-effort — and only while it still wears the eval factory title, so a session you adopted (renamed) in the GUI mid-run survives a failed run; an explicit `PINVOU3_AGENT_TASK_KEEP_SESSION=0` sandbox restores the one-shot cleanup too, with the same adoption exception (a renamed session survives even then). Set `PINVOU3_AGENT_TASK_KEEP_SESSION=0|false|no|off` to restore the legacy one-shot cleanup that deletes the temporary session once the report has been produced; the legacy truthy values (`1`/`true`/`yes`/`on`) are still accepted and keep the default. The falsy comparison is ASCII case-insensitive but does not trim whitespace — a quoted `="0 "` counts as keep — so avoid inline comments or stray spaces in harness scripts. A caller-provided `--session` is never deleted by the run regardless of this setting (it still counts toward retention like any chat session). Retention counts these kept sessions against the same 50-per-kind cap as GUI chat sessions: a batch harness looping this command against the desktop's default `PINVOU3_HOME` will evict the user's oldest non-pinned GUI chat sessions. When that actually happens, the run prints a stderr warning carrying the evicted count — including on a failed run, whenever the evicting save happened before the fault — so watch for it, and point `PINVOU3_HOME` at a sandbox for bulk runs. There is no cross-process lock between `--session` and a GUI session open in the app; concurrent writes are last-writer-wins. A fresh run whose turn never started always cleans up its own session — no zero-message stubs. "Never started" is decided on the durable record: if the engine admitted the user message before the fault surfaced, the transcript stays inspectable under the default-keep behavior (the falsy values still remove it, matching the legacy one-shot contract).

Prerequisites: the `settings.json` of the sandbox `PINVOU3_HOME` needs an active model (any OpenAI-compatible endpoint works, `preset = "openai_compatible"`); `PINVOU3_ALLOW_SHELL=1` pins shell authorization without relying on prefs. Tool-call rounds are **not limited anywhere**: no host-level cap and no environment knob exists (the former `PINVOU3_MAX_TOOL_CALLS` knob was removed) — runaway protection comes from the engine's own bounds (2,000 model steps per turn by default, a 3,600 s per-turn wall clock, bounded retries, the cancel boundary), plus this command's `--timeout-secs` watchdog (which cancels the turn and still emits a report) and the FINAL ANSWER output contract. The 2,000-step figure is the host default for the main turn and the sub-agent default alike, not a hard cap on every call: an `agent` call that explicitly passes `max_steps` keeps the foundation's spawn semantics — positive values clamp to the same 2,000 ceiling, and an explicit 0 remains the foundation's unbounded sentinel.

## Output contract

JSON report fields: `session_id`, `status` (`Completed`/`Failed`/`timeout`/`error` or another engine status), `timed_out`, `completed_after_deadline` (timeout race marker: a turn that finished naturally after the deadline but before the cancel took effect keeps the engine's real `status` instead of being rewritten to `timeout`, letting graders distinguish "finished, but past the line" from "cancelled"; absent in older reports, defaults to false), `assistant_text` (last turn's assistant text), `tool_events` (tool names and success flags only, never arguments/results), `usage` (input/output/cache hit/cache miss/cache write/reasoning tokens and context window), `error` (host-side root causes — populated on `status=error` reports and on `timeout` reports whose session setup did not finish in time, whose cancel did not settle, or whose final turn-result read failed after the deadline fired — as well as the engine's own failure message for failed turns). Tool events deliberately carry no payloads, so reports can safely be persisted under `/logs` for harness usage aggregation. While the turn runs, a liveness heartbeat is written to stderr every 10 seconds; stdout stays reserved for the final report.

Exit codes: whenever a report is produced (including `timeout`/`error` statuses) the process exits 0 — in-turn failures are settled by the harness grader from the report, while a non-zero exit would make timed-out tasks count as exceptions instead of zero-reward runs and skew the mean. Non-zero exit codes are reserved for host-level failures (unreadable `--prompt-file`, missing or non-directory `--workspace`, unusable backend, ...); argument errors (missing `--prompt-file`, out-of-range `--timeout-secs`, ...) exit 2.

## Running inside a container (Terminal-Bench shape)

The binary is a dynamically linked Tauri program; task containers need the GTK3/WebKit2GTK 4.1 runtimes and xvfb (the windowed event loop still requires an X server without a display):

```dockerfile
RUN apt-get update && DEBIAN_FRONTEND=noninteractive apt-get install -y \
    libwebkit2gtk-4.1-0 libgtk-3-0 libjavascriptcoregtk-4.1-0 \
    libayatana-appindicator3-1 xvfb xauth ca-certificates procps curl
```

Run as `xvfb-run -a pinvou agent run ...`. The model endpoint must be reachable from inside the container (docker bridge gateway, e.g. `http://172.17.0.1:13000/v1`). Mind glibc forward compatibility: a binary compiled on an older distro baseline (e.g. Debian bookworm) runs on newer baselines, not the other way around.

## Implementation location

- `pinvou3-app/src-tauri/src/features/assistant/product_runtime/agentic_task.rs`: host bootstrap, execution root binding, turn driving, and the timeout watchdog.
- `pinvou-cli/crates/pinvou-product-backend`: the public `run_agentic_task` launcher.
- `pinvou-cli/crates/cli/src/agent_task.rs`: `agent run` argument parsing and output rendering.
