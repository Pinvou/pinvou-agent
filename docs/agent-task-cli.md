# Headless agentic single-task CLI (`pinvou agent run`)

`pinvou agent run` executes **one product-equivalent agentic turn** inside a windowed Tauri host: the same send path as GUI chat (Yolo mode, product tool allowlist, real Bash / File (write/edit) / Git / Web execution), with the session execution root bound to a caller-provided task directory. It targets external benchmark harnesses (Terminal-Bench/Harbor) that install Pinvou Agent into a task container to perform real terminal work. It does not go through the eval backend (`HeadlessAgentBackend`) and never touches any eval tool policy — the read-only isolation semantics of GAIA-style evaluation are unaffected.

Relationship with `pinvou benchmark ...`: the benchmark subcommand family runs batch evaluation over fixed datasets, with a read-only tool policy and a privacy output pipeline; `agent run` performs full agentic execution of a single task instruction and returns its output (assistant text, tool events, usage) directly to the caller. Both share the same windowless host bootstrap.

## Build and run

```bash
cargo build --manifest-path pinvou-cli/Cargo.toml --bin pinvou
PINVOU3_HOME=/path/to/sandbox pinvou agent run \
    --prompt-file task.txt \
    --workspace /path/to/task-dir \
    --timeout-secs 600 \
    --output json
```

- `--prompt-file` (required): task instruction file; its content enters the product send path verbatim, without any eval envelope. Two narrowings over a plain `read_to_string`, both stated in the command's own usage text and both exit 1 (they depend on the resource's content, not on argv): the path must resolve to a **regular file** — symlinks to one are fine, but a FIFO, a character device, `/dev/stdin` or a `<(...)` process substitution is refused, because their read blocks before any cap or deadline could act — and it must be at most **4 MiB**, enforced by a bounded read so an unbounded source cannot be pulled into memory before the engine ever sees it.
- Sandbox pre-flight: before anything else, the run validates the data root the same way every other `pinvou` family does. A `PINVOU3_HOME` that is set but empty, not valid UTF-8 (the app reads it with `std::env::var` and would silently drop it, splitting the store), or that resolves to a relative path fails with exit 1 — as does an empty or unusable `$HOME`, whose `.pinvou3` join is the *relative* `.pinvou3`, i.e. a session store materialized under the current working directory. This matters most here, because this is the command that spawns a real shell agent.
- `--workspace` (optional): task working directory. When provided, the directory must already exist; it is canonicalized to an absolute path and becomes the engine cwd and the shell execution directory (same mechanism as the project binding of native code sessions; the `ExecutionRootResolver` only applies to this run's session id — fresh or caller-provided). For a fresh session the workspace is also persisted as the session's durable workspace binding, so reopening the session in the desktop app keeps working in that directory; a caller-provided `session_id` keeps its own binding (the run-scoped resolver overrides this run only, and attachment references are rendered absolute in that combination so they resolve against the staging root, not the run cwd). When omitted, a fresh session uses a session-private directory (the same isolated scratch as eval sessions) and a caller-provided session keeps its own resolution (its bound directory, else its scratch).
- `--session <ID>` (optional): continue an existing chat session instead of creating one. The session must exist in the sandbox's session store and must be an ordinary chat session — unknown ids fail with `agent_session_not_found`, non-chat (scheduled-run or native code) sessions with `agent_session_not_chat`. A caller-provided session is never auto-deleted by the run (see the session lifecycle below), and `--workspace` applies to this run only as described above.
- `--mode plan` (optional): submit the read-only plan turn the GUI produces in Plan mode instead of the default full-write Agent turn. The requested mode is also persisted on the session (a persistence failure fails the run before submit), so reopening it in the desktop app restores Plan. On a caller-provided `--session`, a setup that fails, or times out before the submit is entered, rolls the session's mode back to its previous durable state — including "no stored mode" — so a run that did no work leaves no permanent change; once the submit is entered the mode stays, exactly like a GUI Plan send. **The mode is per-request, the default is Agent, and it is not inherited from the session.** A `--session` run that omits `--mode` therefore submits a full-write **Agent** turn — real Bash, file writes/edits, Git execution — into a session the desktop app may be holding in **Plan**, and it does so silently: only an explicit `--mode plan` is ever persisted, so the session's stored mode is left untouched and the GUI keeps displaying Plan for a session in which a full-write turn has just run. Pass `--mode plan` on every continuation that must keep Plan's read-only contract; omitting it is not "keep whatever the session had", it is "run with writes".
- `--model <ID>` (optional): pin the session's model like the GUI per-session model switch; the id must exist in the configured model list (unknown ids fail with `agent_model_not_found`). On a caller-provided `--session` the chip-switch binding is written during setup and rolled back on the same setup failure/timeout arm as `--mode plan`, so it stays in force only once the submit is entered; a fresh session that fails goes with its binding whenever the session lifecycle below deletes it as an unadopted stub.
- `--attach <PATH>` (optional, repeatable): attach files to the prompt through the GUI attachment pipeline — staged into the session's `attachments/` directory, ingested like GUI chip uploads, and referenced from the prompt by path. Source files are kept after ingest (the CLI never deletes caller files). Limits: at most 16 files, 20 MiB each, 100 MiB total; missing paths and over-limit batches fail before the session is created.
- `--timeout-secs` (default 600, capped at 604800 = 7 days): task timeout. The deadline covers the whole task, including session prepare/submit — a hang in either phase still produces a `timeout` report instead of hanging forever. On timeout the turn is cancelled first; if it has not settled within the 30s settle window, the report is emitted immediately and the process never waits unboundedly. The cap is enforced at parse time — an unbounded `u64` would overflow the internal `Instant + Duration` and panic; the library clamps to the same cap (`MAX_TIMEOUT_SECS`) for direct API callers.
- `--output human|json`: `human` prints a session/status line plus the assistant text; `json` prints the full report as a single-line JSON.
- Session lifecycle: sessions persist after the run (GUI parity — engine resources are reclaimed, and the transcript/artifacts/timeline stay under `$PINVOU3_HOME/sessions/<session_id>`). Fresh `agent run` sessions are evicted against a **headless retention budget of their own** (50 sessions, keyed on the `agentic_` id prefix; pinned sessions are exempt), separate from the desktop app's chat sessions, so no number of runs can evict a conversation started in the GUI. When the prepare-time save evicts older headless sessions at that cap, a stderr warning carries the evicted count — also on a failed run whose evicting save preceded the fault. These kept sessions stay available for later continuation (`--session`, or a library caller's `session_id`). A caller-provided `--session` is never deleted by the run regardless of any setting. A fresh session created by this run carries the shared new-chat placeholder title, which is also the runner's **adoption marker**. Under the default keep behaviour exactly one path deletes a session: a run that fails outright (an `Err` outcome — no report was produced, the CLI exits 1 and prints no session id) on a session it created itself. Even there the delete is best-effort and conditional, read at teardown:
  - a turn the engine is **still running** keeps it: engine liveness outranks the durable record, whose first write lands asynchronously after admission;
  - a record carrying an **admitted user message** is treated as adopted and kept — content this failed run cannot prove it produced (a GUI user may have opened the session mid-run). The title alone cannot see such a user: the GUI's auto-rename off the placeholder lands long after the message;
  - any other title means a rename, which is ownership, and keeps;
  - an unreadable record keeps, because deleting on unknown state is the unsafe direction;
  - only a zero-message record on an idle engine still wearing the placeholder is this run's own unadopted stub, and is cleaned up.
  These keeps are independent of `PINVOU3_AGENT_TASK_KEEP_SESSION`. The **setup timeout is not a failed run** in this sense and keeps its session: it is the one never-submitted path that still returns an `Ok` timeout report, and the id it reports to the caller must stay resolvable. Set `PINVOU3_AGENT_TASK_KEEP_SESSION=0|false|no|off` to restore the legacy one-shot cleanup, which deletes a fresh session once a report has been produced — a completed turn, an in-turn error, **or the setup timeout**. That branch is deliberately title-blind and message-blind: the caller asked for a clean sandbox and owns everything the run wrote, so the only thing that stops the delete is a record that cannot be read at all. Under the falsy values a library request marking an attachment `remove_after_ingest` is refused up front, since it would lose both the source and the staged copy. The legacy truthy values (`1`/`true`/`yes`/`on`) and any value outside both lists (e.g. `=cleanup`) keep — a flip from the legacy parse, where only `1|true|yes|on` kept and every other value, including unset, deleted. The falsy comparison is ASCII case-insensitive but does not trim whitespace — a quoted `="0 "` or an empty value counts as keep — so avoid inline comments or stray spaces in harness scripts. There is no cross-process lock between `--session` and a GUI session open in the app; concurrent writes are last-writer-wins.
- Session title: `agent run` does **not** rename the session it creates. The fresh session keeps the localizable new-chat placeholder, for two reasons. It is the exact sentinel the GUI's auto-rename triggers on, so stamping a literal label here would freeze the session's name forever; and that label was untranslated English (`CLI agent run <epoch>`) in all three UI languages, which is exactly what the session store's placeholder now exists to avoid for headless sessions that surface in the GUI history. The placeholder is also what lets a failed fresh run recognize its own session as unadopted and clean it up. Give the session a name from the desktop app, or with `pinvou sessions rename`.

Prerequisites: the `settings.json` of the sandbox `PINVOU3_HOME` needs an active model (any OpenAI-compatible endpoint works, `preset = "openai_compatible"`); `PINVOU3_ALLOW_SHELL=1` pins shell authorization without relying on prefs. Tool-call rounds are **not limited anywhere**: no host-level cap and no environment knob exists (the former `PINVOU3_MAX_TOOL_CALLS` knob was removed) — runaway protection comes from the engine's own bounds (200 model steps per turn, a 3,600 s per-turn wall clock, bounded retries, the cancel boundary), plus this command's `--timeout-secs` watchdog (which cancels the turn and still emits a report) and the FINAL ANSWER output contract.

## Output contract

JSON report fields: `session_id`, `status` (`Completed`/`Failed`/`timeout`/`error` or another engine status), `timed_out`, `completed_after_deadline` (timeout race marker: a turn that finished naturally after the deadline but before the cancel took effect keeps the engine's real `status` instead of being rewritten to `timeout`, letting graders distinguish "finished, but past the line" from "cancelled"; absent in older reports, defaults to false), `assistant_text` (last turn's assistant text), `tool_events` (tool names and success flags only, never arguments/results), `usage` (input/output/cache hit/cache miss/cache write/reasoning tokens and context window), `error` (host-side root causes — populated on `status=error` reports and on `timeout` reports whose session setup did not finish in time, whose cancel did not settle, or whose final turn-result read failed after the deadline fired — as well as the engine's own failure message for failed turns). Tool events deliberately carry no payloads, so reports can safely be persisted under `/logs` for harness usage aggregation. While the turn runs, a liveness heartbeat is written to stderr every 10 seconds; stdout stays reserved for the final report.

Exit codes: whenever a report is produced (including `timeout`/`error` statuses) the process exits 0 — in-turn failures are settled by the harness grader from the report, while a non-zero exit would make timed-out tasks count as exceptions instead of zero-reward runs and skew the mean. Non-zero exit codes follow the CLI-wide rule that exit 2 is reserved for what is decidable from argv alone: argument errors (missing `--prompt-file`, out-of-range `--timeout-secs`, a `--mode` that is neither `plan` nor `agent`, a malformed `--session` id, a duplicated flag, ...) exit 2, while everything that depends on a resource's content or the host's state is exit 1 — an unreadable, non-regular or over-4-MiB `--prompt-file`, a missing or non-directory `--workspace`, a relative/empty `PINVOU3_HOME` or unusable `$HOME`, an unusable backend.

## Running inside a container (Terminal-Bench shape)

The binary is a dynamically linked Tauri program; task containers need the GTK3/WebKit2GTK 4.1 runtimes and xvfb (the windowed event loop still requires an X server without a display):

```dockerfile
RUN apt-get update && DEBIAN_FRONTEND=noninteractive apt-get install -y \
    libwebkit2gtk-4.1-0 libgtk-3-0 libjavascriptcoregtk-4.1-0 \
    libayatana-appindicator3-1 xvfb xauth ca-certificates procps curl
```

Run as `xvfb-run -a pinvou agent run ...`. The model endpoint must be reachable from inside the container (docker bridge gateway, e.g. `http://172.17.0.1:13000/v1`). Mind glibc forward compatibility: a binary compiled on an older distro baseline (e.g. Debian bookworm) runs on newer baselines, not the other way around.

## Implementation location

- `pinvou3-app/src-tauri/src/features/assistant/product_runtime/agentic_task.rs`: host bootstrap, execution root binding, turn driving, and the timeout watchdog.
- `pinvou-cli/crates/pinvou-product-backend`: the public `run_agentic_task` launcher.
- `pinvou-cli/crates/cli/src/agent_task.rs`: `agent run` argument parsing and output rendering.
