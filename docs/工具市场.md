# 工具市场设计方案

最后更新: 2026-06-12

## 一、产品定位

工具市场是 pinvou3 的**能力扩展中心**。用户在市场里浏览、安装、卸载 MCP 工具，改变 LLM 可用的能力集。

核心交互：
- **未安装**天气工具 → 用户问天气 → LLM 走 `web_search` 联网检索
- **已安装**天气工具 → 用户问天气 → LLM 调 `mcp_weather_get_weather` → 前端渲染天气卡片

## 三、工具的载体

每个市场工具 = 一个或多个 **MCP Server**，分两种类型：

- **本地 stdio**：Python 脚本，通过 `command/args` 启动（如天气、问财）
- **远程 HTTP**：云端 MCP 服务，通过 `url/headers` 连接（如企查查）

### 3.1 工具 Manifest

每个工具目录下有一个 `manifest.json`，定义元数据和路由规则：

```
pinvou3-app/resources/mcp-servers/
├── weather/
│   ├── manifest.json
│   └── server.py
├── email/
│   ├── manifest.json
│   └── server.py
└── ...
```

manifest.json 示例（天气）：

```json
{
  "id": "weather",
  "name": "高德天气",
  "description": "查询国内城市实时天气与未来预报",
  "version": "1.0.0",
  "icon": "cloud-sun",
  "category": "生活工具",
  "mcp_tools": ["mcp_weather_get_weather"],
  "command": "python",
  "args": ["server.py"],
  "env": {
    "AMAP_KEY": "2bc7f30dc77ea6eda286775e99ce9cbb"
  },
  "config_fields": [],
  "routing_rules": [
    "天气/气温/温度/下雨/下雪/穿衣/带伞 → `mcp_weather_get_weather`，不要用 `web_search`"
  ],
  "tool_table_entries": [
    "| 天气 | `mcp_weather_get_weather` (高德天气 API,参数 city + days) |"
  ],
  "pip_dependencies": ["mcp", "httpx"]
}
```

字段说明：
| 字段 | 用途 |
|------|------|
| `id` | 唯一标识，对应 mcp.json 的 server name（本地工具）或安装记录标识（远程工具） |
| `mcp_tools` | 该 server 注册的 MCP 工具名列表（前端判断卡片渲染用） |
| `command` / `args` | **本地工具**：MCP server 启动命令（写入 mcp.json） |
| `env` | 环境变量（API key 等，写入 mcp.json） |
| `config_fields` | 需要用户填写的配置项（如自定义 API key），空数组=开箱即用 |
| `routing_rules` | **核心**：安装后注入 system prompt 的路由规则 |
| `tool_table_entries` | 安装后注入 instructions §1 工具表的条目 |
| `pip_dependencies` | Python 依赖，安装时自动 `pip install`（失败则安装中止并报错） |
| `servers` | **远程工具**：多 server 配置数组（见下方远程工具示例） |

### 3.2 远程工具 Manifest（新增）

远程 MCP 工具不需要本地 Python，通过 HTTP 连接云端服务。一个工具可对应多个 server endpoint：

```json
{
  "id": "qcc",
  "name": "企查查",
  "description": "企业工商、风控、知产、经营数据查询 — 182个企业数据工具",
  "version": "1.0.0",
  "icon": "building",
  "category": "金融数据",
  "mcp_tools": [],
  "command": "",
  "args": [],
  "env": {
    "QCC_API_KEY": "<内置Key或留空>"
  },
  "config_fields": [],
  "servers": [
    { "name": "qcc-company",   "url": "https://agent.qcc.com/mcp/company/stream" },
    { "name": "qcc-risk",      "url": "https://agent.qcc.com/mcp/risk/stream" },
    { "name": "qcc-ipr",       "url": "https://agent.qcc.com/mcp/ipr/stream" },
    { "name": "qcc-operation", "url": "https://agent.qcc.com/mcp/operation/stream" }
  ],
  "routing_rules": [
    "企业/公司/工商/股东/法人/风险/失信/专利/商标/招投标/供应商/高管/董监高 → `qcc-*` 系列工具，不要用 `web_search`"
  ],
  "tool_table_entries": [
    "| 企业信息 | `mcp_qcc-company_*` (企查查: 工商登记/股东/财务) |",
    "| 风险查询 | `mcp_qcc-risk_*` (企查查: 失信/被执行/行政处罚) |",
    "| 知识产权 | `mcp_qcc-ipr_*` (企查查: 专利/商标/软著) |",
    "| 经营数据 | `mcp_qcc-operation_*` (企查查: 招投标/资质/舆情) |"
  ],
  "pip_dependencies": []
}
```

> **内置 Key vs 用户配置**：开发/内测阶段 `env` 内置 Key、`config_fields` 为空（一键安装）；
> 正式上线时 `env` 清空、`config_fields` 加回 `QCC_API_KEY`（按钮自动变「配置」）。

**与本地工具的区别：**

| | 本地工具（天气、问财） | 远程工具（企查查） |
|---|---|---|
| 传输协议 | stdio | Streamable HTTP |
| mcp.json 写法 | `command` + `args` + `env` | `url` + `headers` |
| 依赖安装 | pip install | 无 |
| 安装耗时 | 数秒~数分钟 | 秒完（只写配置） |
| manifest 字段 | `command`/`args`/`pip_dependencies` | `servers` 数组 |
| 一个工具对应 | 1 个 mcp.json server 条目 | 可能多个 server 条目 |

### 3.3 工具来源

**v1：内置 bundle**
- 工具随 app 打包在 `pinvou3-app/resources/mcp-servers/` 下
- `bundle.rs` 解包到 `~/.pinvou3/bundle/mcp-servers/`
- 用户在市场页面"添加"后写入 mcp.json 并生效

**v2（远期）：远程仓库**
- 从 Git 仓库或 HTTP registry 下载新工具
- 下载到 `~/.pinvou3/user/mcp-servers/`

## 四、安装/卸载流程

### 4.1 安装

**本地工具（如天气、问财）：**
```
用户点「安装」
  → 有 config_fields？弹配置弹窗让用户填 API Key → 确认（问财/天气无 config_fields，直接安装）
  → 前端 invoke('install_marketplace_tool', { toolId })
  → Rust MarketplaceManager::install():
    1. 读 manifest.json
    2. 自动安装 Python 依赖：pip install <pip_dependencies>（问财无依赖，跳过）
    3. 写 installed.json：追加 tool_id
    4. 写 mcp.json：在 servers 下加一条 command/args/env（内置 Key 从 manifest.env 自动带入）
  → 前端弹 iOS Alert（"已安装 · 新会话生效" + 新建会话按钮）
```

**远程工具（如企查查）：**

内置 Key 阶段（开发/内测）：
```
用户点「安装」（与天气/问财一致）
  → 前端 invoke('install_marketplace_tool', { toolId: "qcc" })
  → Rust MarketplaceManager::install():
    1. 读 manifest.json
    2. 无需 pip install（pip_dependencies 为空）
    3. 写 installed.json：追加 tool_id
    4. 检测 manifest.servers[] 非空 → 远程工具分支
    5. 从 manifest.env 中读取内置 Key（QCC_API_KEY）
    6. 遍历 manifest.servers[]，在 mcp.json 中写入多条 url/headers 配置：
       {
         "qcc-company": {
           "url": "https://agent.qcc.com/mcp/company/stream",
           "headers": { "Authorization": "Bearer MGpgzx..." }
         },
         "qcc-risk": { ... },
         "qcc-ipr": { ... },
         "qcc-operation": { ... }
       }
  → 前端弹 iOS Alert（"已安装 · 新会话生效" + 新建会话按钮）
```

正式上线阶段（用户填 Key）：
```
用户点「配置」（config_fields 非空时自动切换）
  → 弹配置弹窗让用户填 API Key → 确认
  → 前端 invoke('install_marketplace_tool', { toolId: "qcc", config: { QCC_API_KEY: "xxx" } })
  → 后续流程同上，但 Key 来自 user_config 而非 manifest.env
```

### 4.2 卸载

```
用户点"卸载"
  → 前端 invoke('uninstall_marketplace_tool', { toolId })
  → Rust MarketplaceManager::uninstall():
    1. 从 installed.json 移除 tool_id
    2. 本地工具：从 mcp.json 删掉 tool_id 对应的 server 条目
       远程工具：从 mcp.json 删掉 manifest.servers[] 中所有 name 对应的条目
  → 前端弹 iOS Alert（"已卸载 · 新会话生效" + 新建会话按钮）
```

v1 不支持热重载：已运行的 session 不受影响，新建 session 时读取最新 mcp.json + installed.json 生效。

### 4.3 已安装状态持久化

```
~/.pinvou3/marketplace/
└── installed.json    ← ["weather", "email", ...]
```

app 启动时读取此文件，确定哪些工具是已安装状态。

## 五、LLM 行为切换（方案 B：动态 instructions）

### 5.1 原理

`build_session_system_prompt()` 渲染 `INSTRUCTIONS_MD` 模板时，根据已安装工具列表动态拼接路由规则段。

当前 instructions.md 中的静态写法：

```markdown
### 工具路由(优先用专用工具,不要用 web_search 替代)
- 天气/气温/温度/下雨/下雪/穿衣/带伞 → `mcp_weather_get_weather`，不要用 `web_search`
```

改为模板占位符：

```markdown
{{MARKETPLACE_TOOLS}}
```

### 5.2 动态拼接逻辑

```rust
// bridge/mod.rs — build_session_system_prompt()
let marketplace_fragment = MarketplaceManager::new().build_instructions_fragment();

INSTRUCTIONS_MD
    .replace("{{PINVOU3_WORKSPACE}}", &ws.to_string_lossy())
    .replace("{{PINVOU3_SUDO_INSTRUCTION}}", ...)
    .replace("{{MARKETPLACE_TOOLS}}", &marketplace_fragment)
```

```rust

// 根据已安装工具生成两部分：
// 1. tool_table_entries — 注入到 instructions §1 工具表
// 2. routing_rules — 注入到路由规则段
pub fn build_instructions_fragment(&self) -> String {
    let installed = self.installed_ids(); // 读 installed.json
    // 遍历已安装工具的 manifest，拼接 tool_table_entries + routing_rules
    ...
}
```

### 5.3 效果

| 场景 | installed.json | system prompt 路由段 | LLM 行为 |
|------|---------------|---------------------|----------|
| 天气工具未安装 | `[]` | （空，不出现） | 用户问天气 → `web_search` |
| 天气工具已安装 | `["weather"]` | `天气/气温/... → mcp_weather_get_weather` | 用户问天气 → MCP 工具 → 天气卡片 |
| 多工具已安装 | `["weather","email"]` | 两条路由规则 | 各走各的专用工具 |

### 5.4 为什么不用 tool_search（方案 C）

| | B: 动态 instructions | C: tool_search |
|---|---|---|
| **可靠性** | 模型直接看到路由规则，一轮命中 | 模型先搜再调，多一轮出错机会 |
| **弱模型友好** | Qwen3.6 遵循明确指令 OK | Qwen3.6 搜索+激活链路不稳定 |
| **安全性** | 不影响 blocklist | tool_search 一旦放开可能激活 blocklist 里的 60+ 隐藏工具 |
| **token 成本** | 每条路由 ~20 token，10 个工具 ~200 token | tool_search schema 自身 ~200 token + 每次搜索一轮来回 |
| **天花板** | 10+ 工具时 prompt 膨胀 → 转代码级路由 | 工具多时搜索准确率反而更高 |

**结论**：当前阶段（≤10 工具）B 完胜。10+ 工具时不走 C，走 MegaClaw 式代码级关键词预路由（零 token 消耗）。

## 六、前端工具市场页面

### 6.1 设计原则

**保留现有精美 UI 不变**（精选 carousel、分类筛选、搜索、卡片列表、详情弹窗），只改按钮逻辑。
用户体验 = 应用商店：安装即可用，卸载即消失，不暴露配置面板。

### 6.2 数据架构：前端 mock + 后端状态合并

前端维护完整的工具目录（`tsToolsData`，12 条 mock 数据），每条增加 `backendId` 字段关联后端 manifest：

```js
// 有后端 manifest 的工具 — 可安装/卸载
{ id: 1, backendId: 'weather', title: '天气查询 MCP', ... }

// 内置 API Key 的工具 — 按钮显示"安装"（与天气一致）
{ id: 2, backendId: 'iwencai', title: '同花顺问财', ... }

// 尚无后端 manifest 的工具 — 展示"即将上线"
{ id: 3, backendId: null, title: 'QQ邮箱 API', ... }
```

页面 mount 时调 `list_marketplace_tools()` 获取后端已安装列表，合并到 mock 数据的 `installed` 字段：

```js
useEffect(() => {
  window.__TAURI__.core.invoke('list_marketplace_tools')
    .then(backendTools => {
      const installedIds = new Set(backendTools.filter(t => t.installed).map(t => t.id));
      setTools(tsToolsData.map(t => ({
        ...t,
        installed: t.backendId ? installedIds.has(t.backendId) : false,
        available: !!t.backendId,  // 有后端 manifest = 可操作
      })));
    });
}, []);
```

### 6.3 按钮逻辑（三态统一）

所有出现按钮的位置（一级卡片、carousel 底部小卡片、详情弹窗）逻辑一致：

| 状态 | 按钮文字 | 样式 | 点击行为 |
|------|---------|------|---------|
| `available && !installed && 无config_fields` | 安装 | 蓝色实心 | invoke `install_marketplace_tool` → 刷新状态 → 弹 Alert |
| `available && !installed && 有config_fields` | 配置 | 蓝色实心 | 弹配置弹窗 → 用户填 API Key → 确认后 invoke install → 弹 Alert |
| `available && installed` | 卸载 | 红色描边 | invoke `uninstall_marketplace_tool` → 刷新状态 → 弹 Alert |
| `!available` | 即将上线 | 灰色 disabled | 无 |
| 操作中 | ... | 半透明 + cursor-wait | disabled |

**按钮文案判断**：manifest 中 `config_fields` 非空 → 显示「配置」；为空 → 显示「安装」。已安装统一显示「卸载」。

- 按钮区与 Alert 一致：`border-t` 分隔，全宽按钮

### 6.5 工具介绍卡片（安装后引导）

> **现状（2026-06-15）**：最终实现为**方案 A 纯前端卡片**（见 11.1），不发 LLM query。该特性曾在合并中被误删、现已还原，详见 **10.18**。本节描述的「自动发送介绍请求」是早期方案，已被方案 A 取代。

安装工具后点「新建会话」，自动发送一条介绍请求，LLM 回复时渲染工具介绍卡片，帮助用户了解工具能力。

**完整交互流程：**
```
用户在工具市场安装「同花顺问财」
  → 弹出成功 Alert（"已安装 · 新会话生效"）
  → 用户点「新建会话」
  → handleNewChat({ justInstalledTool: 'iwencai' })
  → bridge.createNewSession()  // 进草稿态
  → setCurrentView('chat')     // 跳转聊天页
  → 自动调用 bridge.sendMessage("介绍下同花顺问财工具")
  → LLM 收到 query，生成回复
  → 前端在 assistant 回复区域渲染工具介绍卡片（替代/补充纯文字）
```

**卡片 UI：** 见 `docs/前端/同花顺问财功能介绍卡片.md`（已设计完成）。

**集成适配：**
- 去掉深浅色切换按钮（跟随 app 主题，通过 `isDark` prop 控制）
- 卡片宽度对齐聊天气泡（`max-w-[800px]`）
- 点击 chip → 调用 `bridge.sendMessage(chipText)` 发送

**开发步骤：**

**Step 1：传递安装信号**
- App 组件新增 state：`const [justInstalledTool, setJustInstalledTool] = useState(null)`
- TsAlert「新建会话」按钮的 onClick 改为：
  ```js
  // 原来：onClick={() => { handleNewChat(); setAlert({...}) }}
  // 改为：
  onClick={() => {
    setJustInstalledTool(alert.toolId);  // 记录刚装的工具
    handleNewChat();
    setAlert({ visible: false });
  }}
  ```
- `alert` state 扩展：安装成功时保存 `toolId`
  ```js
  setAlert({ visible: true, title: '已安装「同花顺问财」', toolId: 'iwencai', ... })
  ```

**Step 2：自动发送介绍 query**
- ChatView 中检测 `justInstalledTool` 变化：
  ```js
  useEffect(() => {
    if (justInstalledTool && bridge.available) {
      const tool = tsToolsData.find(t => t.backendId === justInstalledTool);
      if (tool) {
        bridge.sendMessage(`介绍下${tool.title}工具`);
      }
      setJustInstalledTool(null);  // 只触发一次
    }
  }, [justInstalledTool, currentView]);
  ```

**Step 3：渲染工具介绍卡片**
- 在 assistant 回复的渲染逻辑中，检测是否是工具介绍回复
- 检测方式：对话的第一条 user message 匹配 `介绍下XXX工具` 模式
- 匹配到则在 assistant 回复中插入 `ToolWelcomeCard` 组件（从 `docs/前端/同花顺问财功能介绍卡片.md` 移植）

### 6.6 操作结果弹窗（iOS Alert 风格）

安装/卸载成功后弹出**居中 Alert 弹窗**，不自动消失，用户必须主动操作：

```
┌──────────────────────────────┐
│                              │
│      ✓ 已安装「高德天气」      │
│                              │
│   新工具需要在新会话中生效      │
│                              │
├──────────────────────────────┤
│          知道了               │  ← 常规色，关闭弹窗留在市场
├──────────────────────────────┤
│        新建会话               │  ← 蓝色加粗，关闭弹窗 + 新建 session + 跳转聊天
└──────────────────────────────┘
```

卸载时文案变为「已卸载「高德天气」」，副标题变为「已移除，新会话将不再加载该工具」。

操作失败时只显示标题「操作失败，请重试」+ 「知道了」按钮，不显示副标题和「新建会话」（通过 `isError` 标记区分）。

为什么用 Alert 而不是 Toast：
- Toast 3 秒消失太不起眼，用户容易错过"需要新会话"这个关键信息
- Alert 强制用户看到，并且直接提供「新建会话」快捷操作，一步到位
- 符合 iOS 对重要操作结果的交互惯例

样式规范：
- 居中弹窗，毛玻璃遮罩（`backdrop-blur-md`）
- 弹窗圆角 `rounded-[20px]`，宽度 `max-w-[280px]`（iOS Alert 标准窄宽）
- 浅色模式：`bg-white/95 text-slate-900`
- 深色模式：`bg-[#2C2C2E]/95 text-white`
- 标题 17px 加粗居中，说明文字 13px 常规居中
- 按钮区底部排列，每个按钮占满宽度，用 `border-t` 分隔
- 「知道了」= 常规字重蓝色，「新建会话」= 加粗蓝色
- 弹窗出现用 scale + opacity 动画（`@keyframes tsAlertIn` 从 1.05 缩到 1.0）

### 6.6 安装中 Loading 蒙层

安装工具时后端需要 pip install 依赖（pytdx 等），耗时 10-30 秒。当前按钮只显示"..."不够明确，需要 loading 状态。

**交互流程：**
```
本地工具（有 pip_dependencies）点击「安装」/「配置」
  → 有 config_fields？先弹配置弹窗 → 确认后
  → 立即弹出 loading 蒙层（全屏遮罩，不可关闭，不可点击其他元素）
  → 后端 async（spawn_blocking）执行 pip install + 写配置
  → 完成后 loading 蒙层消失 → 弹出成功/失败 iOS Alert

远程工具（无 pip_dependencies）点击「配置」
  → 弹配置弹窗 → 用户填 API Key → 确认
  → 不显示 loading（只写 mcp.json，瞬间完成）
  → 直接弹出成功 iOS Alert

点击「卸载」
  → 不显示 loading（卸载只删配置，瞬间完成）
  → 直接弹出 iOS Alert
```

**注意**：`install_marketplace_tool` 必须是 async Tauri command（`spawn_blocking`），否则 pip install 阻塞主线程导致 UI 卡死。

**pip 加速**：默认使用清华镜像源（`-i https://pypi.tuna.tsinghua.edu.cn/simple`），pytdx 含 numpy/pandas 等重型依赖，首次安装可能需要 1-3 分钟。

**Loading 蒙层设计：**
```
┌──────────────────────────────┐
│                              │
│        ◐ (旋转 spinner)      │
│                              │
│   正在安装「通达信行情」       │
│                              │
│   安装 Python 依赖中…         │
│                              │
└──────────────────────────────┘
```

**实现方式：**
- 复用 `TsAlert` 组件，新增 `loading` 状态（与 `visible` 互斥）
- `alert` state 扩展：`{ visible, loading, title, subtitle, isInstall, isError }`
- `loading=true` 时渲染 spinner + 标题 + 副标题，无按钮，backdrop 不可点击关闭
- `handleAction` 流程：
  1. 安装：`setAlert({ loading: true, title: '正在安装「XX」', subtitle: '首次安装需下载依赖，请耐心等待…' })`
  2. invoke 完成：`setAlert({ visible: true, loading: false, title: '已安装「XX」', ... })`
  3. 卸载：不设 loading，直接 invoke → `setAlert({ visible: true, ... })`

**State 提升（防切页丢失）：**
- `alert` 和 `busyId` 从 `ToolStoreView` 内部提升到 `App` 组件
- `ToolStoreView` 通过 props 接收 `alert`、`busyId`、`setAlert`、`setBusyId`
- 用户切走页面再切回，loading 蒙层仍在；安装完成后正常弹成功 Alert
- 这样做的原因：`ToolStoreView` unmount 后内部 state 被销毁，async invoke 完成时 setState 无效

**样式规范：**
- 与 iOS Alert 同容器样式：`rounded-[20px]`、`w-[280px]`、backdrop blur
- Spinner：CSS `@keyframes tsSpinner` 旋转，24x24 圆形，蓝色(`#007AFF` / `#0A84FF`)
- 标题 17px 加粗居中，副标题 13px 常规居中，与 Alert 一致
- 无按钮区域，无 border-t 分隔线

### 8.1 天气 MCP（Phase 1，已完成）

基于高德地图 API 的天气查询工具，pinvou3 第一个真实 MCP 工具。

**调用链路**：
```
用户: "杭州明天天气"

  → DeepSeek-TUI MCP client ──stdio──→ weather server.py
```

**MCP server**：`pinvou3-app/resources/mcp-servers/weather/server.py`（~146 行）
- 协议：MCP stdio，`mcp` Python SDK + `httpx`
- 注册工具 `get_weather`，参数 `city`（string）、`days`（JSON 数组，0=今天 1=明天，最多 4 天）

```json
  "highTemp": "31",
  "lowTemp": "23",
  "windDirection": "东南",
  "windPower": "3",
  "queryMode": "today | single_day | multi",
  "daily": [
    {
      "date": "2026-06-10",
      "week": "周三",
      "dayWeather": "多云",
```

### 8.2 天气 MCP Bug 记录

#### Bug #1：MCP server "Failed to find MCP server: weather"

**根因**：天气 server 配置被写到 `~/.deepseek/mcp.json`（DeepSeek-TUI 默认位置），但 pinvou3 有路径隔离，读的是 `~/.pinvou3/bundle/mcp.json`。

**修复**：配置写到 `~/.pinvou3/bundle/mcp.json`。

**教训**：pinvou3 所有配置在 `~/.pinvou3/` 下（`bridge/paths.rs`），不要用 `~/.deepseek/`。现在由 MarketplaceManager 统一管理 mcp.json，不再手动配置。

#### Bug #2：vLLM 连接地址回退 127.0.0.1

**根因**：`bridge/mod.rs` 的 `LOCAL_VLLM_BASE_URL` 硬编码为 `http://127.0.0.1:8000/v1`，新终端启动丢失 `DEEPSEEK_BASE_URL` 环境变量。

**修复**：启动命令加 `DEEPSEEK_BASE_URL=http://10.214.74.113:8000/v1`，或通过 settings.json 配置 `custom_base_url`。

#### Bug #3：天气卡片不渲染 — ToolCard 折叠未自动展开

**根因**：`useState(weatherDone)` 只在首次 mount 取初始值，工具从 running→done 时 expanded 不会自动更新。

**修复**：加 `useEffect(() => { if (weatherDone) setExpanded(true); }, [weatherDone]);`

#### Bug #4：天气卡片不渲染 — MCP 协议信封未解包

**根因**：MCP 工具返回值有一层 JSON-RPC 信封 `{ content: [{ type: "text", text: "..." }] }`，前端直接 parse 拿到的是信封而非天气数据。

**修复**：前端 ToolOutput 加 MCP 信封解包逻辑，先提取 `content[].text` 再 parse 天气 JSON。

**教训**：MCP 工具和原生工具输出格式不同——原生直接返回字符串，MCP 有信封包裹。

### Phase 2：同花顺问财 MCP（进行中）

第二个真实工具，金融数据场景。基于开源 [lorek666/iwencai-mcp](https://github.com/lorek666/iwencai-mcp)。

**方案选型过程：**

**API Key 方案决策（2026-06-12 更新）：**

最初设计让用户自行到 SkillHub 获取 API Key（弹配置弹窗），但实际测试发现：
- SkillHub 页面的 Key 藏在 CLI 安装指令里，用户很难找到
- 小艺 Claw 等竞品通过手机号自动绑定，但需要商务合作+账号体系，我们不具备
- 问财 API 免费且限流宽松（**每 15 分钟 5000 次**，正常对话远够用）

**结论：内置 API Key，用户零配置一键安装。** 与天气工具体验一致。

| 项目 | 说明 |
|------|------|
| 请求上限 | 每 15 分钟 5000 次（全局共享） |
| 费用 | 免费，无调用费用 |
| 风险 | 用户量大时可能共享限流 |
| 兜底 | 如 Key 被限流/封禁，可申请新 Key 发版替换 |

### Phase 2b：企查查 MCP（待开发）

第三个真实工具，企业信息查询场景。**远程 MCP**（非本地 Python），pinvou3 首个远程工具。

**产品定位：** [企查查智能体数据平台](https://agent.qcc.com/) 提供 182 个企业数据工具，覆盖工商/风控/知产/经营/历史/董监高六大模块。

**接入方式确认（2026-06-12）：**

底座（DeepSeek-TUI）原生支持 Streamable HTTP MCP transport（CHANGELOG #1300），mcp.json 中写 `url` + `headers` 即可，**不需要本地 Python 桥接脚本**。证据：

- `mcp add http <name> <url>` CLI 命令

这比同花顺（本地 Python 调远程 REST API）更简单：无 server.py、无 Python 依赖、无跨平台 python/python3 问题。

##### Step 3：`add_to_mcp_json()` 扩展 — 远程工具分支

当前 `add_to_mcp_json()` 只写 `command`/`args`/`env`。需要在现有逻辑前加一个分支：

```rust
fn add_to_mcp_json(&self, manifest: &ToolManifest, user_config: &HashMap<String, String>) -> Result<(), String> {
    // ...existing mcp.json read + servers 获取逻辑不变...

    if !manifest.servers.is_empty() {
        // ── 远程工具：遍历 manifest.servers[]，写 url/headers ──
        for server in &manifest.servers {
            let mut headers = serde_json::Map::new();

            // 1. config_fields 中 target="bearer" 的字段（正式上线时用户填入）
            for field in &manifest.config_fields {
                if field.target == "bearer" {
                    if let Some(val) = user_config.get(&field.key) {
                        headers.insert(
                            "Authorization".to_string(),
                            serde_json::Value::String(format!("Bearer {}", val)),
                        );
                    }
                }
            }

            // 2. manifest.env 中以 _API_KEY 结尾的字段（内置 Key 阶段）
            //    当 config_fields 为空时，从 env 中取 Key 写入 Authorization
            if headers.is_empty() {
                for (k, v) in &manifest.env {
                    if k.ends_with("_API_KEY") && !v.is_empty() {
                        headers.insert(
                            "Authorization".to_string(),
                            serde_json::Value::String(format!("Bearer {}", v)),
                        );
                        break;
                    }
                }
            }

            let mut entry = serde_json::json!({ "url": server.url });
            if !headers.is_empty() {
                entry["headers"] = serde_json::Value::Object(headers);
            }
            servers.insert(server.name.clone(), entry);
        }
    } else {
        // ── 本地工具：现有逻辑（command/args/env）不变 ──
        // ...
    }

    // ...write mcp.json...
}
```

**Key 来源优先级**：`config_fields`（用户填入）> `manifest.env`（内置 Key）。
正式上线时只需把 Key 从 `env` 移到 `config_fields`，代码不用改。

##### Step 4：`remove_from_mcp_json()` 扩展 — 多 server 条目删除

当前 `remove_from_mcp_json()` 只删 `tool_id` 一条。远程工具有多个 server name：

```rust
fn remove_from_mcp_json(&self, tool_id: &str) -> Result<(), String> {
    // ...existing read mcp.json...

    // 先尝试加载 manifest 看是否有 servers 字段
    if let Some(manifest) = self.load_manifest(tool_id) {
        if !manifest.servers.is_empty() {
            // 远程工具：删除所有 server name
            for server in &manifest.servers {
                servers.remove(&server.name);
            }
        } else {
            // 本地工具：删除 tool_id
            servers.remove(tool_id);
        }
    } else {
        // manifest 不存在（被删了？），fallback 删 tool_id
        servers.remove(tool_id);
    }

    // ...write mcp.json...
}
```

#### 隐患与风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 182 个工具太多，LLM 路由混乱 | 小模型可能选错工具或 tool list token 爆炸 | 先全量接入观察；如不行用 mcp.json 的 `enabled_tools` 裁剪到核心 20-30 个 |
| 免费额度有限（每日频次限制） | 高频使用可能触发 `-32001` 错误 | 工具描述注明"免费试用"；错误时 LLM 会收到报错信息并告知用户 |
| 网络延迟 | 远程 HTTP 比本地 stdio 慢（~200-500ms） | 可接受，底座有 per-server `execute_timeout` 配置 |
| API Key 泄露 | Key 明文存在 mcp.json 中 | 与底座一致（MCP.md 已提醒 treat as secret） |
| 4 个 Server 全装但部分 endpoint 不稳定 | 某个 Server 超时影响用户体验 | 底座有 per-server connect_timeout/execute_timeout |
| 企查查 endpoint URL 变更 | manifest 中 URL 硬编码，需发版更新 | v2 远程仓库可解决；当前版本用户需更新 app |

## 十、MCP 工具接入踩坑记录

> 以下是 iwencai（同花顺问财）接入过程中踩过的坑，接入新 MCP 工具时务必对照检查。

### 10.1 前端 JS 变量声明顺序（`const` 无提升）

**症状**：白屏，控制台报 `ReferenceError: xxx is not defined`。

**原因**：`const` / `let` 没有变量提升（hoisting），在声明语句之前的代码不能引用它——即使是在函数体内，只要该函数在声明之前被 React 调用渲染就会崩。

**案例**：
- `tsToolsData` 在 line 1127 用 `const` 定义，但 `ChatView`（line 850）的渲染函数在 line 879 引用了它。React 调用 `ChatView` 时 `tsToolsData` 还在 temporal dead zone → 白屏。
- 解决：把 `tsToolsData` 移到所有引用它的组件**定义之前**。

**检查清单**：
- [ ] 新增的 `const` 数据（工具列表、配置等），确保在所有引用组件的 `const XxxView = ...` **之前**声明
- [ ] 不要在同一作用域声明两个同名 `const`（`SyntaxError`，整个 React 崩掉）

### 10.2 React hooks 规则

**症状**：白屏，控制台报 hooks 相关错误。

**原因**：`useState` / `useEffect` 等 hooks 必须在组件函数体的**最顶层**调用，不能放在条件语句 `if (...) return null;` 之后。

**案例**：
```jsx
// ❌ 错误 — useState 在条件 return 后面
const ToolWelcomeCard = ({ toolId }) => {
  const tool = data.find(...);
  if (!tool) return null;       // ← 提前 return
  const [hovered, setHovered] = useState(null); // ← hooks 在条件后，违规
};

// ✅ 正确 — hooks 在任何条件 return 之前
const ToolWelcomeCard = ({ toolId }) => {
  const [hovered, setHovered] = useState(null); // ← 先声明 hooks
  const tool = data.find(...);
  if (!tool) return null;       // ← 再条件 return
};
```

### 10.3 跨组件状态传递（props 遗漏）

**症状**：白屏，报 `ReferenceError: justInstalledTool is not defined`。

**原因**：`useState` 在父组件 `App` 中声明，但子组件 `ChatView` 直接引用了变量名，没有通过 props 传入。

**检查清单**：
- [ ] 新增的状态变量如果跨组件使用，必须在 JSX 调用处传 prop，并在子组件参数解构中接收
- [ ] 搜索新变量名，确认所有引用点都在定义所在的组件内，或通过 props 链路传递

### 10.4 bundle.rs 覆写 mcp.json（工具市场条目丢失）

**症状**：安装了 iwencai 后重启 app（或 bundle version 升级），iwencai 从 mcp.json 消失，LLM 连不上 MCP server。

**原因**：`bundle.rs` 的 `ensure_extracted()` 在 VERSION 变化时用 `DEFAULT_MCP_JSON`（只含 `pinvou` present_artifact）整体覆写 `~/.pinvou3/bundle/mcp.json`，不保留 marketplace 动态追加的条目。

**影响**：每次升级 `BUNDLE_VERSION` 或首次解包，marketplace 安装的所有工具注册信息丢失。

**修复**：新增 `ensure_builtin_mcp_servers()` 方法，在 VERSION check **之前**调用（每次启动都跑）。读取现有 mcp.json → upsert `pinvou` 条目 → 保留 marketplace 条目 → 写回。VERSION-gated 区域不再写 mcp.json。

**状态**：✅ 已修复

### 10.5 MCP server 生命周期（安装后必须新建会话）

**症状**：安装 iwencai 后在当前会话中问金融问题，LLM 说"工具连接不上"并回退到 web_search。

**原因**：DeepSeek-TUI 底座在**创建会话时**读取 mcp.json 并启动 MCP server 进程。安装工具只写了 mcp.json，不会热加载到已有的 engine 实例。必须新建会话才能让 engine 重新读取配置并启动新的 MCP server。

**前端已有处理**：安装成功后弹出 iOS Alert 提示"新工具需要在新会话中生效"，并提供"新建会话"按钮。

**潜在改进**：未来可考虑让 engine 支持运行时 hot-reload mcp.json（需底座改动，非短期目标）。

### 10.6 Windows 上 `python3` 命令不可用

**症状**：MCP server 启动失败，`python3` 命令找不到。

**原因**：Windows 上标准 Python 安装只注册 `python` 命令，`python3` 指向 Microsoft Store 的 stub（WindowsApps），实际上不可用。

**修复**：`ensure_builtin_mcp_servers()` 中 pinvou server 的 command 已改为 `"python"`。

**检查清单**：
- [x] manifest.json 的 `command` 字段在 Windows 上应写 `"python"` 而非 `"python3"`
- [x] `ensure_builtin_mcp_servers()`（bundle.rs）内置 pinvou server 已用 `"python"`

**状态**：✅ 已修复

### 10.7 Tauri 2.0 外部链接打开

**症状**：点击"免费获取"按钮无响应。

**原因**：Tauri 2.0 webview 中 `window.__TAURI__.shell.open()` 不存在，`window.open()` 被拦截。

**解决**：必须通过 Rust 后端 command 打开：
```js
// 前端

```
```rust
// 后端 commands.rs — 白名单 + 平台分支
#[cfg(target_os = "windows")]
std::process::Command::new("cmd").args(["/c", "start", "", &url]).spawn()?;
#[cfg(not(target_os = "windows"))]
std::process::Command::new("xdg-open").arg(&url).spawn()?;
```
- [ ] 新工具如有外部链接，需把域名加入 `EXTERNAL_URL_ALLOWLIST` 白名单

### 10.8 工具介绍卡片与 LLM 回复重复

**症状**：安装工具 → 新建会话 → 自动发 query → 弹出工具介绍卡片 + LLM 文本回复，信息重复。

**原因**：自动发送 `bridge.sendMessage("介绍下XXX工具")` 会真的触发 LLM 生成回复；同时前端检测到这个 pattern 又插入了本地工具介绍卡片。

**修复（方案 A）**：不发真实 query 给 LLM，改为设置 `welcomeToolId` 本地状态，在空态页面直接渲染 `ToolWelcomeCard`。用户点击 chip 时才发送实际 query。不浪费 token，响应即时。

**状态**：✅ 已修复

### 10.9 调试白屏的通用方法

单页 HTML 应用白屏时，浏览器控制台可能看不到（Tauri webview 默认不开 devtools）。

**注入错误捕获**：在 `<head>` 最前面加一段，把 JS 错误直接渲染到页面上：
```html
<script>
  window.onerror = function(msg, url, line, col, err) {
    document.body.innerHTML = '<pre style="color:red;padding:20px">'
      + msg + '\nLine: ' + line + '\n' + (err && err.stack || '') + '</pre>';
  };
</script>
```
调试完记得移除。

### 10.10 bundle.rs merge 必须在 VERSION check 之前

**症状**：`ensure_builtin_mcp_servers()` 放在 VERSION-gated 区域内，但 bundle version 没变时 early return，merge 代码永远不执行。导致 mcp.json 中缺少 `pinvou` server，present_artifact 工具不可用。

**原因**：`ensure_extracted()` 在 `current.trim() == BUNDLE_VERSION` 时直接 `return Ok(())`，VERSION-gated 区域内的所有逻辑都跳过。而 mcp.json 的 merge 需要**每次启动**都执行——marketplace 安装可能在任何时候发生，不受 bundle version 约束。

**修复**：把 `self.ensure_builtin_mcp_servers()` 调用移到 VERSION check **之前**，与 `write_mcp_servers()` 和 `cleanup_retired_skills()` 并列（这些都是"每次启动防御性执行"的逻辑）。

**规则**：bundle.rs 中需要**每次启动都执行**的操作（脚本重写、mcp.json merge、废弃清理），必须放在 VERSION check 之前。VERSION-gated 区域只放**仅在升级时执行**的操作（instructions.md 重写、deny_sensitive.sh 等）。

**状态**：✅ 已修复

### 10.11 MCP 工具注册但不在 tool catalog 中

**症状**：mcp.json 中有 iwencai server 配置，API 直接调用也正常，但 LLM 报 `Tool 'hithink_market_query' is not available in the current tool catalog`。

**原因**：底座的 tool catalog 在**会话创建时**从 mcp.json 构建。如果 mcp.json 在上次会话创建之后才被修改（如 marketplace 安装），当前会话的 tool catalog 不包含新工具。

**排查步骤**：
1. 检查 `~/.pinvou3/bundle/mcp.json` 是否包含目标 server 条目
2. 检查 server 的 `command`（python vs python3）和 `args`（server.py 路径）是否正确
3. 新建会话后再试——底座会重新读取 mcp.json 并启动 MCP server
4. 查看启动日志中 `tool_catalog` 行：`active_count` 和 `deferred_count` 是否包含预期的工具数

**状态**：✅ 已知行为，前端已有"新建会话"引导

### 10.12 Windows Python stdio 编码导致 MCP 连接失败

**症状**：MCP server 启动成功（stderr 输出 `starting on stdio`），但底座报 `Stdio transport read error: stream did not contain valid UTF-8`，所有 MCP 工具不可用。

**原因**：Windows 上 Python 的 `sys.stdout` / `sys.stdin` 默认使用系统编码（GBK/CP936），而 MCP 协议的 JSON-RPC over stdio 要求 UTF-8。当 JSON 响应包含中文（如 iwencai API 返回的中文字段名），GBK 编码的字节不是合法 UTF-8 → 底座解析失败。

**修复**：在 server.py 启动时强制 UTF-8 编码：
```python
import io, sys
if sys.platform == "win32":
    sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8")
    sys.stdin = io.TextIOWrapper(sys.stdin.buffer, encoding="utf-8")
```

**检查清单**：
- [x] 所有 MCP server.py（iwencai、present_artifact）已加 UTF-8 强制
- [ ] 新增的 MCP server **必须**包含此 Windows UTF-8 修复，否则中文内容一定崩

**状态**：✅ 已修复

### 10.13 MCP server 必须零第三方依赖（PEP 668）

**症状**：Linux deb 环境安装工具时，`pip install mcp httpx` 报 `error: externally-managed-environment`。

**原因**：Debian/Ubuntu 新版本（PEP 668）禁止在系统 Python 中直接 `pip install`，必须用 `venv` 或系统包管理器。

**规则**：所有 MCP server 必须只用 Python 标准库（stdlib），不依赖第三方包。参照 iwencai server 的模式：
- HTTP 请求：`urllib.request` + `urllib.parse`（注意 `urlencode` 在 `urllib.parse` 里，不在 `urllib.request`！）
- MCP 协议：手写 JSON-RPC 2.0 over stdio（`_send` / `_error` / `_result` + stdin readline 循环）
- Windows UTF-8：`io.TextIOWrapper` 强制编码

**案例**：天气 server 原来依赖 `mcp` + `httpx`，已重写为纯 stdlib。

**检查清单**：
- [ ] 新增 MCP server 的 `manifest.json` 中 `pip_dependencies` 必须为空数组 `[]`
- [ ] 不使用 `import httpx` / `import requests` / `from mcp import ...`，全用 `urllib`
- [ ] `urllib.parse.urlencode`（不是 `urllib.request.urlencode`！后者不存在会 AttributeError）

**状态**：✅ 天气/iwencai/present_artifact 均已零依赖

### 10.14 python 命令跨平台兼容

**症状**：Linux 上 MCP server 启动失败，`python: command not found`。

**原因**：Windows 只有 `python`，Linux 很多环境只有 `python3`。代码里写死任何一个都会在另一个平台挂。

**修复**：Rust 侧按平台选择命令：
```rust
let python_cmd = if cfg!(target_os = "windows") { "python" } else { "python3" };
```

**注意两处都要改**：
1. `bundle.rs` 的 `ensure_builtin_mcp_servers()` — 内置 pinvou server
2. `marketplace.rs` 的 `add_to_mcp_json()` — 工具市场安装的 server

`manifest.json` 的 `command` 字段写 `"python"` 即可，`marketplace.rs` 运行时会按平台覆写。

**状态**：✅ 已修复

### 10.15 PR 提交与 rebase 注意事项

**症状**：PR diff 包含大量不属于自己的改动（已删代码复活、无关文件夹），reviewer 拒审。

**原因**：本地分支基于旧 main，领先远程的 commit 包含别人后来已删除的代码。

**正确做法**：
1. **从最新 `origin/main` 建干净分支**：`git fetch origin && git checkout -b xxx origin/main`
2. **只带自己的文件**：`git checkout <旧分支> -- <文件列表>`，不要整体 cherry-pick 或 merge
3. **`commands.rs` / `lib.rs` 等公共注册文件不能整体替换** — 会丢失别人新增的命令。应该恢复 origin/main 版本后，只追加自己的代码到末尾
4. **`lib.rs` 的 `generate_handler![]` 要同步注册** — 新增 Tauri command 必须加到这里，否则编译报 `cannot find __cmd__xxx`
5. **`bridge/mod.rs` 要声明新模块** — 新增 `marketplace.rs` 文件必须加 `pub mod marketplace;`

## 十三、知识库工具接入方案（Obsidian + Notion）

> 目标：让用户把自己的**个人知识库**接进 Pinvou，作为大模型的检索工具。
> 覆盖两类用户：**本地派（Obsidian）** 和 **云端派（Notion）**。
> 版本：draft v0.1 · 2026-06-15

### 13.0 核心结论（先对齐认知）

接知识库给大模型用，本质就是**再造一个 MCP 工具**挂进市场，路子跟天气/企查查完全同构。但两家的**连接模型天生不同**，这是方案分叉的根因：

| | **Obsidian** | **Notion** |
|---|---|---|
| 产品形态 | 本地优先（local-first），笔记就是本机磁盘上的 `.md` 文件 | 云端 SaaS，笔记存在 Notion 服务器 |
| 有没有「账号登录接入」 | ❌ 官方**不开放** API，第三方拿账号也读不到云端笔记 | ✅ 有官方 OAuth + REST API + 官方 MCP |
| Pinvou 怎么连 | 直接读本机 **vault 文件夹**（用户已登录的 Obsidian 早就把笔记同步到本地了） | 走 **OAuth / Integration Token**，云端实时 |
| 用户体感 | 选一次 vault 路径，之后**无感** | 点按钮**登录授权**（或填 token） |
| 对应市场里的工具类型 | **本地 stdio**（同天气、问财） | **远程 HTTP**（同企查查） |

> ⚠️ 重要澄清：Obsidian 的「账号登录」只是登录它**自己的桌面 App / Sync 服务**，用来把笔记同步到你本机。它**没有对外开放 API**，所以 Pinvou 里**做不出「用 Obsidian 账号登录」的 OAuth 按钮**——不是不想做，是对方没接口。好在用户已登录的 Obsidian 已把笔记落到本地磁盘，Pinvou 直读即可，体验反而更简单。

### 13.1 Obsidian 接入方案（本地 stdio）

**载体类型**：本地工具，与天气 MCP 完全同构（`command` + `args` + 零依赖 `server.py`）。

**连接原理**：用户安装时填一次 vault 路径（即笔记文件夹，例如 `C:\Users\123\Documents\我的笔记`），server.py 直接扫描该目录下的 `.md` 文件做检索，**不依赖 Obsidian 进程运行、不装任何插件**。

**对外暴露的 MCP 工具（最小有用集，只读优先）**：

| 工具名 | 作用 | 参数 |
|---|---|---|
| `mcp_obsidian_search` | 全文检索 vault，返回命中片段 + 笔记路径 | `query`，可选 `limit` |
| `mcp_obsidian_read_note` | 读取指定笔记完整内容 | `path`（相对 vault 的路径） |
| `mcp_obsidian_list` | 列目录 / 按标签列笔记 | 可选 `folder`、`tag` |

> 二期可加：顺 `[[wikilink]]` 展开关联笔记、按 `#tag` 聚合、写入（新建/追加笔记）。**首版只读最安全。**

**manifest.json（草案）** —— `resources/mcp-servers/obsidian/manifest.json`：

```json
{
  "id": "obsidian",
```

**server.py 要点**：
- **MCP stdio 协议**：必须实现 JSON-RPC over stdio 的 `initialize` / `tools/list` / `tools/call` 握手——**直接拷 `weather/server.py` 或 `present_artifact_server.py` 的协议骨架**改业务逻辑，不要从零手写。
- **零第三方依赖**（PEP 668，参照 10.13）：只用 Python stdlib（`os`/`pathlib`/`re`/`json`），检索用纯 Python 遍历 `.md`（量大再考虑调系统 ripgrep，但不作硬依赖）。
- **Windows 编码**：stdio 读写显式 `utf-8`（参照 10.12），避免 GBK 乱码导致 MCP 连接失败。
- **路径安全**：`read_note` 的 `path` 必须 `resolve` 后校验在 vault 根目录内，拒绝 `..` 越界。
- **vault 路径健壮性**：读 `OBSIDIAN_VAULT_PATH` 后 strip 首尾引号/空格、容忍尾部斜杠；路径不存在时返回明确错误而非崩溃。
- 跳过 `.obsidian/` 配置目录和附件二进制文件，只索引 `.md`。

**⚠️ bundle.rs 是逐工具硬编码嵌入（核对 bundle.rs:172-178 / 355-363）**，加 Obsidian 必须手动改两处，否则解包后 `servers_dir` 里没有 obsidian 目录，安装会报「工具 'obsidian' 不存在」：

```rust
// 1) 顶部加两个编译期内嵌常量（仿 WEATHER_*）
pub const OBSIDIAN_SERVER_PY: &str =
    include_str!("../../../resources/mcp-servers/obsidian/server.py");
pub const OBSIDIAN_MANIFEST_JSON: &str =
    include_str!("../../../resources/mcp-servers/obsidian/manifest.json");

// 2) write_mcp_servers() 里加解包块（仿 weather_dir）
let obsidian_dir = dir.join("obsidian");
std::fs::create_dir_all(&obsidian_dir)?;
std::fs::write(obsidian_dir.join("server.py"), OBSIDIAN_SERVER_PY)?;
std::fs::write(obsidian_dir.join("manifest.json"), OBSIDIAN_MANIFEST_JSON)?;
// server.py 加可执行位（非 Windows），仿现有 weather 处理
```

> **核对结论（已读 bundle.rs:219-238 确认）**：`write_mcp_servers()` 在 `ensure_extracted()` 里于 VERSION 提前返回**之前**无条件调用（line 231，注释「每次启动防御性重写」），所以**新增 MCP server 资源不需要 bump `BUNDLE_VERSION`**——每次启动都会解包到 `~/.pinvou3/bundle/mcp-servers/obsidian/`。这点与「改 instructions/workflow 才需动 version」不同，别混淆。

**✅ marketplace.rs 不需要改**：`load_manifest` / `load_manifests` 按 `id` 动态读 `servers_dir/<id>/manifest.json`，本地工具通路（command/args/env）已通用，Obsidian 直接复用。

**✅ 路由无需额外接线**：`routing_rules` + `tool_table_entries` 在安装后由动态 instructions（第五章）自动拼进系统提示，不用写代码。

**安装体验**：按钮态走「配置」流程（同 6.4 API Key 弹窗），但收的是**文件夹路径**而非 token → 写入 mcp.json 的 `env.OBSIDIAN_VAULT_PATH` → 新建会话生效（参照 10.5）。Windows 路径里的 `\` 由 serde_json 自动转义，无需手动处理。

> 💡 体验优化（二期）：安装时尝试自动探测本机 Obsidian 的 vault 列表（读 `%APPDATA%\obsidian\obsidian.json` 里记录的库路径），做成下拉选择，免去用户手填路径。

### 13.2 Notion 接入方案（远程 HTTP）

**载体类型**：远程工具，与企查查同构（无本地 `server.py`，靠 `servers` 数组 + `url`/`headers`）。Notion 官方已提供 hosted MCP（`https://mcp.notion.com/mcp`），无需我们自建 server。

**这里有个架构现状要正视**：当前市场的远程工具机制（见 3.2 / 7.3）只支持**静态写入 url + bearer header**，**还没有 OAuth 回调基建**（重定向、本地回调、token 交换/刷新）。所以 Notion 分两阶段落地：

#### Phase 1（今天就能跑通）：Integration Token + bearer

复用企查查那套远程机制，**不需要新基建**：

1. 用户去 Notion 后台 `Settings → Connections → 开发者 → New integration` 建一个 internal integration，复制 token（`ntn_xxx`）。
2. 在 Notion 里把要给 AI 看的页面/数据库 `Share → 邀请这个 integration`。
3. 回到 Pinvou，安装 Notion 工具时把 token 填进 `config_fields`（`target: "bearer"`）。

**manifest.json（草案）** —— `resources/mcp-servers/notion/manifest.json`：

```json
{
  "id": "notion",
  "name": "Notion 知识库",
  "description": "连接你的 Notion 页面与数据库，让大模型检索云端笔记",
  "version": "1.0.0",
  "icon": "file-text",
  "category": "知识库",
  "mcp_tools": [],
  "command": "",
  "args": [],
  "env": {},
  "config_fields": [
    { "key": "NOTION_TOKEN", "label": "Notion Integration Token（ntn_ 开头）", "required": true, "target": "bearer" }
  ],
  "servers": [
    { "name": "notion", "url": "https://mcp.notion.com/mcp" }
  ],
  "routing_rules": [
    "我的 Notion/云端笔记/工作区/页面/数据库 → `mcp_notion_*` 检索 Notion，不要用 `web_search`"
  ],
  "tool_table_entries": [
    "| Notion 知识库 | `mcp_notion_*` (检索/读取 Notion 页面与数据库) |"
  ],
  "pip_dependencies": []
}
```

> 体验：偏「半自动」，需用户手动建 integration + 共享页面。适合内测先跑通，验证检索质量。

#### Phase 2（真正的「登录即接入」）：OAuth

这才是用户想象的那种「点一下用 Notion 登录 → 授权 → 自动接入」体验。**需要新增 OAuth 基建**：

- **新增**：OAuth 授权流程 —— Pinvou 把用户跳到 Notion 授权页 → 用户在 Notion 自己页面登录并同意 → Notion 回调把 `access_token` 发回。
- **Tauri 回调**：用 deep-link（自定义协议 `pinvou://oauth/callback`）或本机临时端口接 redirect（注意 10.7 的外链打开方式）。
- **token 管理**：安全存储 access/refresh token，过期自动刷新。
- **marketplace.rs 改造**：远程工具支持「动态 token」而非静态 bearer，安装按钮态新增「连接/授权」分支。

> 结论：**Phase 1 先上**（复用现有远程机制，零基建，验证价值）；**Phase 2 排期做 OAuth**（一次性投入，之后语雀/飞书/Google 等云端知识库都能复用这套授权框架）。

### 13.6 知识库选型对比：Obsidian / Notion / ima（调研结论）

> 调研日期：2026-06-15。结论：**本地派用 Obsidian，云端派用 Notion；ima 暂缓**。

| | **Obsidian** | **Notion** | **ima 知识库（腾讯）** |
|---|---|---|---|
| 数据位置 | ✅ 本机 vault | ☁️ 云端 | ☁️ 腾讯云端 |
| 官方 API / MCP | ❌ 无（local-first） | ✅ 官方 OAuth + API + 官方 MCP | ⚠️ **无官方**，仅"将开放"的口头规划 |
| 可用接入 | 本地读文件（已做） | 官方 token / OAuth | 仅**第三方逆向** MCP（`highkay/tencent-ima-copilot-mcp`） |
| 认证体验 | 选一次路径，无感 | 登录授权 / 填 token | **手抠浏览器 cookie**（`x-ima-cookie`+`x-ima-bkn`），无 OAuth，过期手动换 |
| 能力 | 搜索 / 读全文 / 列目录 | 检索页面与数据库 | 仅 `ask` / `ask_with_kb`（问答 RAG，**不给原文检索**） |
| 与 Pinvou 定位 | ✅ 完美契合"本地不出域" | 🟡 云端但正规 | ❌ **冲突**：云端 KB，数据要出域，对政企/金融/涉密是减分 |
| 风险 | 低 | 低 | 逆向无 SLA、接口一改即崩、明文凭证、**可能违反 ToS / 账号风险** |

**ima 决策**：
- **暂不接入**，列为"待官方开放 API"观察项；官方正式 API（可能带 OAuth）放出后再评估。
- ima 是**云端**知识库，与 Pinvou"本地推理、数据不出内网"的护城河（见 `对标-workbuddy差异分析.md`）正面冲突，不进主推。
- 现有占位卡 `ima 知识库 Plugin`（id 4）原文案"官方底层集成"**不属实**，已改为如实描述（云端·接入中·非官方）。
- 若确需演示，最多做成"尝鲜"卡片，明确标注"云端 / 需手动授权 / 第三方逆向"。
