P PINVOU OS · AGENT RUNTIME
ARCHITECTURE REVIEW · 2026.08.19

One identity · Many concurrent workers

一个 Pinvou，
十二个系统角色

用户永远只面对 Front Agent。其余 Agent 不争夺用户关系，而是通过可审计的调用、事实、约束与控制指令，支撑同一个 Pinvou 做出最终决定。

核心拓扑：中心化权责，去中心化工作

Front 持有业务决策与最终回复；Orchestrator 只编排复杂任务；Runtime Kernel 持有事件、权限与硬安全。普通 Agent 不互相私聊，优先读写统一事实账本。

01 · OPERATING MODEL

先把权力边界钉死

PinvouOS 没有用户 Session，但内部仍需要 Mission、Run、Event 和因果链。消灭的是用户可见的会话容器，不是运行时隔离与审计。

01

Front 是唯一一线单元

只由 Front 接受用户意图、决定 Direct / Clarify / Orchestrate / Interrupt，并给最终答复。

02

Orchestrator 不是第二个 Pinvou

只接收 Front 授权的目标，拆成最小工作图，收集证据，再把回执交还 Front。

03

事实先进入 Runtime

观察型 Agent 发布 Event / Claim；消费方读取投影。减少 Agent 间私有对话和状态分叉。

04

硬安全可以阻止，但不能代答

Policy、Governor、Attention 可拒绝、限流、暂停或停止工作；最终如何向用户解释仍属于 Front。

谁调用谁，谁只发布事实

03 · SYNC / ASYNC

三种运行时序

同步只用于低延迟读、授权门和一次原子能力；耗时工作、后台观察和结果回传都走异步路径，避免 Front 被整个系统拖死。

简单交互 · 快路径

解释、改写、翻译或边界清晰的短操作。Orchestrator 不启动。

01
Front 接受输入语音转写只在入口发生一次。同步
02
读取必要投影当前读取 Capability、网络与模型状态；Front Context Compiler 接入后才会读取 Memory 的稳定、只读投影。同步
03
最多三轮工具同一轮的并行工具算一轮；达到完成标准立即停止。同步工具批次
04
Front 最终回复三轮仍未完成则转入复杂任务路径，绝不静默结束。

复杂任务 · 编排路径

多产物、多能力、长任务、并行工作、调查→实施→验证或明显副作用。

01
Front 授权一个目标只传目标、完成标准、约束、已知事实和证据，不复制整段对话。异步 handoff
02
Orchestrator 建最小工作图先做 NO_OP / Clarify 判断，再查询 Capability、Policy、Resource。同步规划读取
03
Mission Agents 并行执行独立项并行、有依赖项串行；并发上限 4、派工深度上限 2。异步并行
04
证据回执返回 FrontFront 核对状态、证据、变更、风险和阻塞，再决定最终表达。最终回执

状态变化 · 控制路径

用户取消、设备过热、权限拒绝或并发超载时，不等待 LLM 自觉停手。

01
观察或用户指令进入 Runtime事实必须带时间、来源、置信度和证据。异步事件
02
确定性规则作出约束Policy 给出拒绝结论并由 Kernel 强制；Governor 判断 Warm / Hot / Critical；Attention 重新分配预算。同步规则
03
Adapter 执行 DirectivePause / Stop / Resume 必须得到 Applied / Rejected Ack，并持续 Reconcile。硬控制
04
Front 统一告知用户安全内核能阻止动作，但不能假装成用户业务决策者。
04 · INTERRUPT AUTHORITY

谁能打断谁

“能影响”与“能打断”必须分开。绝大多数 Agent 只能提供事实；真正的中断权集中在用户/Front、任务父级和 Runtime 硬治理。下表定义目标 Authority Contract；当前用户 busy 时不能 steering，Runtime Mission 与统一 Policy Gate 也未闭环，实施差异以 06 · Current Truth 为准。

发起者作用对象权限边界与执行方式
用户 → Front当前 Orchestrator 与相关 Mission Agents目标：可取消 / 改目标目标由 Front 将 Interrupt 转为运行时取消；当前 busy UI 不能自然 steering，用户链尚未接到完整 Runtime 控制闭环。
Front Agent自己授权的 Orchestrator / Mission可中断基于用户意图或业务判断撤销授权；Front 不能解除 Policy 的硬拒绝，也不能强迫 Kernel 越过安全阈值。
Orchestrator自己派出的子 Mission Agents可取消 / 重排只管理工作图，不得中断 Front、系统观察 Agent或其他不属于该 Mission 的工作。
Resource GovernorMission AgentsPause / Stop / ResumeWarm 延后重任务；Hot 暂停低优先级可中断任务；Critical 硬停止非必要任务。通过 Adapter 执行并 Ack。
Attention Agent并发 Run调度级抢占已可通过原子工具输出 Run / Throttle / Pause / Stop 计划；Scheduler 执行仍待接入，Atomic 只在安全边界抢占。
Policy Agent + Kernel拟执行动作执行前否决Policy Agent 评估 Allow / Deny / Require Confirmation；Kernel/AuthorityStore 才是强制执行者。确认绑定完整动作内容且可过期。
Surface / Device / Connectivity / Inference / Memory / Capability / ASR Context其他 Agent不能直接中断只提交事实、投影或解释。其他组件消费新事实后，才可能由 Front、Policy、Governor 或 Scheduler 采取行动。
05 · RESPONSIBILITIES

十二个系统 Agent 的原子职责

每个 Agent 只拥有一种主要变化原因：交互、编排、感知、事实、能力、记忆、授权或调度。职责重叠时优先删掉重复，而不是再加协调层。

06 · CURRENT TRUTH

当前真实完成度

这张图同时画目标关系与本地工作树当前接线状态，不代表 MegaBook 已部署版本。评审时最重要的是别把“有契约”误当成“已闭环”。

现在已经是真的

  • Front → pinvou-orchestrator 的 manager-as-tool happy-path 已通过 Engine 回归；Front 恢复并独占最终回复。唯一 profile、同批单实例与结构化回执仍待内核化。
  • Resource、Connectivity、Inference 与 ASR Context 都有真实后台循环，并持续写入统一 Runtime 投影。
  • Capability 已是可调用的进程内确定性 Agent；Memory Runtime 核心已接同一账本的决策、检查点与精确重放。
  • Memory 写入已受单写锁与 durable-head CAS 保护；结构化 Claim 做精确语义绑定，热投影使用可重建结构索引和有界 Top-K。
  • 旧 Memory 全量 snapshot 已停写；启动时只做一次可验迁移，不继续双写两套真相。
  • Attention 已接成只读原子规划工具；Runtime 状态、能力报告、编排工作图和 ASR Context 也都有同源进程内工具，不维护 MCP 影子状态。
  • Resource Governor 已能对注册了 Control Adapter 的 Mission Agent 签发 Pause / Stop / Resume，并记录 Ack。
  • Front 的 3 轮工具预算已由 Engine 强制执行，不只靠提示词自觉。

还只是契约或半闭环

  • Surface 还没有真实 AT-SPI / Surface Provider；Device 还没有持续设备 Provider，且需解决“内核枚举 ≠ 物理可用”。
  • Policy 的确定性算法已完成，但 AuthorityStore 与所有副作用工具的统一闸门尚未接通。
  • Attention 已能算优先级与预算，但 Scheduler 尚未消费其 Run / Throttle / Pause / Stop 计划。
  • Memory 尚未接 Front / Orchestrator 异步 worker、消费游标和候选提取；完整 UserMessage / VerifiedTaskOutcome 也未成为受信证据。
  • 失败经历的类型和门槛规则已在 Memory 内核中，但自动采集要等 VerifiedTaskOutcome；周期 checkpoint / compaction、冷归档、SQLite 和 Obsidian 也未接。
  • Front 尚未消费 Memory Context Projection；token budget、稳定上下文编译与 context_plan_hash 仍属于后续 Context Compiler。
  • Capability 目前主要读取 Manifest、Agent 状态和资源压力；Device / Connectivity / Inference 等事实还需进入统一前置条件解析。
  • Orchestrator 的 Mission Work Graph 与所有原子 Agent 的正式 dispatch / receipt 协议仍需完成端到端接线。

建议本轮评审只拍板四件事

  1. 是否坚持“Agent 不直接互相聊天，默认经 Runtime Event / Claim 协作”，只为 Front→Orchestrator→Mission 保留显式调用链。
  2. 是否确认 Front 的最终业务决策权与 Kernel 的硬安全否决权并存：前者对用户负责，后者只阻止危险执行。
  3. 是否确认 Orchestrator 不在每次输入时投机并跑，而是在 Front 判定复杂或三轮未完成后才启动。
  4. 是否确认 Surface 在本图中只负责“看见什么”；“Front 如何控制 UI 呈现”以 Interaction / Presentation 架构文档为唯一权威。
