交互 Agent
到底能做什么？

这份文档把 Front Agent 的真实能力、软约定和目标设计 分开说明。 它不是一个聊天头像，而是 PinvouOS 的用户关系所有者、交互路由器和最终表达者； 但它不拥有系统事实、用户授权、硬安全规则或最终像素。

01 · Position

先把角色钉死：它是门面，也是边界

“所有 Agent 都在 Front 后面”只适用于人机交互边界；系统事实与安全控制仍可直接经 Runtime Ledger 和 Kernel 运转。

Canonical statement
Front 是 PinvouOS 唯一面向用户的 Agent，也是唯一能提出普通用户态 front/* 呈现意图的 Agent；它不拥有 Runtime 事实、系统审批、用户授权或最终像素。

当前本体

部分接通

Runtime 投影

外层已经记录 InteractionRun、工具摘要、终态和精确 resume，但这是 best-effort 观测，不是聊天执行的强事务。

目标态

完整交互平面

Runtime 以 InteractionRun 持有生命周期权威并经 AG-UI 暴露；Front 参与交互、通过 A2UI 编排 front/*，由 Policy、Memory 和 Host 提供硬支撑。

02 · Routing

每次输入先走四选一

顺序不是为了“多 Agent 化”，而是让简单事保持快、复杂事有结构、危险和歧义不会被模型硬猜。

01

Interrupt · 打断

用户明确要求停止、取消或改变正在执行的工作时，优先中断，再给简短确认。

路由仅 Prompt
02

Direct · 直接完成

闲聊、解释、改写、翻译，或边界清楚、低风险且能在三轮工具内验证完成的短任务。

预算硬实现
03

Clarify · 只问关键问题

仅当缺失信息会实质改变目标、安全边界或结果时澄清；不拿澄清代替可安全推进的工作。

策略仅 Prompt
04

Orchestrate · 后台编排

多产物、多依赖、可并行、耗时、需要调查→实施→验证，或跨资源/设备/策略协同时委派。

happy-path 接通
!
必须区分“规则写在 Prompt 里”与“内核真的拦得住”

四路由选择、只问一个问题、只启动一个 pinvou-orchestrator 目前主要靠 Prompt；真正硬化的是三轮 Direct 工具预算及其执行期复检。

三轮 Direct 是怎样“硬”起来的

一轮 = 一次 assistant batch 里整批工具调用；同批并行多个工具仍只算一轮。

第 1 轮普通工具开放；尽量并行取证。
第 2 轮基于结果补充执行或验证。
第 3 轮最后一次普通工具批次。
→
只剩 handoff模型目录只暴露允许的 agent handoff；执行入口再次复检。
→
本轮工具关闭agent batch 出现后，无论成功失败，后续工具都拒绝。
05 · Orchestration

复杂任务现在怎么走，目标又怎么走

当前是 manager-as-tool：Front 调通用 agent 工具启动后台子 Agent；目标才是进入 Runtime Mission / Run 与权威 Work Graph。

当前真实路径

部分接通
1

Front 识别复杂任务

路由判断来自系统 Prompt，不是确定性分类器。

2

调用通用 agent tool

happy-path 使用 profile="pinvou-orchestrator"，但内核未 pin profile，也未限制同批只能一个 agent 调用。

3

CodeWhale 后台子 Agent 执行

这是兼容层的 subagent，不是 Runtime Mission Agent，Governor 不能按 Mission pause / stop。

4

Front 回收结果并最终回答

子 Agent 不直接对用户说话；回执格式和证据完整性目前主要靠 Prompt。

目标权威路径

目标态
1

打开 Mission / Runtime Run

目标、完成标准、约束和证据进入 Runtime Ledger。

2

冻结权威 Work Graph

Orchestrator 只规划与修订图；Kernel 拥有状态迁移和派发权。

3

分层回执与验证

Mission Agent Result → Orchestrator Receipt → VerifiedTaskOutcome，执行自报不等于已完成。

4

Front 解释并呈现

Front 接受、修改或拒绝建议，决定普通用户态表达；安全否决和用户确认仍不归 Front。

×

pinvou_orchestrator_plan 只生成确定性临时计划，不创建 Mission / Run，也不派发任务。当前复杂执行仍属于 CodeWhale 子 Agent 路径。

06 · Interaction Runtime

AG-UI 语义已经有骨架，但还没有标准线协议

InteractionRun 让一次用户交互有独立 ID、状态、终态和恢复关系；当前回答正文仍走兼容的 chat 流。

硬状态机

一个 terminal

成功打开的 InteractionRun 只能以一个 terminal outcome 结束；状态迁移和 resume 绑定有硬校验。

best-effort trace

只存摘要

记录工具 start/finish、消息 digest 与终态，不保存参数和完整输出；入账失败只告警，交互继续。

用户链未闭环

busy 时不可 steering

request_user_input 可产生精确 interrupt/resume，但 VoiceShell 忙时锁定输入，用户尚不能自然取消或改目标。

!
当前 modality 还不是完整真实输入通道

生产链普通输入目前统一标为 Voice，request_user_input 恢复输入标为 Touch；Text / System 的真实 plumbing 尚未接通，不能把投影里的 modality 当成完整多模态事实。

08 · Display & Interaction

二维码、对话框与富 HTML：现在到底能不能

答案不是简单的“有”或“没有”：宿主旧界面已经有不少能力，但 Front 与当前 A2UI 调不到。正确扩展方式是原生 A2UI、系统覆盖层与沙箱 AppSurface 三层并存。

当前结论

Front 不能正式弹认证二维码，也不能调用自定义 HTML 对话框。

旧 ToolStore 能生成二维码，旧 Artifact UI 能预览或运行 HTML，完整 App 也有许多 React Modal；但 PinvouOS 首页提前返回 VoiceShell，这些入口不在当前树里。Front 又没有 begin_auth、present_surface 或 open_dialog 工具，所以能力存在于宿主，却没有成为交互 Agent 的能力。

Challenge 是 tagged union：device_code 使用可信 verification_uri_complete 生成 QR，并且必须同时显示文本 URI 与 userCode；authorize_url / scan_login 显示 Adapter 验证的登录 QR，userCode 可以没有。device_code、token、PKCE state 和真实 URL 均不进模型或 A2UI 长期数据；按钮只携带 challengeId。

自己写的 HTML 如何呈现

两条安全路径

静态交付物：用 ArtifactPreview(artifactId) 在画布内预览；脚本关闭。
复杂交互：用 AppSurface(appViewRef) 挂载预注册 ui:// 或可信 artifact descriptor。

交互 iframe 使用 opaque origin、严格 CSP、默认断网、无 Tauri / 文件 / cookie / top-nav 权限；只允许版本化、限速、验 schema 的 postMessage。认证、OTP、支付和系统确认永不在 Widget 内完成。

!
P3 Presentation Host · 阻断级安全门禁

真实 Chromium 已证明当前回答 Markdown 会保留固定定位样式、原生 dialog、表单输入和远程图片，因此虽然没有正式 dialog API，模型仍可能“画出一个假的登录框”。必须先把 Markdown 改成严格标签/属性白名单，禁用 style、form、input、button、dialog 与任意远程资源；所有可交互控件只走 Host A2UI，并用固定恶意 payload 做回归。普通来源链接仍可显示，但回答 HTML 不得直接导航：HTTP(S) 点击统一改写成 Host open_external(evidenceRef)，执行 URL 标准化、Punycode / 端口与初始目标域名展示，并按需确认。旧连接器 QR 还必须把字符串包含式域名判断升级为 HTTPS + 精确 Host / 端口 / Provider Adapter 校验，并为 OAuth 固定 callback / redirect_uri allowlist，不能声称能拦截手机浏览器里的远端跳转链。

09 · Relationships

它与其他 Agent、Runtime 和 UI 怎么分工

Front 是用户态总入口，不是系统总权威。把“最终表达”“事实真相”“安全强制”“像素渲染”拆开，架构才可控。

Front 与 Orchestrator、Runtime、Policy、Memory、System Agents 及 Host Renderer 的分工
协作者给 Front 什么Front 能决定什么Front 不能决定什么当前连接
Orchestrator计划、执行结果、证据、风险、阻塞、澄清问题接受、修改、拒绝建议；组织最终答复不能把用户关系移交出去通用 agent tool
Runtime Ledger身份、Mission、Run、Interaction、Agent、资源等事实读取并解释事实不能把投影当第二真相源trace + 只读投影
Policy / KernelAllow / Deny / RequireConfirmation 与强制结果提出 Action Intent、解释结果不能替用户确认，不能覆盖硬拒绝统一 gate 未接
Memory Agent经证据筛选的稳定上下文在回答与计划中使用上下文不能把任务进度写进长期记忆Front consumer 未接
System Agents资源、连接、推理、设备、界面感知等事实和风险面向用户解释与建议不能阻断它们经 Ledger / Kernel 的系统路径多为投影或算法
Host Renderer组件能力、动作回执、本地交互事件声明普通用户态呈现意图不能控制最终像素、焦点和系统确认层只读投影已渲染
10 · Boundaries

哪些是真硬边界，哪些只是模型自觉

设计评审时最重要的问题不是“Prompt 写了什么”，而是“模型不听话时，哪一层会拒绝”。

内核 / Engine 硬约束

不可绕过
✓
同一隐藏执行会话只有一个 root turn并发根请求会得到 session_turn_in_progress。
✓
三轮工具 batch 后只允许 handoff工具目录会收窄，真实执行入口还会二次复检。
✓
handoff 后本轮工具全部关闭即使 profile 错或调用失败，也不会重新开放普通工具。
✓
子 Agent 深度、scope、写权限受约束不是只靠 Orchestrator 自己承诺。
✓
InteractionRun 状态迁移与精确 resume前提是该 Run 已成功打开；一个 Run 只能有一个终态。

当前仅 Prompt 约定

模型可违背
!
必须选择四种路由之一确定性 ingress 尚未进入生产链。
!
只调用一次 pinvou-orchestratorKernel 没有 profile pin，同批可提出多个 agent 调用。
!
委派后不重复执行目前没有跨 Front / Orchestrator 的去重事务。
!
Orchestrator 五段式回执没有 parser / schema 强校验证据和回执结构。
!
Front 不绕过新 Policy AgentPolicy gate 尚未成为工具执行的统一入口。
!
一个容易踩的边界

任何 agent action——包括 status、wait、cancel——都可能消耗唯一 handoff；因此不能只在 Prompt 里要求 profile，下一步必须把 handoff 变成专用、可验证的内核动作。

11 · Failure Semantics

失败条件与系统收口

稳定错误码与语义条件共同决定 Front 能否诚实告诉用户“哪里失败、是否执行过、还能不能继续”。

session_turn_in_progress同一兼容执行会话已有 root turn；新根请求不并发进入。
submission_failed请求未成功提交到 Engine；不能假装已经执行。
engine_turn_failed本轮执行失败；Front 应给可行动说明或安全降级。
engine_stream_stopped事件流异常结束；不能把缺失 terminal 当成功。
runtime_restarted重启时发现未完成 InteractionRun，会以明确失败原因闭合。
Trace 写入失败Runtime trace 入账失败只告警，用户交互继续；因此 Ledger 目前不是完整对话重放源。
Handoff 调用失败错误 profile 或失败的 agent 调用可能失败，但该用户轮次工具面仍保持关闭。
Resume 绑定不匹配恢复用户输入必须同时匹配父 Run 和 interrupt ID，不能重复恢复。
12 · Front Enablement Gates

Front 要成为完整交互 Agent，还依赖什么

这不是第二套全局迁移路线，只列 Front 的解锁依赖；全局实施顺序以“AG-UI × A2UI 交互画布架构”的迁移路线为唯一权威。

G1

专用 Orchestrate 准入

把唯一 profile、单 Orchestrator、handoff action 类型与 receipt schema 做成 Engine 硬约束。

门禁：错误 profile / 多 agent / status action 均不可消费或绕过正确 handoff
G2

生产 ingress 接线

让 Voice / Text / Touch / System 全部经过规范化 FrontIntentEnvelope，并形成可审计路由。

门禁：同输入确定性分类；Interrupt 优先级与模式一致
G3

Runtime Mission / Run 闭环

冻结 correlation、权威 Work Graph、派发、回执、暂停/恢复/取消和 VerifiedTaskOutcome。

门禁：复杂任务不再只存在于 CodeWhale subagent 内存
G4

Policy Gate、Auth Broker 与 system/*

所有副作用 Action Intent 统一经过 Capability、Policy、AuthorityStore 与 Kernel；Broker 生成受信 challenge state，只有 Kernel / Host Projector 写不可隐藏的系统层。

门禁：Front 无法替用户确认、伪造认证成功或覆盖 Deny
G5

Memory Context Compiler

让 Front 消费有证据、限预算、按范围投影的 Memory v2，而不是依赖隐藏 transcript。

门禁：无原始秘密、无任务进度污染、可解释来源
G6

front/* Presentation Planner 与 App Host

增加 present_surface、白名单 catalog 与 opaque appViewRef；Front 只提交语义结构、数据绑定和 Action Intent。

门禁：未知组件、跨 namespace、任意代码、路径、URL 与未注册 App 全部 fail closed
G7

AG-UI wire 与可恢复交互

输出标准事件、共享状态、steering、cancel / resume，并支持断连后的 Surface 与 Run 重放。

门禁：exactly-one terminal、exact resume、跨断连 sequence / revision 冲突测试
13 · Examples

放到真实请求里，就很容易理解

同一个 Front 身份，根据任务复杂度和风险选择不同内部路径；用户不需要切 Agent，也不需要切“会话人格”。

用户

“解释一下这段架构文档。”

Direct

无需启动 Orchestrator；Front 直接读取、解释并给结论。若用工具，仍受三轮预算。

用户

“MegaBook 现在热不热？”

Direct + 只读状态

Front 可读取 Runtime / Resource 投影后回答；不会凭一个 Running 徽标夸大设备能力。

用户

“把这个模块重构、部署，再做白盒和黑盒验证。”

Orchestrate

按 Prompt 契约应进入、happy-path 会进入 CodeWhale 子 Agent；目标态应建立 Runtime Mission、Work Graph、回执和验证终态。

用户

“先停，部署范围改成只动前端。”

Interrupt 链未闭环

Prompt 会要求先打断，但当前忙时 UI 不能自然 steering；这是 AG-UI 接线必须补齐的关键体验。

用户

“把整个屏幕整理成这项工作的操作台。”

front/* Canvas

目标不是让 Front 输出任意 HTML，而是声明 Mission、产物、风险、等待决定等语义块；Host 用统一设计系统渲染，并由 Policy / Kernel 保护 Action。

14 · Decision

最终判断

这三个结论决定下一阶段怎么做，能避免“画布很丑”“权限失控”和“看起来已完成、实际上没接通”。

它确实应该负责用户看到什么

但负责的是语义编排、最终表达和 Action Intent，不是任意像素、系统确认和执行授权。

现在还不能称为完整交互 Agent

它是一个能力很强的根 Agent，加上三轮硬边界和部分 Runtime 观测；关键闭环仍待接通。

显示面的第一纵切做认证卡

先封住 Markdown 伪造与 QR 域名漏洞，再用现有连接器完成 system/auth/*。它可与 Mission/回执闭环并行开发，但发布前必须通过 Presentation Host 安全门和 Auth/Policy 子门禁。
