本地文件管理 + 本地知识库 · 完整设计

在 pinvou3(Tauri + 本地 GB10/Qwen3.6)之上，把"全盘文件查找"与"AI 可引用的本地知识库"做成一套分层系统：L0 全量元数据、L1 选定知识集内容化、L2 生成式 RAG 问答。本文档覆盖全链路（非 MVP），含架构、技术选型、存储、接口、交互与部署。

版本 v1.0 日期 2026-06-22 状态 设计定稿 · 待动手 作者 pinvou3 团队 分支 feat/files-manager

01定位与目标

先把"找文件"和"喂给 AI"这两件相反的事讲清楚——它们是两个产品、两种心智、两套范围策略。

两个产品，一套入口

能力定位范围类比核心价值
本地文件管理
L0 已实现		全盘文件查找 + 分类浏览 + 去重清理全量（家目录/选定根）Everything / Spotlight不知道文件在哪也能秒找到；去重要全量才有意义
本地知识库
L1/L2 新建		精选资料内容化 → 语义检索 → AI 问答选定（知识集）AnythingLLM / NotebookLM让 35B 基于"我挑过的资料"回答并溯源
核心原则：L1 从 L0 长出来 用户在 L0 全盘浏览/搜到文件 →「加入知识库」→ L1 才对这一小撮做内容解析与向量化。L0 是货架（轻、全量、零模型），L1 是挑进购物车的东西（重、选定、按需）。绝不对全盘百万文件做内容化/向量化——那是成本、噪音、隐私的三重灾难。

设计原则

  • 本地优先：全部能力在 GB10 本地完成，零云依赖；以当前 Qwen3.6-35B 能力为基线设计。
  • 复用底座，不重造轮子：解析复用 file_ingest、存储复用 rusqlite、生成复用 engine/vLLM、分发沿用 .deb 单体。
  • 分层解耦：L0/L1/L2 各自独立演进；embedding 与生成是两个独立模型，各跑各的，互不拖累。
  • 可溯源高于聪明：本地 35B 答案质量有基线上限，每个回答必须带可点击的原文引用——这是本地知识库相对云端的信任优势。
  • 后台不打扰前台：扫描/解析/embedding 全部节流让步，绝不卡设备（L0 性能教训已落地）。

03数据流：四条链路

全链路拆成四条独立数据流。前两条是写入（建索引），后两条是读取（查询）。

mtime+size 未变则跳过

2000/批 + 节流 sleep

files_fts(name) trigram

04技术选型

每个环节给选型 + 理由 + 备选 + 何时切换。原则：嵌入式、进程内、Rust 原生，不破坏单体离线分发。

环节选型理由备选 / 何时换状态
运行时Tauri 2 + Rustpinvou3 既有底座；单体、跨平台、Rust 后端—既有
元数据/全文存储SQLite (rusqlite) + FTS5 trigram一个库装元数据+全文+向量；trigram 中文子串友好；WAL 并发tantivy（更强相关性，规模大时）L0已用
文档解析file_ingest（自建，复用）已验证通路，覆盖 pdf/docx/md/xlsx/pptx；依赖降 recommends—（别另造）既有
切块 Chunker自研，按句/字符 ~512token + 15% 重叠切分质量决定召回上限；保留标题/结构边界按语义切（后续优化）新建
Embedding 模型bge-m3（0.56B，1024 维）MTEB 中文/多语第一梯队；ONNX 可得；自带稀疏可选Qwen3-Embedding-0.6B；要更省 bge-small新建
Embedding 运行时fastembed-rs（进程内 ONNX，CPU EP 起步）零外部服务、契合单体；不抢 vLLM 显存、不连累其稳定性vLLM embed 实例 / TEI（要 GPU 速度时）新建
向量检索起步 BLOB + Rust 暴力余弦 → sqlite-vec选定知识集几千~几万 chunk，暴力 KNN <10ms，零扩展依赖sqlite-vec / LanceDB（>10万 chunk 上 ANN）新建
生成模型Qwen3.6-35B-A3B-FP8（vLLM）pinvou3 既有后端；RAG 答案生成 + 重排—既有
重排RRF 融合 + 可选 35B listwiseRRF 零成本融合双路；35B 重排在召回不准时兜底专用 reranker（bge-reranker）新建
LLM 联动MCP kb_query零 fork 加工具通路；模型自主调知识库内部工具直注入新建
实时增量notify watcher（复用 L0）知识集内文件改动 → 重解析；L0 已有 watcher周期重扫兜底复用
选型上的两个真坑 ① ARM/Blackwell 上的 ONNX-GPU：GB10 是 aarch64 + 新架构，onnxruntime CUDA EP 不一定现成 → 起步用 CPU EP（Grace 20 核跑 0.5B 后台建索引可接受），嫌慢再切 vLLM-embed 走已调通的 GPU 栈。② 维度/模型绑定：换 embedding 模型必须重建全部向量，用 schema version 卡死。

05存储设计 · Schema

单库（index.db），L0 表已存在；L1 新增 collections / documents / chunks / vec_chunks。用 PRAGMA user_version 管迁移。

L0（已实现，v2）

-- 文件元数据（不存内容）
CREATE TABLE files(
  id INTEGER PRIMARY KEY, path TEXT UNIQUE, name TEXT, ext TEXT,
  size INTEGER, mtime INTEGER, is_dir INTEGER, hash TEXT, status TEXT, indexed_at INTEGER);
-- 只索引文件名（砍 path 全路径，省 2/3 体积）
CREATE VIRTUAL TABLE files_fts USING fts5(name, content='files', tokenize='trigram');

L1（新增，v3）

-- 知识集
CREATE TABLE collections(
  id INTEGER PRIMARY KEY, name TEXT, category TEXT, description TEXT,
  created_at INTEGER, updated_at INTEGER,
  embed_model TEXT, embed_dim INTEGER,        -- 绑定模型，换模型→重建
  status TEXT);                            -- ready / indexing / pending

-- 知识集内文档（来源文件，关联 L0 的 files）
CREATE TABLE documents(
  id INTEGER PRIMARY KEY, collection_id INTEGER, file_id INTEGER,  -- → files.id
  path TEXT, name TEXT, mtime INTEGER, parse_status TEXT,    -- parsed/skipped/failed
  n_chunks INTEGER, parsed_at INTEGER);

-- 文本块 + 向量
CREATE TABLE chunks(
  id INTEGER PRIMARY KEY, document_id INTEGER, collection_id INTEGER,
  ord INTEGER, text TEXT, n_tokens INTEGER,
  vec BLOB);                              -- f32[1024]，起步暴力 KNN
CREATE VIRTUAL TABLE chunks_fts USING fts5(text, content='chunks', tokenize='trigram');

-- 规模上来后改用 sqlite-vec 的 vec0 虚表（替代 chunks.vec BLOB）
-- CREATE VIRTUAL TABLE vec_chunks USING vec0(chunk_id INTEGER, embedding float[1024]);
溯源链 chunks.document_id → documents.file_id → files.path，回答里的引用据此定位原文件，用 L0 的 open_in_system 打开。

08资源 · 分发 · 性能预算

资源占用（GB10 128GB 统一内存）

组件占用说明
35B-A3B-FP8（vLLM）~35GB 显存 + KV既有，生成 + 重排
bge-m3（fastembed）~1.1GB（int8 ~0.7GB）权重 + 激活；CPU EP 则不占 GPU
L0 索引库~800MB / 149 万文件砍 path-trigram 后，元数据为主
L1 向量1024×4B = 4KB/chunk1 万 chunk = 40MB，可忽略

性能预算（单知识集）

规模建索引（CPU）检索方案
几千 chunk（百~千文档）几分钟暴力 <5msBLOB+暴力 ✅
~1 万 chunk十几分钟~10msBLOB+暴力 ✅
~10 万 chunk转 GPU 更佳~50-100ms（内存~400MB）暴力天花板
100 万+ chunk需 GPU毫秒（ANN）换 sqlite-vec/LanceDB

问答延迟：检索毫秒级 + 35B 生成秒级（本地基线）；35B 重排会额外加几秒，仅在召回不准时触发。

模型分发

  • embedding 模型 ~1GB 不进 .deb（太大）：首次按需下载 + sha256 校验（复用 sha2）+ 设置页"知识库模型"下载/体检卡（仿现有依赖体检卡）。
  • 离线场景：允许手动放置模型到 ~/.pinvou3/models/。
  • 不破坏 OTA：模型缺失时知识库功能优雅降级（仅 fts 全文可用），运行时 chip 提示。

09演进路线

目标是全链路，但分阶段交付——每阶段都可独立用，后端与 UI 壳解耦推进。

Phase 1 · 文件管理（后端就绪）

FilesView 全量上线 L0 已备

拆 KnowledgeView → FilesView；搜索 + 按类型浏览（补 kb_type_counts）+ 最近修改 + 全部文件表 + 行内"加入知识库"占位。深色 + 三语。最快出真实可用页面。

Phase 2 · 知识集 + 全文（零额外模型）

L1 骨架 + fts 检索 MVP 验证

collections/documents/chunks 表；知识集 CRUD UI（照稿）；file_ingest 解析 + chunker + chunks_fts 全文检索。不碰向量，先验证"选定范围 + 按内容找"的交互。

Phase 3 · 语义检索（加 embedding）

fastembed-rs + 混合检索 语义

接 bge-m3（CPU EP）；BLOB 向量 + 暴力 KNN；fts + 向量 RRF 融合。模型按需下载 + 校验 + 设置页卡。

Phase 4 · RAG 问答 + 联动（全链路）

35B 问答 + 对话 @ + MCP 完整

kb_ask 带引用的 RAG；可选 35B 重排；对话里 @知识集；MCP kb_query 暴露给模型自调；增量重解析；规模大时切 sqlite-vec/GPU。

10风险与权衡

风险影响缓解
ARM 上 ONNX-GPUGB10 aarch64+Blackwell 上 onnxruntime CUDA EP 可能不现成起步 CPU EP（够用）；嫌慢切 vLLM-embed 走已调通 GPU 栈
本地 35B RAG 质量答案聪明度受本地模型基线封顶强制可溯源（用户自校）；检索质量 > 生成花哨；必要时 35B 重排
全量 vs 选定误用对全盘做向量化=成本/噪音/隐私灾难架构强约束：L1 只对选定知识集；UI 不提供"全盘建知识库"
切块质量chunk 切不好直接拉低召回上限保留结构边界 + 重叠；后续上语义切分
模型分发体积~1GB 模型不能进 .deb按需下载 + sha256 + 离线手动放置 + 缺失降级到 fts
vLLM 高负载卡死GB10 上 vLLM 持续高负载会累积卡死embedding 进程内隔离不压 vLLM；RAG 调用走既有跑批纪律
schema 迁移换 embedding 模型/维度需重建向量user_version 卡死；L1 向量是可重建缓存，重建无数据损失
一句话总览 L0 全量做货架（已就绪），L1 让用户圈选知识集做内容化（file_ingest 解析 + chunk + fastembed 进程内 + 混合检索），L2 用既有 35B 做可溯源的 RAG 问答并暴露给对话/MCP。全部进程内嵌入式、不依赖 vLLM 做 embedding、不破坏单体离线分发。先文件管理、再知识集全文、再语义、再问答——四阶段全链路落地。
