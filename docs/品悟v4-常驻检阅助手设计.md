## 0. 为什么推翻自动触发

旧 v4 P0：pinvou 只在主 AI 调 `request_user_input` 时自动出场，看一个 stateless 的选择题 packet，fresh context 不喂历史。三个问题逼我们放弃它：

1. **工程坑**。自动触发 = 在主 AI 流程里硬塞一次同步 LLM 调用。实测本地 Qwen3.6 审一个 3 题×3 选项的 gate 要 6.2s，超过代码里 5s 超时 → review 静默丢失 → 一个 session 两次 gate 只出一次审查。且 review 阻塞选择卡显示，Boss 白等 5s。
2. **噪音**。每个选择题都自动插一段审查，Boss 没要也来，多数是「这个你确认下」的废话。
3. **能力弱**。stateless 只看当前选择题，pinvou 连主 AI 在干嘛都不知道，只能就选项论选项。

Boss 主动召唤把这三条全解了：异步（转圈等天经地义，无超时/阻塞坑）、只在 Boss 想要时出场（无噪音）、能看到全局（审得准）。

**讨论中翻案的两条**（旧版隐含假设，本稿推翻）：

- **产物不是普适的锚**。无产物场景（咨询/决策/情感/头脑风暴/答疑）占一大半，那里 AI 在对话里说的话本身就是应对、就是审查对象。上下文组装不能预设 `write_file` 存在。
- **「屏蔽推理层」是错的**。审决策、咨询场景里 AI 的推理恰恰是审查对象，屏蔽了 pinvou 直接哑火。独立性的真来源不是裁内容，是 **角色框定 + 「比对需求 vs 应对」的任务结构**（见 §4）。

## 1. 设计结论

新 v4 做的事：**Boss 任何环节主动召唤 → pinvou 拉取召唤点之前的 session 上下文，投影成「需求 vs 应对」→ 自选领域人格 → 单次独立审查 → 在对话流插一张审查卡，给建议/风险，Boss 自行消化。**

它不是：

- 自动驾驶，不替 Boss 点按钮、不调 `submit_user_input`。
- 自动触发，不在任何 gate 主动出场（除非 Boss 召唤）。
- 把审查或返工指令发回主 AI（P0 不回传，回传即滑向自动驾驶）。
- 带独立 state / Boss 偏好记忆的长期体（连续召唤靠审查卡进 messages 解决，见 §6）。
- 多 agent loop / 和主 AI 多轮打磨。

保留旧版唯一的硬边界：**pinvou 只检阅、不决策，最终选择永远归 Boss。**

---

## 2. 统一抽象：需求 vs 应对

抛开「产物 / 轮数 / 层」，所有 Boss×AI 工作只有两个语义对象：

```
   Boss 的需求/处境/意图   ←→   AI 的应对
            pinvou 审这两者之间的「差距」
```

这个抽象不挑场景。「应对」的形态随场景自适应：

| 场景 | 「AI 应对」= 什么 |
|---|---|
| 产物型（旅行/邮件/报告/PPT/代码） | 最新产物 |
| 咨询/决策（offer/商业/人际） | AI 的论述/分析/推理本身（**是应对主体，必喂**） |
| 操作执行（订票/改配置/跑脚本） | 已发生的副作用 + 将要做的计划 |
| 探索型（边聊边演化方向） | 当前阶段的方向性结论 |

pinvou 的价值 = 站在 Boss 侧，独立检查「AI 的应对是否真的服务了 Boss 的需求」，并发现 AI 和 Boss 自己都可能忽略的风险/遗漏/意图偏移。

## 3. 召唤交互

### 3.1 零负担召唤

召唤 = **一个动作**，Boss 不选领域、不填范围。入口形态见 §10（待拍板），建议默认「输入框旁常驻按钮」。

### 3.2 领域人格：自报家门 + 可换脸

**核心原则：别让 Boss 选人格。** Boss 召唤恰恰因为「说不清哪里不对」，逼他先判断「这属于商业/情感/法务」是错的负担，且领域无法穷举、边界天然模糊。

把领域分类从【召唤前 Boss 的决策】挪到【召唤后 pinvou 的自我声明 + Boss 的可选纠偏】：

```
┌──────────────────────────────────────┐
│ 🧭 商业顾问视角   ·  换 ▾ 情感 / 法务  │  ← 自报家门 + 一键换脸
├──────────────────────────────────────┤
│ 风险：这笔预算占你流动资金 60%……        │
│ 建议：先留 3 个月缓冲……                 │
└──────────────────────────────────────┘
```

- pinvou 单次调用内：**先自判领域 → 以该人格审 → 输出**（分类+审查一步到位，不拆多步，本地小模型更稳）。
- 卡顶一行**署名**「商业顾问视角」：既是透明度，也是纠偏入口。
- pinvou 自识别的次相关领域作为「换 ▾」候选，Boss 点了重审。

### 3.3 跨领域决策（实测修正）

原设计想要「多人格并列三栏」。**实测发现模型不这么干**——跨领域问题（如「为创业搬城市」=商业+家庭+法务），Qwen3.6 自然塌缩成 **单主人格 + `alternates` 暴露相关领域 + issues 按维度分**，内容一条不少、形态更紧凑。采纳这个自然形态（比逼它多栏并列或多次调用更省、更稳）：

```
┌──────────────────────────────────────┐
│ 🧭 职业规划顾问  ·  也涉及 法务 / 家庭   │  ← 单主人格 + 相关领域标签
├──────────────────────────────────────┤
│ ⚖️ 竞业协议：2 年内做同行有违约风险……     │
│ 💼 客户网络：8 年本地积累切断即归零……     │
│ ❤️ 家庭：老婆工作、孩子上学未安置……       │
└──────────────────────────────────────┘
```

每条 issue 自带 `persona` 维度标签，UI 分维度展示。触发由 pinvou 自己判断，不由 Boss 选。

### 3.4 鲁棒性：不求识别准，只求可见可纠

本地 Qwen3.6 判旅行/代码很稳，判商业/情感/人生决策这种模糊边界会晃。但「自报家门 + 一键换脸」兜底 → 晃了 Boss 一眼就能纠，识别不完美也不致命。**把识别的不确定性摊开在桌面上、交给 Boss 兜最后一手**，比「系统静默自动分类（错了 Boss 都不知道）」更稳。

## 4. 上下文投影：召唤时喂什么

### 4.1 全程骨架原则（实测修正：能全喂就全喂）

「召唤需要多少轮」是伪命题——真正该控制的是「每轮留多少」。按轮数切（最近 N 轮）一定出事：会拦腰砍断跨多轮的任务，且 Boss 最关键的约束往往第一轮就说了。

**实测推翻了「必须先投影」的前提**：真实 session 全喂 1.2 万 token、94% 是 tool 噪音，pinvou 没被淹没、不乱挑刺，还能从噪音里挖出事实核查（签证有效期、景点闭园）。所以策略改为：

> **能全喂就全喂，超过阈值才投影。** 短 session（粗估 < ~1.5 万 token）直接喂原始 transcript，挖得最深、还省掉投影盲区；长 session 才降级到投影压缩。投影是「上下文超长时的降级手段」，不是默认路径。

投影时仍按信息价值裁剪（每轮只留骨架），**但事实层不能粗暴截断**——实测确定性截断 web_search 会丢深层事实（全喂能抓到的签证/闭园，投影截断后丢了）。事实层要么 LLM 摘要、要么保留更多要点，见 §10.2。

### 4.2 投影规则（从 `messages` 抽取，可验证到 block 级）

messages 是 anthropic 风格 content blocks（`text` / `tool_use` / `tool_result`）。投影规则：

| 抽取目标 | 从哪来 | 规则 |
|---|---|---|
| Boss 需求 | `user` 消息的 `text` block | **全留原文**——Boss 亲口说的，密度高、量小 |
| Boss 已确认决策 | `request_user_input` 的 answers（`tool_result`） | 留——Boss 的历次选择是强需求信号 |
| 需求演化转折 | 同上，识别「改主意」语句 | 留转折点（见 §4.4） |
| AI 应对·产物 | **读 workspace 文件当前内容**（识别最后 write_file/**edit_file**/present_artifact 的 path） | 整篇喂到 `ARTIFACT_CHAR_LIMIT`(30k 字)，超大才截断+标注。**不从 tool input 重建**——会漏 edit_file（实测 bug，§10.10） |
| AI 应对·论述 | `assistant` 的 `text` block | 咨询/决策场景**留**；产物场景可略 |
| 事实证据 | `user` 的 `tool_result`（对应 `web_search` 等） | 留**被产物采用的结论摘要**，不留原始 dump |
| 噪音（扔） | `checklist_*`、中间产物版本、工具调用细节 | 不喂 |

### 4.3 独立性靠框定，不靠裁剪

不靠「不给推理」换独立——那既误伤审决策场景、又不是独立性的真来源。靠两点：

1. **角色框定**：system prompt 把 pinvou 钉死在「Boss 的代理人/批判者」，明确「你的任务是挑 AI 应对的毛病，不是复述/认可它」。
2. **任务结构**：pinvou 拿到的是「需求 + 应对」的并置，工作是**比对二者差距**，起点永远是 Boss 需求、不是 AI 结论。这个结构天然抗同化。

同一段 AI 论证，标成「背景，请采信」会同化，标成「待审对象，请挑刺」不会——**同化取决于框定，不取决于内容选择。**

### 4.4 需求漂移 / intent drift

长期工作里 Boss 想要的会从 A 漂到 B。按初衷审会误报「AI 偏了」（其实 Boss 自己变了）；按最新审又漏掉「AI 把 Boss 不知不觉带偏」——而后者恰是 pinvou 最该抓的。

**对策：需求维度保留演化的关键转折点，不只给最新快照**，让 pinvou 自己判断漂移是 Boss 主动的还是被带的。

## 5. 领域人格演进：一个骨架，深度独立加

§3 的交互骨架（召唤零负担 → 自报视角 → 可纠偏）永远不变，底下的人格可以慢慢加深：

| 阶段 | 「人格」是什么 | 交互 |
|---|---|---|
| **MVP** | prompt 里一个「视角参数」（一句话切关注点） | 不变 |
| 升级 | 真正分离的 persona（各自审查清单/关注点/语气，复用 `personas.rs`） | **不变** |
| 跨域 | 自识别到跨领域 → 多人格各一句 | **不变** |

先把交互定对，人格深度后面慢慢喂。复用 `personas.rs`（`get(id)` / `equip_body_injection` / `equip_anchor` 现成）。

## 6. 连续召唤与持久化

Boss 大概率追问（「那预算呢」）。纯 fresh 每次重读 = 不知道「那」指代上轮 pinvou 说的啥；给 pinvou 独立 state 又违反「无记忆」边界。

**解（实测修正）：审查卡进 sidecar（`pinvou_reviews.json`），不进 `messages`。** 审查卡是纯前端展示，**绝不能进 messages**——messages 会在 engine 冷启动时注水回 LLM，污染主 AI。走独立 sidecar（同 `persona_events` 范式）：每条 `{pos, review}`，按 pos 在 `rerenderFromMessages` 插回，切会话/重载不丢，**不引入 pinvou state**（顺带解决 `rerender_restores_live_bubbles`）。Boss 要主 AI 看审阅 → 走转交按钮（§7 B1），那才进 messages/LLM。

**实测 ✓（机制）**：sim 里把上一轮审查塞进上下文后 Boss 追问「那预算怎么砍到 2 万」，pinvou 接得上、人格切「成本控制顾问」、给具体置换方案。机制可行。**但 B2 sidecar 不进 LLM**，所以「纯召唤接续上轮审查」需 summon 时读 sidecar 喂回——未做（§10.8）；当前接续靠 Boss 点转交（B1，审阅进 messages，下次召唤自然可见）。

## 7. 输出协议（审查卡数据结构）

单次调用产出，结构 guard 在 Rust 层做：

```json
{
  "personas": [
    {"id": "business", "label": "商业顾问", "primary": true}
  ],
  "alternates": ["emotion", "legal"],
  "trace": "给 Boss 看的短句，像微信",
  "recommendations": [
    {"topic": "待决策点（方案选择/出发日期…）", "pick": "推荐选哪个", "why": "一句理由"}
  ],
  "issues": [
    {"severity": "low|medium|high", "kind": "risk|irreversible|quality|intent_drift|missing_constraint",
     "persona": "business", "text": "问题", "suggestion": "建议"}
  ],
  "risk": "low|medium|high",
  "confidence": 0.0
}
```

- `personas`：pinvou 自选的出场人格，**实测通常单个 primary**；跨领域时其余相关领域放 `alternates`，不并列多 primary（§3.3）。`issues[].persona` 标维度。
- **含 `recommendations`（助决策）**：AI 把选择/待定项抛回 Boss 时（弹选项 or 文本列方案），pinvou 逐项给推荐 `{topic, pick, why}`。推荐 ≠ 替选（§1 允许），与 issues 正交——没 issue 也可有推荐。**实测修正**：曾误删此字段（理由"召唤式无推荐语义"），被真实场景证伪（主 AI 列 A/B/C 问偏好，pinvou 不能干说"没问题"）。
- 不含 `verdict`——召唤式不替 Boss 拍板。
- **转交（B1，已实现）**：审查卡「让主 AI 按此改」按钮把 recommendations+issues 组装成 Boss 消息发给主 AI——Boss 主动驾驶、不是 pinvou 自动回传，这才进 messages/LLM。
- 空 `issues` 合法且常见——无实质问题就返回 `[]` + trace「看过了没问题」（实测 4/4 机械琐事场景如此）。
- Runtime guard：`issues[].persona` 必须在 `personas`∪`alternates` 内。MVP 阶段人格是「视角参数」非预注册 persona，**暂不校验 id 已注册**（理由见 §11 实证）；升级到真 persona 后再加白名单。

## 9. MVP 边界（P0 做什么）

第一刀只做：

- 纯召唤（删自动触发），输入框旁按钮。
- 全程骨架投影（§4.2 规则，先用确定性规则抽，不上 LLM 抽骨架）。
- 人格用「视角参数」**不做真 persona 分离**；自报家门 + 可换脸。
- 审查卡 sidecar 持久化（不进 messages，独立 `pinvou_reviews.json`）+ 转交按钮——B1+B2 已实现。
- 单次调用，超时放宽到 20–30s。

**验证目标**：① 自识别领域准不准；② Boss 用不用「换脸」；③ 全程骨架够不够 pinvou 审到点。这三个数据决定下一步是否把人格做深、是否要 LLM 抽骨架。

## 10. 已知难题 / 待拍板（评审聚焦）

1. **召唤入口形态**：输入框旁常驻按钮 / `/pinvou` 命令 / 每张卡上挂「让 Pinvou 看看」。建议默认按钮。
2. **谁抽骨架 / 全喂还是投影**（实测有数据）：① 短 session 直接全喂——实测 1.2 万 token、94% 噪音不崩、挖得更深，免投影盲区；② 超阈值才投影降级，但确定性截断 web_search 会丢深层事实（全喂抓到的签证/闭园，截断投影丢了）→ 事实层考虑 LLM 摘要。MVP：全喂为主 + 长 session 投影降级，事实层暂留确定性并标注盲区。阈值具体多少 token 切，只测了 1.2 万一个点，需补测。
3. **自识别错误率**：本地 Qwen3.6 对模糊领域的识别准度未实测，靠「可换脸」兜底，但需要数据。
4. **超长 / 多任务 session**：「全程骨架」会把不相关任务也塞进来稀释重点，需要按「任务段」切分——P0 不做，遇到再加。
5. **跨领域多角的触发与成本**：单次调用扮多角 vs 串行多次，本地模型质量/速度待验证。
6. **人格做多深、何时从视角参数升级到真 persona**：取决于 §9 验证数据。
