# 对话记录提交与引擎回收

应用会在模型热切换、空闲回收、会话删除重建以及失败 spawn 清理等时机回收引擎实例。底座在空闲期间仍可通过 `SessionUpdated` 追加内部运行时消息，例如 MCP 启动失败说明。

此前，事件转发器通过 `spawn_blocking` 写入对话记录，等待写入完成后才发出 `chat:transcript_committed`。引擎回收可以中止等待中的转发器，却不能中止已经开始的 blocking 写入。于是文件已增加运行时消息，界面仍只知道上一个提交版本；严格版本对账一直失败，并误报“对话记录暂未同步”。

修复将普通对话的引擎快照写入、版本计算和提交通知放在同一个 blocking 事务中。写入成功后即使转发器被中止，也会发布这一份快照的版本及消息数；失败不发布提交标记。终态缓存继续避免重复保存，后续运行时提交会提供更新的版本，不放宽界面的版本比较或编辑 CAS。

每个引擎实例另有独立的写入存活标记。回收和未发布引擎的销毁先撤销标记，再中止转发器。写入在 SessionStore 的 mutation 锁内检查标记，排队中的旧引擎写入因而不能覆盖后继任务。已获准的写入持有同一把锁直至通知结束；新引擎在 blocking worker 上取得这把锁后读取启动基线，保证基线包含这些已完成的提交。界面查询仍可使用普通只读快照接口。

回归测试使用合成任务和合成 MCP 运行时消息，覆盖写入已完成、通知尚未发布时中止转发器，后继引擎基线的等待顺序、退休写入拒绝、后继任务保全、旧版本 CAS 拒绝及失败写入不发布通知。测试不需要模型、联网或用户会话内容：

```sh
cargo test --manifest-path pinvou3-app/src-tauri/Cargo.toml --lib transcript_commit_tests -- --test-threads=1
```
