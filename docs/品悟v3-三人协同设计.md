# 品悟 v3 · 三人协同设计

> 状态：设计稿 v0，待 Boss 评审
> 背景：v2「单 LLM 换 persona」实战觉得不够用 → 升级为「独立 engine 三人协同」。本稿结论多数已用真实 Qwen3.6 实跑验证（见 §12）。
> 一句话：**Boss、AI、品悟在一个聊天室里协作；品悟是 Boss 不在场时的意图锚，AI 干活它把关，Boss 大多数时候当观众，只在岔路口出手。**

---

## 0. 为什么 v2 不够用，v3 改什么

v2 的品悟是**同一个 LLM session 换 persona 审自己前面 turn 的产出**。三个硬伤：

1. **独立性几乎为零**：被审方案就躺在自己上下文里，"换个口气审自己"，审不出自己模型级的盲区。实跑实证：旅行规划里作者把「10 天」做成 7 天行程，同源品悟也没数出来。
2. **不是协同，是一次性把关**：v2 品悟在 plan 节点审一次出报告，没有「AI 改 → 品悟复审 → 收敛」的迭代。
3. **人格是贴在 user 消息里的临时指令，不是真 system prompt**，独立性先天打折。

**v3 的核心升级**：

| 维度 | v2 | v3 |
|---|---|---|
| 品悟载体 | 同 session 换 persona | **独立 engine 实例**（真 system prompt + fresh context） |
| 协同形态 | 节点把关一次 | **作者-评审迭代 loop**（立账→核账收敛） |
| Boss 参与 | plan 出炉时人工 review | **全自动当观众 + 信号灯召回 + 三档介入** |
| 停止 | 用户每次手动 | **品悟报信号自动停**（⚖🔴🟡🟢）+ 轮数兜底 |
| 盲区补偿 | 无 | **结构化核对流程**（不写场景代码、不接外部源） |

v2 已落地的 50%（`review_gate` / toggle / bundle skill / `engine_pool` / `request_user_input` 接入）**全部留用**，v3 是在其上补独立 engine + 编排 + 交互，不是推翻。

## 1. 整体设计（纲领）

### 1.1 核心定位

> **品悟 = Boss 不在场时的意图锚，代行 Boss 的两件事：审 + 答。**

- **审**：用 Boss 的视角看 AI 的产出——这是不是 Boss 想要的？
- **答**：AI 卡住、不确定 Boss 要 A 还是 B 时，品悟代 Boss 回答，让流程在 Boss 不在场时不卡死。

这个定位决定了一切边界：品悟只说 **Boss 会关心的**（方向、风险、是否跑题），不挑技术细节（那不是 Boss 的事）、不加需求（它是审不是设计师）。

### 1.2 统领类比：L2 自动驾驶「人机共驾」

| 角色 | 对应 |
|---|---|
| Boss | 驾驶员（随时可接管，平时放手） |
| 自动档（AI↔品悟 自动协同） | 自动驾驶 |
| 品悟 | 副驾 / 系统（盯路、提示、代答） |
| 信号灯（🟢🟡🔴⚖） | **接管提示** |

整个产品的体验目标：**Boss 能安心放手当观众，但系统持续告诉他"路况健康度"，该接管时高亮叫他。**

### 1.3 架构：三角色 + 一块共享黑板

```
        ┌─────────── 聊天室（一个 session）───────────┐
        │                共享消息流（黑板）              │
        │   Boss ✍       AI ✍        品悟 ✍            │
        └──────────────────────────────────────────────┘
              ▲              ▲                ▲
          真人输入      主 engine        品悟 engine
                       (累积上下文)    (每次 fresh 组装)
```

- **黑板** = 这个 session 的群聊记录，三个角色都往上写、都能读。
- **AI** = 一个长跑的主 engine，累积上下文。
- **品悟** = 一个独立 engine，**不泡在群里**，每次被事件唤起、临时组装材料审完即走（详见 §8）。
- 对用户：就是一个群在聊天。对系统：品悟是独立实例（这是独立性的来源）。

### 1.4 设计哲学（贯穿全文的红线）

1. **通用优先，不为场景写规则**：品悟靠模型 + prompt 流程，**不写领域校验代码、不接领域外部源**——那些是枚举式的，永远覆盖不完，还给虚假安全感。
2. **品悟话少话重**：一个任务出场不超过几个节点，宁可说"这次没啥可挑的"。多 agent 群聊全死于刷屏。
3. **Boss 注意力是最贵资源**：所有设计围绕"减少 Boss 必须出手的次数，但每次出手都是高价值决策"。
4. **诚实标边界**：品悟不假装全知，核实不了的事实明说"未核实"，交 Boss。这是 Boss 敢放手的信任地基。
5. **品悟是 navigator 不是 driver**：它指方向、踩刹车、代答，但**不抢方向盘自己写**。

## 2. 用户流程（端到端）

### 2.1 主干流程

```
Boss 提需求
   ↓
AI 接活 ── 先出「理解 + 骨架」（轻量，不是完整产物）
   │         信息不足处用合理默认值，并显式标注是假设
   ↓
品悟审 ── 第一刀＝结构化核对需求缺口；顺带审硬伤
   ↓
┌── 打磨循环（AI↔品悟 自动，Boss 围观）──┐
│   AI 改 → 品悟核账 → 报信号               │
│   🟢 继续 → 回到 AI 改                    │
└── 🔴/🟡/⚖ → 跳出循环 ──────────────────┘
   ↓
召回 Boss（给干净的决策界面，不是一坨过程）
   ↓
Boss 拍板 / 补充 / 纠偏  ──→ 回到 AI 接活
   ↓（Boss 满意）
收口 ── 品悟 final 体检「你要的都齐了吗」
```

### 2.2 关键设计：AI 先出场，但"第一次发言要轻"

**不是品悟先体检，是 AI 先接活。** 理由：品悟的"审 + 答"都要求先有 AI 的动作；让审查者抢在干活者前面发言，顺序是拧的；而且"缺什么信息"最该由要动手的 AI 判断。

但为了不让 AI 带着错误假设闷头做完一大坨再返工——**控制 AI 第一个产出物的"重量"**：第一次只出「我的理解 + 骨架」，信息不足处用默认值并**显式标注假设**。品悟在这份轻量骨架上审，第一刀正好抠出需求缺口。这样：顺序对（AI 先）、需求澄清没丢（品悟审理解时浮现）、返工小（改的只是骨架）。

`request_user_input` 因此回到它该在的位置：**是 AI 的工具**（AI 连合理假设都做不出来时才弹问题打断 Boss），不是品悟的前置步骤。

### 2.3 两类任务，品悟两种模式

| AI 在干什么 | 品悟的模式 |
|---|---|
| **完成型**（交一个收敛的方案/产物） | 挑硬伤（critic）：结构化核对 + 找风险 |
| **发散型**（头脑风暴 / 创作 / 发散发文） | **别挑刺**（会扼杀发散）：改成"哪个点子 Boss 最会买账 / 这符合你的调性吗"——帮筛选、指方向 |

品悟需在出场时先判断当前是哪类，切换模式。误用 critic 去审发散创作是常见失败。

## 3. Session 设计（多人聊天室）

### 3.1 双人模式 vs 三人模式：品悟 toggle = 模式开关

pinvou3 现状每个 session 是 Boss↔AI **双人对话**。品悟开关本质上把一个 session 从双人切到**三人**：

| 模式 | 挂载的 engine | 说明 |
|---|---|---|
| **双人**（品悟 OFF，默认） | 1 个 AI engine | 现状，Boss 直接和 AI 聊 |
| **三人**（品悟 ON） | 1 个 AI engine（累积）+ 1 个品悟 engine（fresh） | 共享该 session 的群聊黑板 |

这与 v2「品悟是正交 toggle，不是第三种工作流」一致——它正交于 Plan/YOLO，只是 v3 里"开品悟"意味着真的多挂一个独立 engine，而非换 persona。

### 3.2 「单开多人聊天模式」的主张

建议把三人协同做成一种**显式的会话类型**，而不是隐式状态：

- 新建会话时可选「普通对话」/「品悟协同」，或在会话内 toggle 切换；
- 切到三人模式 = 系统为该 session 懒启一个品悟 engine；切回双人 = 品悟 engine 释放；
- 一个 session 的黑板（群聊记录）天然支持多发言者，每条消息带 `speaker`（Boss / AI / 品悟）。

### 3.3 数据模型：黑板 = 带发言者的群聊记录

- SessionStore 的消息流从"双人交替"升级为"多发言者群聊"：每条 `{speaker, content, kind, signal?}`。
- `kind` 区分：Boss 指令 / AI 产出 / AI 干活折叠条 / 品悟审查结论 / 系统决策卡。
- **AI engine 累积订阅**这条黑板；**品悟 engine 选择性引用**（不全量订阅，见 §8）。

### 3.4 一个 session 挂几个 engine + 品悟 engine 要不要每 session 独占

- AI engine：每个三人 session 一个（与现状一致，累积该 session 上下文）。
- 品悟 engine：因为它**无状态**（每次组装输入、审完释放、不累积），有两种实现取向：
  - **MVP**：每个三人 session 懒启一个品悟 engine（简单、隔离清晰）；
  - **优化**：品悟做成**池化的无状态 reviewer 服务**，一个品悟 engine 轮流服务多个 session（省资源）——因为它本就不带 session 状态，每次靠组装输入工作。
- **建议**：MVP 先每 session 独占，跑通后视资源压力再池化。

### 3.5 并发与后端约束

- `engine_pool` 已支持多 session 并发，每个三人 session 挂一对 engine。
- 后端 vLLM `--max-num-seqs 8`（8 路并发）。一个活跃三人 session 同时最多 1–2 个在跑（AI 或品悟，通常交替），**约可支撑 3–4 个并发活跃三人 session**。品悟 engine 池化可缓解这个上限。
- 这是个真实容量约束，UI 上若多个 session 同时高强度跑，需排队提示。

## 4. 交互设计

### 4.1 观众视图（Boss 99% 时间看到的）

```
┌───────────────────────────────────────────────┐
│ 👤 Boss   帮我规划 10 天 9 夜欧洲自由行            │
│                                                 │
│ 🟣 品悟   需求体检：2 件事得你定 ⚖               │  ← 品悟气泡（关键信息，展开）
│   · 预算量级？ · 几个国家？                       │
│   〔我先按经济舒适/法意为主让 AI 起草，你回头看〕  │
│                                                 │
│ ⚙ AI 正在起草方案…                              │  ← AI 干活：折叠成状态条
│                                                 │
│ ┌ 🟣品悟 × ⚙AI 打磨中 · 第 2 轮 ──────── 🟢 ─┐ │  ← 过程折叠 + 信号灯
│ │  上轮：补了签证费、拆了行程天数          展开▾│ │
│ └──────────────────────────────────────────────┘ │
│                                                 │
│ [ 输入框：随时打字即接管 ]            [🟣品悟 ON] │
└───────────────────────────────────────────────┘
```

三条呈现原则：
- **AI 干活折叠**成一行状态条，不刷每一步；
- **品悟发言展开**（它是关键信息），但 AI↔品悟 的逐轮来回**折叠**成一行进度+信号灯；
- **默认克制，热闹可选**：想看它俩怎么来回的，点「展开」。

### 4.2 信号灯仪表盘 = 接管提示

把品悟四信号直接挂在打磨进度条上，当 Boss 的"该不该出手"仪表：

| 灯 | 含义 | Boss 该做什么 |
|---|---|---|
| 🟢 继续 | 在进步 | 安心当观众 |
| 🟡 卡住 | 没进展/僵持 | 可瞥一眼要不要插手 |
| 🔴 交付 | 没硬伤了 | 系统召回：过目 |
| ⚖ 岔路 | 只有你能拍 | 系统召回：决策 |

Boss 盯一个灯即可，不必盯全程。

### 4.3 品悟气泡的三层结构

品悟一次发言分层呈现，不同人各取所需：

```
🟣 品悟
  方向对，但有 2 件事我替你盯着 👇        ← ① 一句话总判（Boss 扫一眼就够）
  · 行程只排了 7 天，你要的是 10 天        ← ② 硬伤清单（每条带"建议怎么改"）
  · 预算漏了签证费，实际偏紧
  ⚖ 这个要你拍：深度游 2 国 vs 打卡 5 国   ← ③ 只有 Boss 能定的，单独标
```

### 4.4 Boss 主动参与：三档力度

| 档 | 入口 | 何时用 | 效果 |
|---|---|---|---|
| **轻** | 对某条消息一键反馈（🚫这条别管 / 📌这条盯紧） | 品悟某条你觉得多虑/很重要 | 不打断，微调品悟关注点 |
| **中** | 输入框打字（可 @AI/@品悟/泛指） | 改方向、补需求、纠偏、提前拍板、回答疑问 | **立即接管**，自动档让位 |
| **重** | 决策按钮 + 全局开关（✓确认/选A选B/换手动档/暂停） | 系统召回时拍板，或换驾驶模式 | 拍板 / 切档 |

「何时参与」的答案：被动上，信号灯 🟡🔴⚖ 亮就是时机；主动上，Boss 任何时候想说都行——**自由不设限，但系统保证他不必时时盯着**。

### 4.5 被动召回：三种停 → 三种决策界面

给 Boss 的不是过程，是干净的决策：

- **⚖ 岔路** → "还剩这个要你拍：〔深度游 2 国〕vs〔打卡 5 国〕" + 两个按钮；
- **🔴 交付** → "打磨好了，过目 →【终稿】" + 〔就这样 / 再改改〕；
- **🟡 卡住** → "它俩在〔X〕上卡住了，两种意见 + 现状，你定夺。"

每个都配「展开看它俩怎么来回的」折叠入口。

## 5. 停止与接管机制

### 5.1 品悟报信号，而不是数轮数

轮数是笨刹车（实跑见过撞 3 轮还在震荡）。改成**品悟每轮收尾报一个信号**，把"还要不要继续"的判断也交给它代行：

判断分两段，**先看岔路，再看进展**：

1. 这轮冒出"只有 Boss 能拍的取舍"了吗？→ 有则 **⚖ 立刻停**（压倒一切，别让 AI 在该问人的假设上越跑越远）；
2. 没有，再看打磨状态：稳了 **🔴 交付停** / 原地打转 **🟡 卡住停** / 还在进步 **🟢 继续**。

**轮数只作兜底保险丝**（硬上限如 4 轮），防品悟自己犯糊涂一直喊 🟢。健康任务通常是 🟢🟢→🔴 或 🟢→⚖。

### 5.2 认知层全自动，执行层留闸

- **认知层**（要不要再磨一轮）：可以全自动，走上面的信号机制。
- **执行层**（AI 要做不可逆的事：花钱、发邮件、删文件）：**不走这套**，由 careful hook 硬拦 → Boss 确认。
- 一句话：**认知可以放手，动作要留闸。** 别让"自动打磨很顺"把"自动按下不可逆按钮"也带过去。

### 5.3 🟡 卡住时的默认处理（待 Boss 拍）

两个选项，文档默认取后者，待评审：
- A：直接交 Boss 裁决；
- B：让 AI 先换个思路再试一次，还不行才交 Boss。

### 5.4 权限交接（Boss 在场 / 不在场）

```
Boss 沉默  → 品悟「代理人」：代审 + 代答，AI↔品悟 自动跑
Boss 发话  → Boss 接管：品悟退位成「参谋」（只在被问时说话）
            → Boss 的话 = 最高优先级，正在跑的 turn 让位，AI 优先执行
            → 办完 Boss 不再出声 → 自动档恢复，品悟回到「代理人」
```

三条铁律：
1. **Boss > 品悟**：冲突听 Boss。**品悟不审 Boss**；只在 Boss 这次说的和他自己之前定的矛盾时**提醒**一句（提醒 ≠ 质疑）。
2. **一句话夺权，无需登入登出**：发话即接管，沉默即归还。
3. **品悟的代理权是借来的**：Boss 在场就收敛成参谋，绝不和 Boss 抢话。

## 6. Pinvou Agent 设计（品悟本体）

### 6.1 两个职能

- **审**：customer（这是 Boss 要的吗）+ attacker（强制找硬伤）+ engineer（实施可行性）三视角混合。engineer 视角是 v2 教训——品悟若只有 customer+attacker，会放任方案膨胀到撞 output budget。
- **答**：代 Boss 回答 AI 的疑问；代不了的（Boss 的私人偏好 / 价值判断 / 外部不可知信息）→ 标 ⚖ 上交，**不瞎代**。

### 6.2 立账 → 核账（防震荡，已实跑验证）

这是 v3 评审能收敛的关键机制：

- **首轮 = 立账**：全面审，一次性立好一张「必改清单」（带 id）。
- **后续轮 = 核账**：只逐条核对清单项**是否闭合**，**严禁提清单外的新问题**（哪怕看到别的瑕疵也不许写）。
- 清单**只减不增**（闭合即移除）→ **必然收敛**。

实跑对照（真实 Qwen3.6）：自由批评式 3 轮在"软↔硬"间震荡、must-fix 永不归零；立账→核账式 2 轮干净收敛 PASS。**唯一变量是这个机制，模型没换。**

### 6.3 结构化核对（替代代码校验，压机械盲区）

不写场景校验代码（覆盖不完），改用**审查流程**逼出机械核对：

> 品悟审查第一步，**不准直接评，先把 Boss 需求里的硬约束逐条抠出来列清单**（10 天 9 夜 / 6 万预算 / 法意为主 / 悠闲），**再拿方案逐条打勾**（✓10 天？→ 方案只有 7 天 ❌）。

这个"抽约束 → 逐条对照"是**通用的**（任何场景都是"先列要求、再逐条核"），零代码、跨场景。实跑里品悟漏天数正是因为"凭印象扫"；逼它逐条核对大概率能逮住（§12 待验证项）。

### 6.4 克制原则（v2 血泪教训）

- 没硬伤就一行 **CLEAR** 收尾，**不硬凑**（"必须 ≥1 finding"会逼它凑"加需求"，v2 已删此约束）；
- **不加需求**（品悟是审不是设计师，任何"把方案做大"的建议都该被抑制）；
- **不挑技术细节**（函数名、代码风格——Boss 不在乎）；
- Suppressions 清单：把"实际增可读性的冗余""会变的阈值注释"等噪音预先压掉。

### 6.5 代答的基础与边界：画像现空，主力是"显而易见的推荐"

品悟"答"的依据分三层，优先级从高到低，**现状只有中间层在用**：

```
① 画像答（按 Boss 偏好/历史决策）  —— 现状：空（UserPrefs 空、无沉淀），留升级接口
② 专业默认答（显而易见的推荐）      —— 现在的主力
③ ⚖ 上交                          —— 既无画像、又无显然好答案的
```

**②是现在的核心**：没有画像时品悟**不装 Boss**，而是以专业/通用最佳实践角度给默认推荐，并明确标"这是默认建议，你可改"——诚实，且让 Boss 能事后纠。

**「直接答」vs「⚖ 上交」的判据**（品悟答疑的核心决策，不划清会把不该自己拍的也拍了）：

| 倾向直接答 | 倾向 ⚖ 上交 |
|---|---|
| 有公认好默认（专业最佳实践） | 无客观对错（纯 Boss 口味/价值观） |
| 低风险、可逆、改起来便宜 | 高风险、不可逆、影响整盘 |
| 例：罗马住几天 → "建议 3 天，可改" | 例：深度游 2 国 vs 打卡 5 国 → 上交 |

类比：**好助理在老板不在时，显然的小事按常识自己拍（并标一句"我按常识定了"），拿不准的大事留着问。** 画像以后填上，"按常识"自动升级成"按 Boss 一贯的习惯"——②③ 不变，①从空长实，平滑演进。

### 6.6 同源盲区与诚实边界

- 品悟和 AI 是**同一个 Qwen3.6 权重**，独立 engine 给的是 fresh context（解决"被前文绑架、不敢否定自己"），但**给不了"模型本来不会的东西"**。
- 共享盲区（"这事该打电话不该发邮件"这种方向性问题）是天花板；
- 事实层（航班、签证、价格）核实不了的，**明确标"⚠ 未核实，Boss 自查"**，绝不自信编造（实跑里品悟编错过罗马机场，反面教材）。

## 7. System Prompt 设计

> 这里给 prompt 的**内容骨架**（方案层），不是最终逐字稿。

### 7.1 AI（作者）—— 复用现状，协同引导走 per-turn

**AI 侧最小改动**：YOLO 执行模式 + 现有常驻 system prompt（`instructions.md`）**原样复用、不变**——执行风格与品悟正交（v2 已确立），careful hook 照旧在 YOLO 上拦危险命令。

下面这些「三人协同」才需要的行为，**不写进常驻 prompt**（否则双人模式也背着它，污染通用 AI），而是开三人模式时走 **per-turn 注入**（复用现有 `system-reminder` 机制；与 v2 把材料塞 user message 的做法同源）：

- 你是干活的，产出 Boss 要的东西；
- **第一次产出先给「理解 + 骨架」，别一上来做完整大物**（呼应 §2.2 + 防 output budget 撞顶）；
- 信息不足：用 `request_user_input` 问，或用合理默认值并**显式标注假设**；
- **群里会有品悟给你审查意见 → 据此修订**，但方向最终听 Boss；品悟是参谋不是老板；
- 受 careful hook 约束，不可逆动作会被拦。

> 结论：**双人模式 AI = 完全现状（零变化）；三人模式的协同行为隔离在 per-turn 层叠加，常驻 prompt 与 YOLO 机制不动。** 唯一注意：「先轻后重」对弱模型最好给一句 per-turn 轻提示，否则 Qwen3.6 可能先做大再被品悟拦、白返工一轮。

### 7.2 品悟（审查者）—— 独立 engine 的真 system prompt

```
你是品悟（代号 Pinvou），Boss 不在场时的意图锚。你替 Boss 做两件事：审 + 答。

【审】用 Boss 的视角看 AI 的产出：
  1. customer：这是不是 Boss 想要的？跑题没有？
  2. attacker：硬伤、风险、漏洞在哪？
  3. engineer：实施上可行吗？（一次输出会不会太大、步骤会不会太多）

  审查必须先结构化核对：
  - 第一步，抽出 Boss 需求里的硬约束，逐条列清单；
  - 第二步，拿产物逐条打勾；对不上的 → RAISE。
  不准跳过核对直接凭印象评。

【答】AI 问你时，代 Boss 回答。
  代不了的（Boss 私人偏好 / 价值判断 / 你不知道的外部事实）→ 标 ⚖ 上交，不要瞎代。

【账本机制】
  - 首轮：全面审，立一张必改清单（带 id）。
  - 复核轮：只核对清单项是否闭合，严禁提清单外的新问题。

【收尾信号】每次给且只给一个：
  🟢 还在进步，继续  🔴 没硬伤了，可交付  🟡 卡住/原地打转  ⚖ 撞到要 Boss 拍的岔路

【边界与克制】
  - 没硬伤就一行 CLEAR，不硬凑；
  - 不加需求、不挑技术细节、不审 Boss（只在他自相矛盾时提醒）；
  - 事实核实不了就标"⚠未核实"，绝不编造；
  - 发散型任务（AI 在头脑风暴/创作）：别挑刺，改成帮 Boss 筛点子、指方向。

【输出协议】结构化字段（信号 / 必改清单 / 账目核对 / trade_off）见 §7.3。
```

### 7.3 协议字段（机器要解析的部分）

- **信号**：`CONTINUE / DELIVER / STUCK / ESCALATE`（对应 🟢🔴🟡⚖）；
- **必改清单**（立账轮）：`[{id, 视角, 问题, 建议改法}]`；
- **账目核对**（核账轮）：`[{id, 闭合/未闭合, 说明}]`；
- **trade_off**：需 Boss 拍的取舍（可空）；
- **总判**：一句话（给 Boss 看的）。
- 协议字段保持稳定命名，UI 显示层翻译成中文；**不要把中文显示文案反写回协议**（v2.1 教训）。
- 复用 `review_gate` 的严格枚举校验：未知值直接判 Malformed（防模型把字段翻译跑偏导致误放行）。

## 8. Context 设计

### 8.1 两个 agent 的 context 性质相反

| | AI（作者） | 品悟（审查者） |
|---|---|---|
| 性质 | **累积**（长记忆，贯穿全任务） | **每次精选组装**（审完即释放） |
| 装什么 | 完整任务史 + 品悟意见 + 工具结果 + 文件 | 需求锚 + 当前被审物（钉死）+ [核账：上轮账单] |
| 谁管理 | 底座 Compaction（会膨胀，要压） | 编排层每次组装（天然有界） |
| 规模 | 大，逼近压缩阈值（256K） | 小-中（几十 K，审完丢） |
| fresh 度 | 持续上下文 | **准 fresh ← 独立性来源** |

### 8.2 品悟"被组装唤起"，不泡在群里

反直觉但关键：**品悟不该一直泡在群里听**。让它累积全程历史 = 独立性下降（退回"换 persona 审自己"）+ context 无谓膨胀。所以：

> **UX 上品悟像一直在群里，实现上它每次 fresh 拼装指定材料。**

每次唤起只喂三样钉死的东西：
1. **Boss 原始需求**（锚，防跑题）；
2. **这轮被审物**（完整，**不许摘要**——必须看完整才能审出硬伤）；
3. **机械事实**？→ 不再由代码算（已砍），改由品悟自己在 system prompt 指导下结构化核对（§6.3）；
4. 核账轮再加一份**上轮账单**。

#### 附带多少前文？——按角色精选，不是按距离取最近 N 条

这是 context 设计里最容易含糊的一块，明确钉死：

- **按距离取（滑动窗口 / 上面 N 条）= 错**。① 锚（原始需求）通常在很靠前的位置，窗口一滑就丢，品悟失去审查基准；② 窗口里反而塞满 AI 碎步、品悟旧话 → 噪音 + 损独立性。
- **按角色精选 = 对**。编排层主动挑出"这次真正需要的那几条"，与距离无关。

| 出场类型 | 精选带什么 |
|---|---|
| 首轮立账 | 锚 + **完整被审物** |
| 核账轮 | 锚 + **新版被审物** + **上轮账单**（不带旧版本全文——账单已浓缩） |
| 代答疑问 | 锚 + AI 的问题 + **必要局部上下文**（如它纠结罗马住几天，就带骨架里罗马那段）+ Boss 画像包（**现空**，见 §6.5） |

**明确不带**：AI 干活碎步、品悟自己历次长篇、核账时的旧版本全文。

**红利**：核账只需「账单 + 新版本」——账单是历史的压缩表示，用几百字账单代替几轮几万字来回。这是「立账→核账」顺带的 context 红利。

**为什么这么抠**：不是为省 token（品悟单次几 K~几十 K，256K 富裕）。真正理由是**信噪比 + 独立性**——多带一条无关的，就多一分被带偏的可能。少而准 > 多而全。

落地上不是一个「带 N 条」参数，而是**几个组装模板**（立账 / 核账 / 答疑），每种出场用对应模板去黑板挑料拼输入。

### 8.3 "不进主 session 累积" = 主 AI 只看到品悟的结论

- 品悟的**完整审查推理**活在它自己 engine 的临时上下文里，审完释放；
- 主 AI 的黑板里**只插入品悟的结论气泡**（总判 + 必改清单 + 信号），**不插入品悟的长篇内部推理**；
- 好处：主 AI 的 context 不被品悟长推理污染；品悟每次 fresh、不被历次审查绑架；品悟 context 永远可控。
- **"不累积" ≠ "失忆"**：核账记忆靠编排层**显式把上轮账单拼进去**。累积 = 被动全留；组装 = 主动精选。

### 8.4 256K window 对两者意义不同

- 对 AI：决定它能累积多久才需 compaction（tool schema 已占 ~30K）；
- 对品悟：够它一次塞完整被审物 + 锚，**绰绰有余**，根本不是约束；
- `MAX_OUTPUT_TOKENS` 已从 16K 提到 64K（v2.1，防大产物撞顶）——AI 侧尤其相关。

## 9. 权限与 Skill 设计

### 9.1 权限：AI 全读受控写 / 品悟全读零写

| | AI（作者） | 品悟（审查者） |
|---|---|---|
| 写 / 执行 | ✅ 受控写（careful hook 拦不可逆动作） | ❌ **严格零写**（铁律） |
| 读 | ✅ 全读 | ✅ 全读（要审就得看得到 AI 干的一切） |
| 改 session 状态 | ✅ | ❌ 不改 mode、不落盘 |

品悟"全读零写"三个理由叠加：定位上是 navigator；安全上只读永远搞不坏；现状 `pinvou_review_chat` 已走只读面，直接复用。

### 9.2 Tools 分配

| 工具类 | AI | 品悟 |
|---|---|---|
| 文件 read/ls/grep/glob | ✅ | ✅ |
| 文件 write/edit | ✅ | ❌ |
| shell / 执行 | ✅（careful hook） | ❌ |
| request_user_input | ✅ | ❌（代答不代问；不确定就 ⚖ 上交） |
| update_plan 等任务工具 | ✅ | ❌ |

品悟**没有**任何能改变世界状态的工具。它通过"说话"（往黑板写结论）影响流程，不通过"动手"。

### 9.3 careful hook（执行层闸，与品悟正交）

- 硬编码危险 pattern（`rm -rf /`、`DROP TABLE`、`git push -f`…）+ Pre-tool 拦截，零 LLM 开销；
- YOLO 下其它工具自动放行，**唯独危险动作弹 Boss 确认**；
- 这是基础安全，**不可关**，与品悟开关无关。

### 9.4 Skill 设计

- **复用**现有 `pinvou-review-plan` / `pinvou-review-final` 两个 bundle skill（编译内嵌、启动解包，跟 app 走不污染用户全局）；
- v3 改造点：
  - skill 内容补「结构化核对」流程 + 「立账/核账」两套指令（按轮次给不同 skill body）；
  - 因弱模型不会 progressive disclosure，**skill body 仍走 eager loading**（完整塞进唤起消息，不指望模型主动 read）；
- `review_gate` 的**协议格式校验**继续留用（检查"有没有按协议输出"，这是通用的，不在"砍场景规则"之列）。

### 9.5 明确不做（本版边界）

| 砍掉 | 理由 | 替代 |
|---|---|---|
| 机械事实块计算器（天数/预算校验代码） | 领域相关、枚举式、覆盖不完、虚假安全感 | 品悟结构化核对（§6.3） |
| 外部事实 MCP（航班/签证源） | 每场景一套、覆盖不完 | 标"未核实" + Boss 兜底 |
| 用户 @品悟 主动召唤 | 保持品悟 100% 被动灵魂 | 节点触发 + 信号召回 |
| 每 turn review | 噪音过大 | 只在交付阶段成果时接 |

## 10. 与 v2 现状的关系 / 复用清单

### 10.1 v2 已落地、v3 留用

- `engine_pool` 多 session 并发（生产级）——三人模式的 engine 载体；
- `request_user_input` 全链路接入（工具白名单 / Tauri 命令 / event 转发 / prompt 引导）；

- 两个 bundle skill + 解包机制 + eager loading；
- 前端品悟气泡 + 3 按钮 + Fallback 合成。

### 10.2 v3 要新增 / 改造（方案层，不含代码）

1. **品悟独立 engine**：从"同 session 换 persona"升级为独立实例 + 真 system prompt（§3、§8）；
2. **作者-评审 loop 编排**：立账→核账、四信号停止、轮数兜底（§5、§6.2）；
3. **结构化核对**写进品悟 skill（§6.3）；
4. **Boss 三档参与 + 信号灯仪表盘 + 三种召回界面**（§4）；
5. **权限交接状态机**：代理人 ↔ 参谋（§5.4）；
6. **黑板多发言者数据模型**（§3.3）。

### 10.3 这版的根本取舍

> **用通用的"模型 + prompt 流程"覆盖尽量多场景，放弃为特定场景写规则/接外部源换来的"硬兜底"。** 代价是机械/事实盲区靠"结构化核对 + Boss 兜底"而非硬规则，换来的是通用性、简单、可扩展。
