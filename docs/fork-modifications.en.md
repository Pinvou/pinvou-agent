## Merged into the maintenance branch: compaction checkpoint role compatibility

- T7: insert the typed Agent topology checkpoint after the latest real user input and before its assistant/tool chain, including when a compaction summary trails that chain. For Chat Completions, place a structurally recognized current-format summary ahead of its retained round on the wire and merge that summary plus the topology checkpoint into the same user wire message. Quoting the summary marker inside an ordinary user prompt does not trigger reordering. The fix covers only the trailing `tool -> user` that compaction itself creates; the reported provider text was `SSE stream request failed: HTTP 400 Bad Request: response_role: "user"` (SSE lane). Saved history and tool-call/result IDs stay untouched, and the session-pinned system prefix is unchanged.
- Not covered: adjacent real users. After repeated compaction the retained **real** user messages sit next to each other on the wire because compaction dropped the rounds between them (`retained_user_messages` keeps 20k tokens of user messages by default, and `compaction_does_not_merge_unrelated_adjacent_user_messages` pins `[user, user(summary+prompt), assistant, tool]`). This fix deliberately does not merge real user turns - that would change the turn boundaries the model sees - so a route whose template also rejects adjacent `user -> user` still fails after repeated compaction. The only evidence is the trailing-shape provider text above; no customer replay was performed, so the template's tolerance for adjacent **real** users is undetermined. That case needs route-aware wire tests and fixes and stays out of scope here.
- Parent companion: `pinvou3-app`'s model-service error classifier now maps role/template 400s on both lanes - the SSE-wrapped `HTTP 400 ... response_role: "user"` and the non-streaming `Invalid request (400): ...` (`LlmError::InvalidRequest` Display text) - to the request-format card without a retry suggestion. The card copy only states that the request format was rejected, so the uncovered case above cannot mislead users. The classifier matches on text and stays deliberately loose: a 400 body that also contains "server error" wording still lands in the retryable `server` kind, and a quoted JSON-kv form `{"response_role":"user"}` misses the `response_role\s*:` arm and drops back to unclassified. Both edges are registered breadth; tightening either would be a separate change.

### Turn-bound cancel: the host dispatches stops by turn identity (parent-side adaptation, this PR)

- The foundation half is already part of the registered batch: CodeWhale PR #38 (squash `f5c68cab8`, see the commit sequence and the T1 retained-content section) upgrades the shared cancel slot to `TurnCancelSlot { turn_id, token }` and adds the host entry points `EngineHandle::cancel_turn(turn_id, reason, mode) -> bool` (identity check, steer disposition, and token clone completed under the same slot lock) and the terminal-closing `EngineHandle::publish_stop_disposition(reason, mode)` (publishes only the stop disposition, never fires any token).
- Foundation candidate half (added in the review round, closes boundary (3)): `Op::SendMessage` / `Op::EditLastTurn` gain a host submission correlation field `submission_id`, echoed verbatim by that turn's `TurnStarted`; every runtime self-start path (idle sub-agent completion, background shell wake, goal continuation, composer shell command) always echoes `None`; the wire `EventMsg::TurnStarted` carries the same additive field (`serde(default)`, absent by default, backward compatible). The regression `forkguard_turn_started_echoes_submission_id_self_starts_stay_none` pins the echo contract: a host-submitted turn's `TurnStarted` echoes its own token, a self-started turn stays `None`. It landed with #58 as squash `f05b9acfa` (2026-09-17), and the 2026-09-17 batch advanced the published `pinvou3-clean` to `92427bd8d`.
- Parent-side adaptation (this PR; together with the foundation it closes pinvou-agent#254): the `EnginePool::cancel` cancel closure receives the (epoch, observed turn_id, closing) same-source identity snapshot inside the same state-lock critical section of `arm_pending_cancel_and_cancel` and dispatches through the `turn_bound_cancel_action` pure function — a slot match cancels via `cancel_turn_with_mode` (a moved-on slot is skipped wholesale by the foundation, publishing no disposition), and the target turn not yet observed as started (the submit→TurnStarted window) converges with the terminal-closing window on publish-only `publish_stop_disposition`, never firing: inside the window the slot may already hold a self-started follow-up turn's live token whose `TurnStarted` a delayed forwarder has not processed, and firing it is exactly #254; the genuinely pending target is cancelled by the forwarder's turn-bound replay of the `pending_cancel` armed in that same critical section once its `TurnStarted` arrives (dropped wholesale by the foundation identity check if the slot has moved on); the forwarder's `pending_cancel` replay becomes turn-bound and is consumed only when the arriving event echoes the submission token recorded at arming time: the host-submitted paths (user send, multi-agent, eval replay, edit-last-turn) mint `sub-<uuid>` tokens through `Pinvou3Bridge::next_submission_id` and the lifecycle records the token at arming time, so an overtaking self-started turn's `TurnStarted` (no token or a foreign token) can neither consume the replay nor redirect its cancel onto itself, and the submitted turn's own echo delivers the replay turn-bound to exactly that turn (app regression `overtaking_self_started_turn_started_cannot_consume_the_replay`). The consumption gate is the submission token alone: the arming-time epoch is recorded for provenance and does not gate consumption — an unrelated autonomous turn inside the window can run its full start→terminal lifecycle, so the target's own `TurnStarted` arrives newly-active and advances the epoch, and gating on it would reject the exactly-matching echo and silently lose the user's stop (app regression `pending_stop_replay_survives_an_autonomous_lifecycle_before_the_target_starts` drives the started → terminal → target-started forwarder order to pin that sequence). ## T6: swarm rate-limit-adaptive scheduling (append topic)

- Replaces the fixed `Semaphore` launch gate with `DynamicGate` (#43): capacity shrinks at runtime (allowed below the active-holder count; surplus holders finish naturally) and permits hand over pre-counted through a oneshot channel, with cancellation-safe handling on both paths so a lost wakeup cannot occur.
- `RateLimitGovernor` is shared per engine and inherited through the `SubAgentRuntime` derive tree (stamped at the manager's single spawn chokepoint): a 60s sliding window halves capacity at ≥2 rate-limit events or >30% ratio (guarded by an attempts≥2 volume floor), pauses new admissions at ≥4 (capacity 0, in-flight unaffected), additively increases one unit per three consecutive successes (AIMD), releases a pause only when the window drains — external limit changes cannot silently lift it — and a 5s queued-side `recover_if_window_drained` probe prevents a frozen queue when the in-flight fleet finishes without any success signal.
- Retries honor `Retry-After` and otherwise use full-jitter exponential backoff (250ms base, 120s cap) to de-synchronize a fan-out thundering herd; `QuotaExhausted` keeps the existing fatal/checkpoint path; the governor only observes and never delays in-flight calls; configured launch concurrency applies to the live gate immediately through the governor.
- Consumed by the parent's swarm mode (PR #444); the governor itself is generic embedder capability.

## Parent boundary and drift reduction

`pinvou3-app` owns product tool policy, AppMode-to-approval/trust mapping, reasoning effort, owner-event filtering, and scheduled-session creation. Its bridge retains v0.9.12 finite turn/tool limits, read denylist, bubblewrap, MCP OAuth, goal-loop, and telemetry-safe defaults.

Shell task reconciliation prefers the stable `origin_tool_call_id` carried by snapshots and completion events (an upstream v0.9.12 behavior, Hmbown/CodeWhale #5869): the host monitor and the Tauri/Web bridges rewrite the originating tool card first and fall back to command-text matching only for legacy origin-less jobs. An identified terminal root job whose origin card was compacted or reloaded away never appends to the current timeline tail, while running jobs keep a visible synthetic status card (`shell_task_projection.test.mjs`, `forkguard_shell_monitor_assigns_identical_commands_by_stable_origin`).

Origin scope: a shell job's `origin_tool_call_id` is the unique root turn-loop tool call that spawned it; subagent jobs carry only `owner_agent_id` with a null origin and take the origin-less reconciliation paths. Read-only `multi_tool_use.parallel` sub-calls share the wrapper call's origin, but shell tools have `ExecutesCode` and cannot enter read-only parallel, so that sharing never applies to shell jobs. Consumers must preserve the owner distinction and never let one job adopt a card already bound to another job.

Bounded gate-held awaits: four side-effect awaits issued while a session turn gate is held are bounded by `TURN_GATE_AWAIT_TIMEOUT` (5s, issue #255) — the cancel phase-two cascade sends, the shell-cleanup join, the reclaim shutdown sends, and the shell-reclaim finalize. On timeout the side effect is abandoned and logged: an abandoned cascade send is never enqueued (tokio mpsc send is cancel-safe) and every gate-held sender is serialized with the next turn's `SendMessage` on the same turn gate, so no late cancel can be enqueued after it (the argument covers gate-submitted turns; engine-autonomous turns start without the gate and are adopted by the forwarder at `TurnStarted` — a pre-existing window outside the guarantee); a timed-out reclaim finalize keeps finishing in the background with `cleanup_failed` preset conservatively, so the session's active scope can never wedge permanently (rebind and delete reset the registry as the escape); a panicked finalize is reported as not settled and replaced by one fresh detached attempt (the finalize is idempotent), so the terminal never claims a verified-clean shell state from a run that died mid-flight — until a detached finalize settles, the session's next send can transiently fail with the scope-still-active bail and succeeds once it has settled (rebind and delete reset the registry and are immune). Cleanup runs no longer serialize on the turn gate, so overlapping kill ladders and the background worker sweep alike are serialized by a per-registry cleanup gate instead — otherwise concurrent `cleanup_scope_once` passes would double-count `PendingKill.attempts` toward `MAX_KILL_ATTEMPTS` and permanently stop retrying a still-dying job. Undelivered reclaim shutdown ops are re-sent by a detached task that holds no gate, in the original FIFO order with a 60s per-op patience: the engine owns a `tx_op` clone that keeps its ops channel open after the entry is dropped, so its run loop only exits through the normal `Shutdown` path — without the retry the engine task would linger until process exit; if the retry also times out it gives up with a diagnostic, and the lingering engine task is then the doing of the stall itself — a delete/evict that already returned can see the lingering engine's late terminal write land under the removed session directory as orphaned files (harmless: session listing reads only top-level `<id>.json` records, so no ghost session appears). Awaits still unbounded are tracked in #525: the user/eval/resent-message submit sends and the spawn-failure teardown `Shutdown` sends (a new send into an already-wedged engine re-blocks evict/delete), the scheduled turn's whole-turn gate hold and its unbounded sends (pre-existing design), plus the reclaim terminal persistence and the forwarder join, which do not wait on the wedged engine and rely on disk-health assumptions. The behavior tests `forkguard_cancel_holds_turn_lock_boundedly`, `forkguard_bounded_join_reports_panicked_task_as_not_settled`, `forkguard_bounded_join_detaches_task_that_outlives_budget`, `forkguard_reclaim_shutdown_sends_bounded_and_retried`, `forkguard_reclaim_shutdown_retry_gives_up_within_patience`, `forkguard_reclaim_cleanup_failed_preset_clears_on_success`, and `forkguard_background_cleanup_sweep_takes_cleanup_gate` are executed by fork-guard layer 3.

The baseline's net +17,336 lines exceed the +1,500 soft limit, chiefly in Engine state, final dispatch, child-only host profiles, explicit-Skill-root boundaries, and review-requested result-level safety coverage where an app-side mirror would create two unsafe sources of truth. Reduction order is: upstream generic steer and per-turn dispatch policy; upstream Automation ownership/misfire behavior; upstream the execpolicy phase-2 expressiveness and subagent wiring; upstream the T5 archive export as a unit; upstream the T6 rate-limit governor; upstream the GLM-5.3 forced-thinking dialect and BigModel route predicate; make the 100 KiB `FragmentId::Permissions` host budget a configurable upstream fragment limit; migrate the parent to explicit re-export APIs and then narrow the 18-module compatibility facade; finally replace T3 once upstream provides complete static-composer, explicit-Skill-root, and host-profile contracts.
