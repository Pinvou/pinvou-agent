# 品悟银河麒麟 OS 原生适配评估

> 评估日期：2026-07-15
>
> 评估对象：PINVOU 桌面应用（Tauri 2 + Rust + React + DeepSeek-TUI）
>
> 目标系统：银河麒麟桌面操作系统 V10 SPx / V11
>
> 当前结论：技术可行，无需重写为 Qt/GTK；单版本、单架构适配复杂度中等，V11 开明包、严格沙箱、官方认证及全国产 CPU 矩阵会显著提高复杂度。

## 1. 评估背景

品悟当前已具备 Linux ARM64 DEB 发布和 OTA 能力，需要评估其面向银河麒麟桌面操作系统进行原生适配时的技术可行性、工作范围、风险和预计投入。

本评估参考：

- 麒麟软件《银河麒麟桌面操作系统应用开发指导文档》；
- 麒麟软件《银河麒麟桌面操作系统原生开发指导手册》（V11）；
- Tauri 2 Linux/Debian 官方打包要求；
- 品悟当前代码、构建脚本和 Linux 平台实现；
- 仓库已有的 V11 x86_64 安装与启动验证记录。

麒麟 OS 不是单一运行环境。正式立项前必须明确以下目标矩阵：

| 维度 | 可能取值 | 对适配的影响 |
|---|---|---|
| 系统版本 | V10 SPx、V11 | V11 引入不可变系统基座、开明包和更严格的应用隔离 |
| CPU 架构 | AMD64、ARM64、LoongArch、MIPS64、SW64 等 | 每种架构都需要独立构建并验证所有本地二进制依赖 |
| 图形协议 | X11、Wayland/XWayland | 影响 WebKitGTK、输入法、多屏拖拽、全局鼠标和窗口行为 |
| 交付方式 | DEB、开明 Kaiming 包、应用商店 | 影响安装权限、沙箱能力、更新机制和认证流程 |
| 模型部署 | 连接现有 GB10/vLLM、麒麟终端本机推理 | 后者属于单独的算力和推理框架适配项目 |

## 2. “原生适配”的范围定义

“能在麒麟上运行”和“完成麒麟原生适配”不是同一个交付标准。建议将目标分为四级：

### L0：技术兼容

- 安装包能够安装；
- 应用能够启动；
- WebKit 主界面能够正常显示；
- 基本对话能够连接模型并完成一次流式输出。

### L1：产品级兼容

- 当前承诺功能均可用；
- 中文输入、HiDPI、多屏、麦克风、通知等桌面行为正常；
- PDF、OCR、Office、压缩包、网页任务等依赖功能正常；
- 安装、升级、卸载、重装和数据保留流程完整；
- 具备目标架构的稳定构建和回归测试链。

### L2：麒麟原生生态交付

- 支持 V11 推荐的开明 Kaiming 包或麒麟认可的正式分发形式；
- 完成沙箱权限、签名、应用商店和版本更新适配；
- 通过麒麟兼容性、安全性和功能测试；
- 完成“麒麟原生适配认证”及应用分发流程。

### L3：深度系统集成

- 按需使用 KYSDK、UKUI 主题、D-Bus、PolicyKit 等麒麟系统能力；
- 与麒麟通知、系统设置、主题、托盘和安全机制深度融合；
- 针对国产 CPU/GPU/NPU 做性能优化。

本评估建议先完成 L1，再决定是否进入 L2/L3。

## 3. 当前实证基础

仓库已有对 PINVOU 0.5.9 的银河麒麟 V11 x86_64 验证，环境为 KVM/libvirt。已确认：

- DEB 可以安装；
- 应用可以启动；
- WebKit 主界面可以正常显示；
- Debian 12 Bookworm 构建产物最高要求 `GLIBC_2.34`，可在 glibc 2.38 的麒麟 V11 上运行；
- VirtIO 虚拟显卡可正常运行，QXL 图形栈会导致 WebKit EGL 初始化失败；
- 麒麟 V11 安装 DEB 前需要进入维护模式，但应用运行不应长期依赖维护模式；
- 当前仍未完成模型、文件、知识库、工具、工作流、升级等完整产品回归。

详细现场记录见：[麒麟OS-V11适配踩坑记录.md](./麒麟OS-V11适配踩坑记录.md)。

因此，目前已经证明的是 **L0 的安装和界面启动子集**，尚不能等同于 L1 产品级适配或 L2 官方原生认证。

## 4. 当前技术路线判断

### 4.1 不需要重写为 Qt/GTK

品悟当前 Linux 桌面程序是编译后的 Rust ELF，窗口与 WebView 使用 GTK/WebKitGTK，安装包使用标准 Debian 体系。该路线符合银河麒麟的 Linux 应用模型。

麒麟 V11 原生开发手册将桌面应用分为：

- Qt/GTK 原生图形应用；
- Electron/Flutter 等跨平台桌面应用；
- Web 应用；
- AI 应用和系统工具。

Tauri 虽未在手册中单独点名，但与 Electron 同属 Web 技术桌面应用路线，并直接复用系统 GTK/WebKit。因此，原生适配的重点应是构建基线、系统依赖、权限、安全、打包和测试，而不是重写全部界面。

只有在以下明确需求出现时，才需要考虑 Qt/KYSDK 壳层或局部原生组件：

- 麒麟认证或客户规范明确禁止 WebView 框架；
- 必须实现 Tauri/GTK 无法提供的 UKUI 深度能力；
- 必须达到特定国产 GPU 上的渲染性能指标；
- 开明沙箱无法满足品悟的宿主机访问能力，且必须通过系统服务拆分解决。

### 4.2 V10 和 V11 应采用不同交付策略

| 目标 | 推荐交付方式 | 说明 |
|---|---|---|
| V10 SPx | 原生构建的 DEB | 最接近品悟当前发布链，优先完成兼容和认证 |
| V11 兼容版 | 目标基线构建的 DEB | 已验证可安装和启动，但安装需要维护模式 |
| V11 原生生态版 | 开明 Kaiming 包 | 需要额外处理沙箱、权限、依赖和商店更新 |

不建议用一个未经区分的 Linux 安装包同时承诺所有麒麟版本和所有 CPU 架构。

## 5. 当前代码与适配差距

### 5.1 构建基线和 glibc

Tauri Linux 应用依赖宿主系统 glibc。当前开发机直接构建的 AMD64 二进制曾要求 `GLIBC_2.39`，无法在 glibc 2.38 的麒麟 V11 上启动，更无法覆盖 glibc 2.31 的部分 V10 环境。

已有验证证明，在 Debian 12 Bookworm 构建后可把最高 glibc 要求降到 `GLIBC_2.34`。正式构建链需要：

- 固定兼容构建镜像；
- 禁止复用宿主机 `target/`；
- 构建后检查所有 ELF 的架构和 glibc 版本；
- 对每个目标架构分别构建；
- 保留构建镜像、Rust、Node、Cargo.lock 和 package-lock 的版本记录。

### 5.2 WebKitGTK 准入

品悟 Tauri 2 Linux 端依赖 `webkit2gtk = "2.0"`，生成的 DEB 会依赖：

- `libwebkit2gtk-4.1-0`；
- `libgtk-3-0`。

每个目标麒麟版本都必须先确认软件源是否提供 WebKitGTK 4.1。若目标版本只提供 WebKitGTK 4.0，当前 Tauri 2 包不能直接安装。

首轮环境探针应执行：

```bash
apt-cache policy \
  libwebkit2gtk-4.1-0 \
  libwebkit2gtk-4.1-dev \
  libgtk-3-0
```

如果目标系统缺少 WebKitGTK 4.1，优先级依次为：

1. 使用包含所需运行时的开明包；
2. 提升支持的最低麒麟版本；
3. 与麒麟适配中心确认受支持的 WebKit 运行时；
4. 最后才考虑框架降级或替换。

### 5.3 X11、Wayland 和图形栈

当前 release 环境默认设置：

```text
GDK_BACKEND=x11
GTK_IM_MODULE=fcitx
QT_IM_MODULE=fcitx
XMODIFIERS=@im=fcitx
```

同时，多窗口撕离功能依赖 X11 全局鼠标状态，在 Wayland 下会降级。因此需要验证：

- UKUI X11；
- UKUI Wayland + XWayland；
- 中文输入法和候选框位置；
- 高分屏、缩放、多屏和休眠恢复；
- 无边框窗口的拖动、最大化和焦点；
- 麦克风授权和 WebKit `getUserMedia`；
- VirtIO 虚拟机与至少一种物理国产显卡。

虚拟机专用的 Mesa EGL 环境变量不能无条件写入物理机安装包，应通过启动器按环境探测后选择。

### 5.4 多架构本地二进制

品悟不仅包含主 Rust ELF，还包含或调用其他本地二进制。当前已发现：

- `resources/platforms/linux/asr/sense-voice-main` 是 ARM64 ELF；
- 历史 x86_64 包中的 `web-template` 曾混入 ARM64 esbuild；
- fastembed/ONNX Runtime 需要逐架构确认可用性；
- ffmpeg、pandoc、poppler、tesseract、LibreOffice 等系统包需要确认目标架构的软件源支持。

正式构建必须增加“包内 ELF 架构扫描”，至少覆盖：

```bash
find <unpacked-package> -type f -exec file {} \; \
  | grep -E 'ELF|executable|shared object'
```

资源应按 target triple 管理，例如：

```text
sense-voice-main-x86_64-unknown-linux-gnu
sense-voice-main-aarch64-unknown-linux-gnu
```

第一阶段只建议承诺 AMD64 或 ARM64。LoongArch、MIPS64、SW64 等架构应分别立项验证，不能仅因为 Rust 主程序可编译就视为整包可用。

### 5.5 依赖安装与 V11 不可变系统

当前 Linux 端会通过 `pkexec apt-get install` 安装：

- poppler-utils；
- pandoc；
- LibreOffice；
- tesseract；
- p7zip；
- Python；
- ffmpeg 等。

这在传统 DEB 环境中可用，但和 V11 的不可变系统基座、开明沙箱存在冲突。V11 原生生态版需要在以下方案中选择：

1. 将必要依赖打入 Kaiming runtime/depend；
2. 使用纯 Rust 实现或随包二进制，减少系统依赖；
3. 对非核心能力做依赖检测和清晰降级；
4. 由管理员在企业镜像中预装依赖；
5. 禁止应用在沙箱内直接修改宿主系统软件包。

### 5.6 沙箱与 Agent 能力冲突

开明应用默认与宿主机隔离，而品悟的核心能力包括：

- 读取和索引用户工作区；
- 执行 shell、Python、Node 和连接器 CLI；
- 启动 MCP server；
- 调用 xdg-open、ffmpeg、pandoc 等宿主工具；
- 访问麦克风、网络、D-Bus 和凭证存储；
- 监控文件变化；
- 按需管理本地推理服务。

因此 Kaiming 适配的主要技术风险不是“能否打出包”，而是沙箱权限能否完整承载品悟的 Agent 能力。

可选架构：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Kaiming 单体 + 广泛权限 | 改动较小 | 可能不符合商店安全审核，沙箱价值有限 |
| Kaiming GUI + 宿主服务 | 权限边界清晰，适合认证 | 需要设计 D-Bus/Unix Socket 协议和宿主服务生命周期 |
| 认证 DEB | 最大程度保留当前能力 | V11 安装体验依赖维护模式，可能不符合长期生态方向 |
| 功能裁剪版 | 最容易进入沙箱 | 会削弱品悟核心价值，不建议作为主版本 |

建议优先向麒麟适配中心确认开明包的文件系统、子进程、D-Bus 和宿主命令权限边界，再决定是否拆分宿主服务。

### 5.7 超级权限安全整改

当前“超级权限”开关会写入：

```text
<user> ALL=(ALL) NOPASSWD: ALL
```

这相当于为整个用户永久开放无密码 root，属于明显的安全和认证风险。麒麟适配版本应：

- 删除通用 `NOPASSWD: ALL`；
- 为安装更新、安装依赖、启动固定服务分别定义细粒度 PolicyKit action；
- 使用最小权限 helper，禁止接收任意 shell；
- 对所有 root 操作使用固定参数或严格白名单；
- 卸载时清理策略和服务；
- 在 V11 不可变系统上遵守维护模式和系统目录保护规则。

该项不仅是麒麟适配要求，也应回馈当前 Linux 主线。

### 5.8 OTA 与多架构发布

当前 Linux OTA 使用单个 `latest.json`，清单只包含一个包 URL。发布第二个架构时，后上传的清单会覆盖前一个架构，导致另一架构客户端可能下载错误安装包。

应改为以下任一协议：

```text
latest-arm64.json
latest-amd64.json
```

或：

```json
{
  "version": "x.y.z",
  "packages": {
    "arm64": {
      "url": "...",
      "sha256": "...",
      "size": 0
    },
    "amd64": {
      "url": "...",
      "sha256": "...",
      "size": 0
    }
  }
}
```

另外：

- DEB 版本可以继续使用品悟自有 OTA；
- Kaiming/商店版优先采用商店更新；
- 两种渠道应使用不同更新策略，防止 Kaiming 应用在沙箱内调用 `apt-get --reinstall`；
- 更新包下载后应校验架构、包名、版本和 SHA256，而不仅校验文件摘要。

### 5.9 本地模型边界

品悟当前本地 vLLM 一键启用逻辑明确针对 MegaCube/GB10 出厂环境：

- 固定读取 `/opt/.h3c/packages/vllm/`；
- 依赖预装 Docker 镜像、模型和启动脚本；
- 通过 systemd 启动 NVIDIA GB10 推理服务。

因此麒麟适配第一阶段建议定义为：

> 银河麒麟终端运行品悟客户端，通过局域网连接现有 GB10/vLLM 或企业内网推理服务。

如果要求在飞腾、鲲鹏、龙芯或国产 NPU 的麒麟终端上本机运行 Qwen3.6-35B，则需要单独评估：

- 推理框架和算子支持；
- 驱动、容器和设备权限；
- 模型格式和量化；
- 内存容量和性能目标；
- 各硬件平台的监控 API。

该工作量通常远高于桌面客户端适配，不应混入第一阶段范围。

## 6. 建议实施计划

### 阶段 A：目标环境冻结与兼容探针

预计：3～5 个工作日。

- 确认麒麟版本、SP、CPU、GPU、X11/Wayland；
- 获取物理机或官方云适配环境；
- 检查 WebKitGTK、GTK、glibc 和依赖包；
- 安装已有兼容 DEB；
- 验证启动、输入法、模型连接、文件访问和麦克风；
- 输出环境探针报告和 blocker 清单。

阶段出口：确认当前 Tauri 2 路线在目标环境无框架级阻断。

### 阶段 B：单架构 L1 产品级适配

预计：2～4 周。

- 固定兼容构建镜像；
- 修复包内跨架构二进制；
- 统一 `pinvou3` 命令和 Desktop Entry；
- 完成图形栈、输入法、多屏和麦克风适配；
- 核实或重构系统依赖；
- 改造多架构 OTA；
- 完成完整功能回归；
- 输出安装包、构建说明和验收报告。

阶段出口：目标版本、目标架构上的功能和升级流程达到发布标准。

### 阶段 C：权限与安全整改

预计：2～4 周，可与阶段 B 部分并行。

- 移除全局 sudo 免密；
- 引入 PolicyKit/最小权限 helper；
- 收紧 Tauri CSP 和外部 URL/命令边界；
- 完成敏感文件、凭证和日志检查；
- 完成静态扫描、依赖漏洞和包内容审计。

阶段出口：具备进入政企部署和官方认证的安全基础。

### 阶段 D：V11 开明包与官方认证

预计：3～6 周，不含官方审核排队时间。

- 获取 Kaiming base/runtime 和开发工具；
- 编写 Kaiming manifest；
- 设计文件、网络、麦克风、D-Bus、子进程权限；
- 必要时拆分宿主服务；
- 完成签名、安装、卸载和更新；
- 运行麒麟兼容性检查工具；
- 提交产品适配申请、测试材料和认证申请。

阶段出口：完成麒麟认可的原生生态分发和认证。

### 阶段 E：扩展第二架构及国产 CPU 矩阵

预计：

- AMD64/ARM64 第二架构：额外 2～4 周；
- LoongArch 等新架构：每架构单独评估，完整矩阵预计 3～6 个月以上。

阶段出口：每个承诺架构都有独立产物、硬件回归和发布渠道。

## 7. 工作量评估

以下估算假设模型继续使用现有 GB10/内网 vLLM，且能够获得目标麒麟环境：

| 目标 | 预计投入 | 复杂度 |
|---|---:|---|
| V11 x86_64 安装和主界面启动 | 已完成初步验证 | 低 |
| 单版本、单架构 DEB 产品级适配 | 2～4 周 | 中 |
| 单架构权限整改 + 完整安全回归 | 2～4 周 | 中高 |
| V11 Kaiming + 应用商店 + 原生认证 | 合计约 6～10 周 | 中高 |
| V10/V11 + AMD64/ARM64 双架构 | 约 8～12 周 | 高 |
| 覆盖龙芯、MIPS、申威等完整矩阵 | 3～6 个月以上 | 高且存在依赖不确定性 |
| 麒麟终端本机运行 35B 模型 | 单独立项 | 极高 |

上述工期不包含：

- 麒麟官方审核排队；
- 第三方闭源依赖等待厂商提供目标架构版本；
- 国产 NPU 推理框架适配；
- 客户私网、国密或专用安全软件的定制要求。

## 8. 适配测试矩阵

### 8.1 安装与生命周期

- [ ] 维护模式下安装；
- [ ] 恢复正常模式后运行；
- [ ] 首次启动和二次启动；
- [ ] 覆盖升级；
- [ ] 降级保护；
- [ ] 卸载和重装；
- [ ] 用户数据保留；

## 9. 主要风险

| 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|
| 目标系统缺少 WebKitGTK 4.1 | 中 | 高 | 首周探针确认；使用 Kaiming runtime 或提高最低版本 |
| Kaiming 沙箱无法承载宿主命令和文件访问 | 高 | 高 | 提前与麒麟确认权限；必要时拆分宿主服务 |
| 包内混入错误架构 ELF | 已发生 | 高 | 构建后自动扫描全部 ELF 和 Node native binary |
| 新系统构建导致 glibc 过高 | 已发生 | 高 | 固定 Debian 12/目标麒麟兼容构建基线 |
| 国产 GPU 驱动与 WebKit EGL 冲突 | 中 | 高 | 物理机矩阵；按环境选择渲染后端，保留软件渲染降级 |
| 全局 sudo 免密阻碍认证 | 高 | 高 | PolicyKit + 最小权限 helper |
| 依赖包在私网或某架构不可用 | 高 | 中高 | 自包含、纯 Rust 替代或管理员预装 |
| 单一 OTA 清单覆盖错误架构 | 高 | 高 | 分架构清单和包架构校验 |
| 把客户端适配误解为本机模型适配 | 中 | 高 | 明确第一阶段模型仍由 GB10/内网服务提供 |

## 10. 推荐决策

### 推荐路线

1. 保留 Tauri + Rust + React 技术路线，不进行 Qt 全量重写；
2. 以一个明确的客户目标版本和 CPU 架构先完成 L1；
3. 没有客户架构约束时，优先选择当前最有交付价值的 AMD64 或 ARM64，不同时承诺全部国产 CPU；
4. 将构建基线、多架构资源、OTA 和超级权限整改先回馈 Linux 主线；
5. 在进入 Kaiming 开发前，先向麒麟适配中心确认沙箱权限是否支持品悟的 Agent 能力；
6. 第一阶段继续连接现有 GB10/内网 vLLM，不把国产硬件本机推理纳入桌面适配范围；
7. 完成 L1 验收后，再决定走“认证 DEB”还是“Kaiming GUI + 宿主服务”。

### 不推荐路线

- 因“原生”二字直接重写为 Qt；
- 用 Ubuntu 上的现有包直接申报所有麒麟版本；
- 在没有真实硬件验证时承诺龙芯、申威、MIPS 全支持；
- 为了进入沙箱而删除品悟的文件、工具和 Agent 核心能力；
- 继续把 `NOPASSWD: ALL` 带入政企或认证版本；
- 用一个 `latest.json` 同时发布多个 CPU 架构。

## 11. 验收标准

单版本、单架构 L1 适配完成应至少满足：

- 目标麒麟系统和架构已明确记录；
- 安装包在兼容基线中可重复构建；
- 包内全部 ELF 架构正确；
- 主程序 glibc 要求不高于目标系统；
- 安装、启动、升级、卸载通过；
- 完成第 8 章测试矩阵中的适用项目；
- 无全局 sudo 免密；
- OTA 不会跨架构下载错误包；
- 物理机至少完成一轮核心回归；
- 输出构建记录、测试报告、已知限制和用户安装说明。

L2 原生生态交付还应满足：

- 开明包或麒麟认可的正式分发包可重复构建；
- 沙箱权限经过最小化设计并通过审核；
- 更新机制符合分发渠道要求；
- 兼容性、安全和功能测试通过；
- 完成麒麟原生适配认证或取得对应测试结论。
