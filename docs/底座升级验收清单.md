# 底座升级验收清单(CodeWhale / CodeWhale sync gate)

> **每次升级底座(sync 上游新 release)必须全过本清单才算完成。** 这是硬 gate,不是建议。
> 配套:`docs/fork-policy.md`(sync 流程/策略)、`docs/fork-modifications.md`(fork 现状清单)、`scripts/fork-guard.sh`。
> 来源:v0.8.60 sync(2026-06-15)实测固化——每一条都对应踩过的坑,删任何一条前先看「防什么」。
>
> 用法:升级时把下面 **L0→L3 + 签收表**逐项跑过,签收表全勾才合并 / 更新父仓 gitlink。

## L0 — 编译(必过,最先)

| # | 命令 | 通过标准 |
|---|---|---|
| 0.1 | `cargo check -p codewhale-tui --lib --bins` | 0 error |
| 0.2 | `cargo check -p codewhale-tui --lib --tests` | 0 error(测试代码也编译——上游新增测试常构造 pinvou3 扩展了字段的 struct,缺字段编译错) |
| 0.3 | `cargo check --manifest-path pinvou3-app/src-tauri/Cargo.toml --lib` | 0 error(app bridge 依赖 submodule API,暴露 EngineConfig/Op 新字段) |

> **防什么**:merge 后最常见的是 struct 加字段 / API 改签名,编译能抓绝大部分。`--tests` 和 app crate 单独 check 不能省(v0.8.60 的 sidebar.rs 测试、bridge 5 新字段、dump bin 2 新字段都是这层抓的)。

## L3 — 回归专项(自动化抓不到,每次必手查)

> 这些是 dump/编译/单测**都抓不到**的隐形回归,上游每个大版本都可能引入新的一种。每次 sync 必逐条过。

| # | 查什么 | 怎么查 | 防什么(实例) |
|---|---|---|---|
| 3.1 | **hook 决策协议** | 读 `turn_loop.rs::fold_tool_call_before_results`,确认 deny 脚本(`deny_sensitive_paths.sh`)退出码契约仍成立 | **v0.8.60 Hooks v2** 把 hard-deny 从「非零」改成只认 `exit_code==2`,旧 `exit 1` 静默失效=敏感目录/sudo 硬墙失灵 |
| 3.2 | **deferred 工具激活与 Hidden 隔离**(结果式守护) | 跑 `forkguard_yolo_tool_search_only_activates_authorized_deferred_tools`：断言首轮只有核心工具与唯一 `tool_search` 入口，普通 native/MCP 为 deferred，Hidden 工具既不能搜索也不能从 unavailable fallback 泄漏，搜索仅激活命中的授权工具；再跑宿主额外工具全模式回归 | 防止上游 activator 改名、硬注入或 fallback 新增路径后绕过三态工具面；单靠 ToolSpec 名单差集抓不到动态注入和兜底泄漏 |
| 3.3 | **per-turn 注入** | `grep -rn "runtime_prompt\|messages.push" turn_loop.rs engine.rs`;新增的 transient 注入要 gate | dump 只抓 system prompt,抓不到每请求注入的 transient 消息(runtime_prompt tag / goal continuation) |
| 3.4 | **工具集合盘点**(结果式守护) | 主查 `forkguard_blocklist_golden`(Hidden 精确名单漂移即 fail 并打印缺/多项→逐项确认)；辅以目录一致性测试和新旧 `ToolSpec::name()` 集合差集 | 上游新增 model-facing 工具默认进入 Deferred，要确认是否应升为 Direct 或降为 Hidden；动态注入工具不在 ToolSpec 名单里，靠 3.2 的最终目录/搜索行为守护 |
| 3.5 | **lib.rs 模块同步** | `git diff <old>..<new> --diff-filter=AD -- crates/tui/src/` 看模块增删 → 同步 `pub mod` | 上游加模块漏 `pub mod`=app 用不到;删模块留孤儿 `pub mod`=编译错(v0.8.60 `prompt_persist` 删除) |
| 3.6 | **EngineConfig/Op/PromptSessionContext 新字段语义** | 编译会逼你填,但要**判断 GUI 该填什么值**(透传 default 还是定制) | v0.8.60 verbosity/goal_*/interactive_launch_limit 等 GUI 透传 default;漏判会拿到错误默认行为 |
| 3.7 | **同名 API 语义分叉** | 上游新实现的同名函数/字段,**逐字段比对语义**(非冲突也非干净 harvest) | v0.8.57/60 composer `effective_static_prompt_composer` vs pinvou3 `static_prompt_composer`——同语义不同名,merge 取上游名要对齐 |
| 3.8 | **auto-compact 触发不倒置**(结果式) | 跑 `forkguard_compaction_threshold_below_emergency_all_windows`(pinvou3 T 换算**对拍底座 `context_input_budget_for_route` 的 E**,跨仓一致)+ `forkguard_compaction_128k_scenarios`;确认 128K/24K 得 `T=45648`、256K/24K 得 `T=133029`，且 route 同时携带 context/output limits | pinvou3 曾**镜像**底座 500K/262144/output 预留/`E=W−O−1024`,上游改这些 pinvou3 编译不报错却**静默倒置**。v0.9 对未知 wire alias 的静态 4K output fallback 还会把 T 错抬高；现在由 SavedModel route profile 提供部署事实，derive 直接调用底座 budget，显式 output 优先于模型名兼容 fallback |
