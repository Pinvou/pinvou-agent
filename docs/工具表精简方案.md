## 1. 背景

### 1.1 现状问题

底座 DeepSeek-TUI v0.8.37 Yolo 模式向 LLM 暴露 **~62 个工具**（含 todo 8 变体、git 5 个、agent/task/rlm/pr 状态管理 23 个、pandoc/OCR/视觉 3 个、各类元工具），schema 总长 ~60-90KB。

pinvou3 实际场景（旅行规划/文档总结/翻译润色/数据分析/代码辅助）只需要 **~15 个核心工具**，其余 47 个工具：
- pinvou3 GUI 单 session 设计上根本不需要（task 持久化/agent 子代理/rlm REPL）
- 或被同等能力工具覆盖（git_* 可用 `exec_shell git`，patch 类可用 edit_file）
- 或本就是 legacy 兼容别名（todo_* 是 checklist_* 的 alias）

### 1.2 量化代价

`docs/验证报告-qwen3.6-deepseek-tui.md` §2 任务 1 实证数据：

| 同一翻译任务 | 工具数 | 请求 body | 耗时 |
|---|---|---|---|
| `exec`（无工具暴露） | 0 | 91 字节 | **1.5s** |
| `exec --auto`（85 工具暴露） | 85 | 119 KB | **19s** |

**10× 慢的根因是 119KB 工具 schema 的 prefill**，与模型推理无关。Qwen3.6 自身在 5 个核心 agentic 任务上 100% 完成率、参数准确率 ~100%（验证报告 §3.1）——瓶颈在工具表大小，不在模型能力。

### 1.3 目标与实测

| 指标 | 验证报告基线 | L1.5 实测 |
|---|---|---|
| LLM active 工具数 | 85（exec --auto 路径） | **22 + 4 advanced**（code_execution / js_execution / tool_search × 2 底座硬塞） |
| tools schema 字节 | ~119KB | **~19-20KB** |
| 翻译任务首响 | 19s | **8s（58% 缩短）** |
| total tool catalog | 76（pinvou3 实际注册数） | 83（blocklist 通过 defer 隐藏 68 个） |

**8s 不到 ≤5s 目标的原因**：剩余开销不在工具表（已砍干净），来自 INSTRUCTIONS_MD（126 行）+ system prompt 模板的 prefill，约占 4-5s。继续优化需精简 prompt 或 vLLM 端 chunked prefill 调优，非工具表改动。

## 2. 决策：选 L1.5（blocklist 隐藏）

### 2.1 三个候选

| 方案 | 操作 | 工具仍注册 | 工具仍可达 | LLM schema 可见 | 跟上游 rebase 摩擦 |
|---|---|---|---|---|---|
| **L1** `defer_loading=true` ×N | 改 22 个 ToolSpec impl 各加 1 行 | ✅ | ✅（tool_search 可激活） | ❌ | 极低（不碰 tool_setup） |
| **L1.5** blocklist | 新增 1 个文件 + registry.rs 改 1 行 | ✅ | ✅（tool_search 可激活） | ❌ | 极低（不碰 tool_setup） |
| **L2** registry 不注册 | 改 tool_setup.rs ~30 行 | ❌ | ❌ | ❌ | 中（上游改 with_agent_tools 要 reconcile） |

### 2.2 选 L1.5 的理由

- **集中可读**：所有被屏蔽工具在一个 `pinvou3_blocklist.rs` 文件，pinvou3 偏好的单一真相点
- **rebase 友好**：不动 `tool_setup.rs` / `registry.rs::with_agent_tools` / 各 ToolSpec impl，上游高频改动区域零冲突
- **可逆**：改 blocklist 常量即可恢复/调整
- **保留按需暴露路径**：工具仍在 registry，未来若做 `tool_search` 动态激活（如开发场景偶尔用 git_log）blocklist 改语义即可
- **改动面最小**：~35 行 fork patch，一个 commit

### 2.3 不选 L2 的代价

L2 直接砍 `tool_setup.rs` 的 builder 链虽然意图最清晰，但：
- 上游 `with_agent_tools` 每次新增 `.with_*()` 调用，我们的 patch 都要决定要不要跟进
- 砍掉的工具完全不可达，未来想做 tool_search 按需激活要回滚改动
- pinvou3 specific 改动放在上游约定的 setup 入口，跟"分离 embedder 偏好与底座结构"的设计原则相违

## 4. 实施方案

### 4.1 四处改动（实测后修正）

```
新增  crates/tui/src/tools/pinvou3_blocklist.rs               ~50 行（含 18 个漏砍补全）
改    crates/tui/src/tools/mod.rs                             +1 行
改    crates/tui/src/tools/registry.rs:231                    改 1 行（防御性，捕获 build_api_tools 路径）
改    crates/tui/src/core/engine/tool_catalog.rs              +20 行（核心修复 + active count trace）
                                                      总计:   ~70 行
```

**实测教训**：仅改 `registry.rs::build_api_tools` 不够——底座 `tool_catalog::apply_native_tool_deferral` 会在 Yolo 模式下用 `should_default_defer_tool` 重新覆写所有 native 工具的 `defer_loading=false`，把我们的设值抹掉。必须同时在 `should_default_defer_tool` 函数最前加 blocklist 检查，让它优先于所有 mode-specific 短路逻辑。

### 4.2 关键代码

**新增 `pinvou3_blocklist.rs`**（结构示例）：

```rust
//! pinvou3 工具默认隐藏清单。
//!
//! 列在此处的工具仍然注册进 ToolRegistry，但 `to_api_tools()` 喂给 LLM 时
//! 标记 `defer_loading=true`，模型默认看不到。未来若做 `tool_search` 按需
//! 激活，工具本身仍可达，仅默认对模型隐藏。
//!
//! 维护要点：上游加新工具时检查是否需要列入（见 docs/工具表精简方案.md §6）。

pub const PINVOU3_HIDDEN_TOOLS: &[&str] = &[
    // 状态管理（pinvou3 GUI 不需要持久化/子代理/REPL/目标跟踪）
    "task_create", "task_list", "task_read", "task_cancel",
    "task_gate_run", "task_shell_start", "task_shell_wait",
    "pr_attempt_record", "pr_attempt_list", "pr_attempt_read", "pr_attempt_preflight",
    "agent_open", "agent_eval", "agent_result", "agent_cancel",
    "agent_close", "agent_list", "resume_agent", "delegate_to_agent",
    "rlm_open", "rlm_eval", "rlm_configure", "rlm_close",
    "create_goal", "get_goal", "update_goal",
    // git（用 exec_shell git 替代；status/diff 已释放）
    "git_log", "git_show", "git_blame",
    // patch/fim（edit_file 已够；revert_turn 已释放）
    "apply_patch", "fim_edit",
    // 附件预处理（移到 bridge；image_analyze 已放出）
    "pandoc_convert", "image_ocr",
    // todo 兼容别名（保留 checklist_*）
    "todo_write", "todo_add", "todo_update", "todo_list",
    // 元工具（diagnostics 已释放）
    "multi_tool_use.parallel", "note",
    "validate_data", "run_tests",
    "handle_read", "retrieve_tool_result", "project_map",
    "recall_archive", "review", "notify", "remember", "web_run",
];

#[inline]
pub fn is_pinvou3_hidden(name: &str) -> bool {
    PINVOU3_HIDDEN_TOOLS.contains(&name)
}
```

**改 `registry.rs::build_api_tools`** (第 231 行)：

```rust
defer_loading: Some(
    tool.defer_loading() || pinvou3_blocklist::is_pinvou3_hidden(tool.name())
),
```

**改 `tool_catalog.rs::should_default_defer_tool`**（关键修复，line 32）：

```rust
pub(super) fn should_default_defer_tool(name: &str, mode: AppMode) -> bool {
    // pinvou3 L1.5: blocklist 优先于所有 mode-specific 逻辑
    if crate::tools::pinvou3_blocklist::is_pinvou3_hidden(name) {
        return true;
    }
    if mode == AppMode::Yolo {
        return false;
    }
    // ... 上游原逻辑
}
```

**`tool_catalog.rs::apply_native_tool_deferral` 加 active count trace**（漂移检测用）：

```rust
let active: Vec<&str> = catalog.iter()
    .filter(|t| !t.defer_loading.unwrap_or(false))
    .map(|t| t.name.as_str())
    .collect();
tracing::info!(
    target: "pinvou3.tool_catalog",
    mode = ?mode, active_count = active.len(),
    deferred_count = catalog.len() - active.len(),
    total = catalog.len(), active = ?active,

```

## 6. 后续演进（依赖项）

### 6.1 附件预处理 pipeline（决策 4）

`pandoc_convert / image_ocr / image_analyze` 三个工具的真正归宿不是 blocklist，而是 **bridge 层附件预处理**：

```
当前: 用户拖 docx → read_file 二进制乱码 → 模型说"让我 pandoc_convert" → 调工具 → 转完再读
改后: 用户拖 docx → bridge 检测 mime → 自动 pandoc → 转好的 markdown 嵌进 user message
```

实施位置：`pinvou3-app/src-tauri/src/bridge/` 加附件 pipeline。
工期：1-2 天。
收益：UX 直接拿数据 + 模型 0 工具调用 + 节省 5-10k token/turn。

### 6.2 视觉能力补足

Qwen3.6 无原生视觉。短期方案：tesseract OCR 在附件 pipeline 内做。
长期方案：GB10 同机起小视觉模型（Qwen-VL-Chat 7B / InternVL2-2B）由 vLLM 并存，bridge 自动 caption。

### 6.3 workflow 编排阶段重启用 subagent

`agent_*` 8 个工具现在 blocklist 屏蔽，但 workflow 编排阶段会重新上线——届时：
- workflow 引擎调 subagent（pinvou3 后端编排，不是模型直接调）
- 或暴露给模型一个简化别名 `delegate(...)`，背后 wrap agent_open

具体路径等阶段 D 之后开始讨论。

## 8. 2026-07-03 全量复核 + 实测（当前 HEAD / v0.8.65）

### 8.2 ★ 头号发现：`tool_search` 门控失效（实测确认的 bug）

**现象**：v0.8.65 上游把 tool_search 从双工具（`tool_search_tool_regex/bm25`）折叠成**单工具 `tool_search`**。`ensure_advanced_tooling`（`tool_catalog.rs:312`）的注入门控改用单名 `TOOL_SEARCH_NAME="tool_search"`，但 `PINVOU3_HIDDEN_TOOLS`（`pinvou3_blocklist.rs:117-118`）**仍停留在双旧名**，没有裸 `"tool_search"`。

**判定链**：`is_pinvou3_hidden("tool_search")` = false → 门控 `&& !false` 放行 → push `tool_search`，`defer_loading: Some(false)`（`tool_catalog.rs:340`，**首轮即可见**）。生产 `tool_whitelist: None`（`bridge/mod.rs:775`）→ `apply_tool_whitelist` no-op，**无兜底**。

**端到端实测**（2026-07-03，改回归测试断言为精确名 `== "tool_search"` 跑真实 `ensure_advanced_tooling(Yolo)`）：
```
test forkguard_tool_search_not_injected_blocks_deferred_activation ... FAILED
catalog=["read_file", "web_search", "code_execution", "js_execution", "tool_search"]
```
→ **确认注入**。且连带把 deferred 的 `code_execution` / `js_execution` 一起带进 catalog（它俩 defer=true 首轮不可见，但可被 tool_search 激活）。

**危害**：模型可 `tool_search` 搜索并 `maybe_activate_requested_deferred_tool`（`tool_catalog.rs:737`）**激活任意被 blocklist defer 的工具**（agent_spawn/delegate_to_agent/rlm_*/git_log/apply_patch/finance/code_execution…）→ 整个 pinvou3 blocklist 隔离被绕过 → 前端不认识这些工具，渲染成裸 JSON。历史 session 已见一次 `tool_search(query="present_artifact")` 真实调用（发生在 sync 前双名可拦时期，但印证模型确实会用它）。

**守护为何没抓住**：
- fork-guard.sh:41 指纹 `is_pinvou3_hidden(TOOL_SEARCH_NAME)` 只验证「这行 gate 代码还在」，不验证「名字对得上」→ sync 改单名后指纹仍命中，静默放过。
- 回归测试 `forkguard_tool_search_not_injected_*` 断言查 `starts_with("tool_search_tool")`，而注入名是 `"tool_search"`（`"tool_search".starts_with("tool_search_tool")` 恒 false）→ **断言恒真通过**，给虚假保证。
- `docs/fork-modifications.md:18/40` 声称「tool_search 已禁用」→ **与实测不符，待更正**。

**修复方案（待决策执行，一个 bundle）**：
1. `PINVOU3_HIDDEN_TOOLS` 加裸名 `"tool_search"`（保留双旧名做前向兼容）→ 门控即拦住，catalog 不含。
2. 测试断言改 `== "tool_search"`（或 `.contains("tool_search")`），恢复真实保护。
3. fork-guard 指纹升级：不只验证 gate 代码在，改为断言「跑 `ensure_advanced_tooling(Yolo)` 后 catalog 不含 tool_search」。
4. 更正 `fork-modifications.md` C2 节。
5. 走 fork patch 流程（同 PR 带指纹 + 更新 fork-modifications，见 CLAUDE.md fork 约束）。

### 8.3 纯噪音：`list_mcp_resources` / `list_mcp_resource_templates`（实测三重坐实）

注入条件（`mcp.rs:2496`）：**只要 mcp.json 非空就无条件注入**，与有无 resources 无关。而 pinvou3 所有 MCP server 都 tools-only：实测 4 个 server（present_artifact / iwencai / gongwen / weather）`resources/list` 全部返回 `-32601 method not found`。→ 这两个元工具对 pinvou3 **永久空转**（模型调用只得空/报错），52 session 零调用。
- ⚠️ 它俩是 **MCP 元工具，不走 native blocklist**（blocklist 只 gate registry native）。隐藏需改 `mcp.rs:2496` 注入条件为「有 resources/templates 才注入」，或在 `apply_mcp_tool_deferral` 加 gate。
- 这其实是**通用优化**（有 server 但零 resources 时不该塞 list 工具），可顺手提上游 PR。

### 8.5 真实调用频率（52 session / 34 个有工具调用 / 23 个不同工具被用过）

**高频必保**：exec_shell(28) present_artifact(25) load_skill(17) write_file(16) read_file(16) agent_open(11) agent_eval(11) web_search(7) kb_search(3)。
**当前暴露但 0 调用**，分两类：

| 类型 | 工具 | 处置 |
|---|---|---|
| 🔴 零调用 + 场景冗余 | `list_mcp_resources`×2、`git_status`、`git_diff`、`diagnostics`、`revert_turn` | 隐藏候选（list_mcp_* 已可直接砍；git/diag/revert 见盲区） |
| 🟡 零调用 但核心能力（**不可删**） | `edit_file`、`image_analyze`、`agent_close`、`grep_files`、`append_file`、`checklist_add`、`checklist_list` | **样本盲区**——见下方「用户复核撤销」 |

**用户复核撤销（2026-07-03，逐个核对工具 description 后从隐藏候选移除）**：
- **`grep_files`**：搜文件**内容**（regex，"instead of `grep -r`/`rg`"），与 `file_search`（搜文件**名**，"instead of `find -name`"）不重叠。隐藏后搜内容只能退回 `exec_shell grep`（小模型易错、慢、不尊重 gitignore）。**保留**。
- **`append_file`**：大产物分块写（≤16KB/块，避免 SSE 超时）；且 `write_file` 描述**主动引导** "for larger artifacts… then call append_file for chunked additions" → 隐藏它会让模型调不存在的工具。零调用=这批 session 无超 64KB 产物。**保留**。
- **`checklist_add`/`checklist_list`**：`update_plan` 描述明确 "checklist_write for primary Work progress; update_plan… not duplicate checklist items" → 两者不同层，plan 顶不了 checklist。内部砍收益小、风险=小模型清单管理变难。**四件套全保留**。

> **盲区纪律**：0 调用 ≠ 冗余（见 `[[prompt_ablation_methodology]]` / `[[feedback_test_behavior_not_satisfy_test]]`）。频率只作信号；真隐藏 🟡/纠结项前，对决策选定的候选跑针对性消融（去工具 A/B 看任务完成率），别盲跑一批（GB10 易卡，`[[vllm_backend_instability_under_load]]` CONC=2 才稳）。
> 健康度旁证：`government-writing()`×3（input 空，首轮就漂）= 技能名被当工具名直调的漂移，应为 `load_skill(name=…)`；与 blocklist 无关，归工具调用漂移专题。
