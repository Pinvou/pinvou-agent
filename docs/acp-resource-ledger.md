# ACP 运行时资源账本

## 目的

ACP Agent 由 Pinvou 启动的外部进程树承载。现有 30 分钟空闲回收能清理长期不用的运行时，但不能回答短时间多会话场景究竟消耗了多少内存，也不能证明某个固定会话上限适合不同设备和 Agent。

本账本先建立跨平台观测事实，不参与会话准入、限流或回收。只有取得 Linux、macOS、Windows 以及 Codex、Claude、Kimi 的真实样本后，才设计资源压力策略。

## 采样口径

- Pinvou 在创建 ACP runtime 时登记自己直接启动的根 PID。
- 随 ACP 池空闲巡检（每 5 分钟一轮）扫描一次系统进程表，把根进程及其后代归入同一 runtime。
- 只聚合常驻内存 RSS 和进程数量，不读取或记录命令行、环境变量、工作目录、会话 ID、prompt、Token 或凭证。
- 最近窗口最多保留 180 个 RSS 样本，计算当前值、P95、生命周期峰值和进程数峰值。
- RSS 变化达到 10% 或 16 MiB、进程结构变化，或者距上次记录达到 15 分钟时，写入 `~/.pinvou3/logs/codex-acp.log`。
- 池内没有常驻 runtime 时不采样，也不写日志。
- 采样在 blocking 线程执行；失败只跳过当前轮次，不影响 Agent 请求。
- Linux 下关闭 sysinfo 的 `/proc` 文件句柄缓存，避免资源账本自身长期占用大量文件描述符。

诊断事件为 `resource:acp_sample`，字段如下：

| 字段 | 含义 |
|---|---|
| `resident_runtimes` | 池中仍登记的 ACP runtime 数量 |
| `sampled_runtimes` | 本轮在系统进程表中成功找到的 runtime 根数量 |
| `process_count` | 所有已归属进程树的进程总数 |
| `rss_bytes` | 所有已归属进程树 RSS 之和 |
| `p95_rss_bytes` | 最近 180 个聚合 RSS 样本的 P95 |
| `peak_rss_bytes` | 当前应用生命周期内观测到的聚合 RSS 峰值 |
| `peak_process_count` | 当前应用生命周期内观测到的进程数峰值 |
| `roles` | 按 Codex、Claude、Kimi 聚合的 runtime 数、进程数和 RSS |

RSS 是各进程 resident set 的加总，共享页可能被重复计算；它适合比较趋势和制定保守预算，不等同于操作系统层面的唯一物理内存占用。脱离原进程树并被系统重新托管的后代无法继续归属；已退出的 runtime 在被空闲回收移除前，其根 PID 若被系统复用也可能短暂错误归属。后续容量决策必须保留这些限制。

## 本地采样开销基线

2026-09-30 在 Linux ARM64 开发机上，用真实父子测试进程连续执行六轮全进程表采样：

| 指标 | 结果 |
|---|---:|
| 子进程归属正确率 | 6/6 |
| 单轮耗时范围 | 7.2–71.3 ms |
| 按最慢值折算的单轮墙钟占比 | < 0.12%（巡检间隔越长占比越低） |

该结果只证明采样开销和进程树归属，不代表 ACP runtime 的实际内存收益。引入账本前没有 ACP 进程树 RSS 数据；引入后可以获得统一口径的当前值、P95 和峰值，但不会自动降低内存。

## 容量策略的后续验收

下一阶段至少采集以下场景：

1. 每种 Agent 分别保持 1、4、8、16 个空闲 runtime；
2. 9 个以上会话循环切换，记录启动耗时和恢复成功率；
3. 多个进行中 turn、等待权限和配置同步同时存在；
4. 低内存与高内存设备上的系统可用内存、ACP RSS P95 和峰值；
5. runtime 正常退出、崩溃、PID 消失和子进程重新托管。

容量策略必须满足：

- 不静默中断进行中的 turn 或用户交互；
- 不把不支持 `session/load` 的 runtime 当作可无损恢复对象；
- 不以固定会话数量代替真实资源成本；
- 压力不足时不制造冷启动抖动；
- 压力确实存在且无法安全回收时，返回明确、可恢复的容量状态；
- 阈值注明设备、平台、Agent、样本数、P95 和峰值依据。
