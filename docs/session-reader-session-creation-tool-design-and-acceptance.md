## 1. Background and goal

The session model previously could only message **existing** sessions (`send_message_to_session`); it could not create new ones. Goal: from **any session**, the model can create a new session through a builtin tool (optionally attaching a first message that starts it immediately), completing the delegation chain "open a session to do X and report back".

## 2. Design decision record

| Decision | Outcome | Rationale |
|---|---|---|
| Ownership | session-reader family (contract §2 "one family = one server") | Session-domain writes belong to the session family; `send_message_to_session` is the precedent; app-automations is the scheduling-automation family |
| Tool shape | A single L1 tool `create_session`, `first_message` as an optional parameter | Contract §4.2 prefers one tool + mode; no need to split create / create_and_chat |
| Focus semantics | **Never `set_active`** | A tool-created session appears silently in the list (`session:list_changed` refreshes both ends automatically) and the user opens it themselves; this is the one deliberate divergence from the Tauri command's default |
| Inheritance semantics | Always "inherit app defaults, not the caller's state" | Model = the app's new-session default (`default_model_for_new_session`), overridable by an explicit `model_id` (must name a saved model; unknown ids are rejected); workspace = app default (`bridge.workspace`), bindable by an explicit `workspace_path` (absolute + existing directory, canonicalized before spooling — review round-3 M2); mode/persona/knowledge sets take fresh defaults. Reusing `create_session_record` semantics comes for free — zero new semantics |
| First message | Becomes the new session's opening **plain-text** user turn (`deliver_messaging_turn`), with no cross-session header block | It is the opening instruction, not a relayed message; isomorphic to `web_access_create_session_and_chat` |
| Workspace scope (round-23 M1) | The pinvou3 home (settings.json, connector credentials, sessions/, spool roots) and filesystem volume roots are REFUSED as `workspace_path` — at the MCP server's shape probe and again at the Rust validator (the panel's own gate, so the panel shares it) | Binding either would present privileged state as an unattended opening turn's project; the tool description and contract §9 disclose the refusal |
| Explicit title | `set_title` after `create_new` | Auto-naming only triggers while the title is still the default "New chat", so an explicit title is naturally never overwritten by the first turn |
| Approval | L1 typed Ask registered (latent pin); panel-parity, unbound only (round-7 D): the Plan mirror applies to UNBOUND sessions; workspace-bound sessions resolve via the code lane's last mode, exactly like the panel; the unattended deny channel is TURN-LOCAL — an unattended run can relay through send_message_to_session into a normal session whose unshielded turn can call create_session (the #627 relay property; depth/rate caps are the future-work closure) | The Ask rule never prompts for MCP tools in any current mode; the review surfaces are the audit trail and the session list. Unattended `sched-`/`eval_`/`aux-`/`agentic_` requesters are denied by validation (round-31 minor 8: the headless family named here as §3/B3 already does), and unattended turns deny the tool via the engine channel — the attended→created recursion (A creates B whose opening message creates C…) is closed AT THE TOOL-NAME CHANNEL for the watcher-delivered opening turn (round-9 M6: the delivery applies the engine-side `unattended_disallowed_tools` shield before the turn, so B's automated first turn cannot CALL create_session/create_goal/the scheduled-task writes — round-10 M5(f): the shield is a tool-name deny list, not a sandbox; under default Yolo the shielded turn's exec_shell can still write the user-writable spool directly and reach the same watcher, so the closure holds at the named-tool channel only); the shield persists on that engine until recycle — a user opening the fresh session inside the idle window inherits the list, fail-closed and disclosed); the #627 relay property (an unattended turn relaying through send_message_to_session into a normal session) and depth/rate caps beyond it remain family-pass future work |
| Failure semantics | At-least-once, window stated honestly (round-1 M-B, rounds 2-7 wording) | The marker is written AFTER the post-create steps (binding → title → first-message delivery, up to the 30s bound). Retention interaction (round-17 M1, round-18 truth pass): tool-created sessions are PLAIN ids competing for the user's 50-chat retention budget — an unattended loop at tool pace reaches the cap in minutes, and past it every further save would evict a pre-existing conversation (with its workspace and checkpoints), the exact headless carve-out lesson (MAX_HEADLESS_SESSIONS). The watcher therefore gates every create on `plain_chat_budget_full()` — whose count mirrors the sweep's enumeration exactly (pinned sessions exempted before counting, so a pin genuinely frees a slot; a listing failure is fail-closed and spends a retry): at cap it poisons with the honest "session budget full" error (on a fresh attempt nothing was created and nothing is displaced; the marker tells the model to delete, pin, or ask the user); below the cap, tool creates consume remaining free slots like any chat (the occupancy itself is inherent to "create a normal session" and bounded by that headroom; a panel create landing between the gate and the save is the same disclosed TOCTOU class as the sweep — and the window spans the model-supplied path's canonicalize + the prefs load (round-31 minor 16: arbitrarily wide on a slow/hanging mount)'s own pin-file window). No per-sender rate limit exists beyond MAX_PENDING_FILES's batch bound; disclosed as the loop-amplification surface. RETRYABLE errors get 3 attempts per attempt-EPISODE — the budget clears on every terminal disposition and a terminal failure marker re-arms the key on the next call (the pending note invites the same-key re-poll), so one key can see multiple 3-attempt episodes in one process; two corners qualify the re-arm (round-29 M2, mirroring contract §9): a materially-replaced body at an exhausted name re-arms via the request-digest mismatch without any restart, while the sticky-quarantine corner (a persistently failing quarantine rename) keeps the exhausted budget stuck until the rename can succeed — safe direction; the restart-rebuy is separate); permanent validation classes (unknown model, invalid workspace, isolated requester) poison on the first failure — so a crash anywhere in that span, or a persistent marker-write failure, can duplicate the session (up to 3 per episode). (Round-10 M4 reword: the round-1..9 "3 TOTAL per key per process" claim was false as written.) Every created session that reaches the Ok arm is audited and announced before the marker write (the audit floor — the non-UTF-8-name quarantine carries no workspace audit (the log line is the trace); the ceiling arm audits parseable records with a usable sender; and the Ok-arm audit line itself lands only when the claimed sender's workspace exists — the audit append fails open for a nonexistent sender directory, so a record whose sender never resolves creates WITHOUT an audit line — round-35 minor 5: the fail-open corners are three (nonexistent sender directory, non-UTF-8-name quarantine, persistently failing audit sink; the log line is the trace for the latter two) (the contract §9 create_session row states this; the warn/log lines are the residual trace)); a workspace-binding failure rolls back and deletes the whole empty session (mirroring the `create_session` command), making the request retryable as a whole |

## 4. Disclosed limitations and boundaries

- **Background first turn (revised round-9 M6)**: when the user has not opened the session, the `first_message` first turn runs autonomously in the background under the resolved mode (Yolo by default, or the work-lane Plan default when set — round-4 R2's mirror); NOTHING pauses and no approval prompt exists today (mutating-MCP Ask rules resolve to silent Allow under full-auto). The watcher-delivered opening turn is **unattended-dispatched**: before the turn reaches the new session's engine, the delivery sends `Op::SetDisallowedTools` with the `unattended_disallowed_tools` list (create_session / create_goal / update_goal / the messaging send tool / the agent delegation tool / the three scheduled-task write tools / the two registry launchers `registry_sync` + `start_registry_mcp_server` — ten named tools; round-38 accounting fix: the previous "eight" undercounted by omitting the launchers), so an injected opening instruction cannot recursively create sessions/goals/task-writes through the NAMED tools, and cannot delegate around them: round-21 adds the `agent` tool to the list because a model-supplied `inherit_disallowed_tools=false` sheds preference denies in a spawned subagent (a clean catalog that keeps MCP tools under full-auto) — the shed route is closed at the named-tool channel; the deny persists across continuation turns until a send through the shared seams restores the catalog (attended sends and the scheduled family's `deliver_session_message` relay alike — round-31 minor 2) (the deny list is not a sandbox: exec_shell remains able to write the spool directly under default Yolo — the channel-scope disclosure above); goal-tool continuation turns on the same engine inherit the shield. The shield persists until the engine is recycled OR the first subsequent send through the attended seams — round-11 M1 as re-cut in round-12/13: `send_reserved_user_message` / `edit_last_turn_reserved` detect the mark AFTER acquiring the turn reservation and restore the ordinary per-session catalog (the restore lives in the production seams — the round-11 form inside `send_user_message` was compiled out of production builds — the shield op is applied only AFTER the delivery's own reserve succeeds, so a reserve failure cannot strand the shield unmarked, and the mark is recorded once the delivered turn's submission succeeds, so the delivery cannot dequeue its own shield; the scheduled family's pre/post-turn evict closes the same invariant by respawning; this is the delivery path's equivalent), so a user who takes over the session regains the full catalog instead of silently losing the ten named tools for the engine's lifetime. Round-13 boundary wording (extended round-31 minor 2): the seams include BOTH relay tail-calls — the messaging relay and the scheduled family's `deliver_session_message` fallback into `deliver_messaging_turn` — whose senders are unauthenticated, so a cross-session relay or a scheduled fire can lift the shield without a human (the scheduled relay's targets pass `ensure_deliverable_target` and its content is authored at task-creation time, but the seam itself is the same lift); that capability is inside the #627 relay boundary disclosed above, so the shield is fail-closed against interactive silence, not against relays. Round-13 disclosure: the delivered turn's `first_message_delivered:false` means "delivery not confirmed within the 30s watcher bound" — a long agentic turn whose op was already submitted can complete after the marker/audit said false; treat the field as conservative, and a manual re-send on it can duplicate the opening message (the family is at-least-once). A connector/skill toggle broadcast in the shield's open window re-shields watcher-marked sessions (round-15: the broadcast consults the mark set) the delete/model-switch engine REBUILD race between the shield op and the submission is CLOSED BY CONSTRUCTION (round-38 fix; round-42 extends the closure to the whole reserve→submit span — see window (d) below): the delivery acquires the engine once, shields that exact handle, and submits through the engine-taking submission core — an eviction in the span now fails the delivery loudly (the mismatch arm reports `first_message_delivered:false` on an ok:true receipt — the delivery is NOT auto-retried; the model re-sends manually) instead of re-resolving a fresh, ordinary-catalog engine and letting the opening turn run unshielded while the mark still recorded success (the pre-fix semantics-inverting window). Round-18 window ledger (all sub-second, all disclosed here): (a) a toggle reading the mark BEFORE the tail inserts it broadcasts the plain catalog AFTER the shield op on the same channel — the pending opening turn runs unshielded; (b) a restore removing the mark while a broadcast enqueues after it can leave the engine shielded with no mark until respawn — an interactive session silently loses the ten named tools; (c) the 30s drop-guard strip landing during the final submission round trip queues its op after the turn op, lifting the shield for the remainder of the very turn it guards. Round-42 window (d): an eviction (model switch / agent reconfigure) landing in the reserve→admit span keeps the unsubmitted reservation valid ON PURPOSE (the attended seam re-acquires after admit — the parent rebuild semantic), so the delivery could submit the opening turn into the reclaimed engine's post-Shutdown channel: silently dropped, a false success mark, and the created session wedged busy (no forwarder → no terminal). Closed by the submission core's incarnation re-validation (round-42 M1: mailbox identity under the admission gate — the mailbox Arc is per-spawn — with a transient bail BEFORE any op is enqueued; the reservation releases on drop, so the retried delivery is not wedged). The residual is the microsecond span between the check and the enqueue, closable only by a user action timed into it. Window (e), fail-closed and self-healing (round-42 review): an evict winning the released turn gate BEFORE the tail's mark insert leaves the mark naming a dead engine — the restore seams consult the live entry and no-op without one, and a respawn starts from the ordinary spawn catalog, so no user-visible surface exists. A serialized shield registry is the structural closure queued behind the follow-up train. Shield alternatives considered (round-38 note): (a) a per-engine atomic flag composed at broadcast time, as the scheduled family's `scheduled_unattended` does — rejected here because the watcher shield is MARK-scoped (a live mark must survive engine rebuilds and restore through the seams, which a per-engine bit cannot express); (b) shielding at SPAWN time (baking the deny list into the spawned catalog for marked sessions) — rejected because the spawn catalog is the ordinary user-shaped surface and the shield must lift on the first attended send without respawning; (c) the serialized shield registry (one writer for shield/restore/broadcast/evict ordering) remains the structural closure; the round-18 windows above are its residual surface. Beyond this turn the exposure matches the existing `send_message_to_session` delivery behavior; the creation is audited — the audit trail and the session list are the review surface.
- **Round-38 disclosure sentences** (each a boundary the reviewer asked to be explicit about):
  (1) **the fourth no-audit corner**: the three audit fail-open corners named in round-35 minor 5 (a charset-valid nonexistent sender directory, a non-UTF-8-name quarantine, a persistently failing audit sink) are joined by a fourth — a panic or process exit BETWEEN the session's creation and its `audit_request` append leaves a created session with NO audit line (the window is the delivery-then-append span; the session record itself remains the trace, and a watcher restart in that window REPLAYS the record — the spool file is consumed only after the marker write, so the create→marker crash span is the duplicate corner §Failure-semantics already discloses);
  (2) **`first_message` operator-authority consequence**: the opening turn executes with the user's full authority (default Yolo: shell and file tools enabled) on content the CALLING model authored — routing a task through `create_session` is not user approval of that content; the shield trims the recursion channels named above, not the ordinary tool surface;
  (3) **pre-existing `agentic_*` senders and targets fail after upgrade** (round-44 convergence): the create path's sender validation rejects the full headless family, and the shipped tools' target re-scope now rides **#752 itself, which main carries** (the shared four-prefix tuple — the round-42 interim "target leg keeps the shipped three" split is superseded by #752's own landing); automations or scripts that previously used an `agentic_*` session as `from_session` or messaged one through `read_session`/`list_sessions`/`send_message_to_session` get the isolated-prefix rejection after upgrading — rename the integration rather than expecting a silent pass-through;
  (4) **multi-root limitation**: one created session binds at most ONE canonical workspace root (`workspace_path`, or the app default when omitted) — a multi-root task needs multiple created sessions or manual rebinding; there is no per-session root set;
  (5) **live-engine count bound**: a creation burst does not accumulate unbounded live engines — each opening-turn delivery spawns at most one engine per created session, the pool's idle reap evicts idle engines, and the plain-chat retention budget (the 50-chat cap the create path already consults) bounds the session population the burst can reach.
- Frontend delta (round-20 wording): the uiToolDetails overlay strings (subtitle + desc × 3 locales, no logic changes) PLUS the `sessions.write` data-access chip label that now names creation (× 3 locales, round-19): the timeline renders the generic MCP tool card; a dedicated result card and "jump to the new session" are future work (P2).
- No new Tauri commands, no new events → no access-policy or protocol-test changes; web behaves identically to desktop.
- Existing users get the tool automatically on upgrade (builtin packages re-release by byte-for-byte content comparison, `ensure_package_released`).
- Fork delta: none in this PR's diff — the re-cut base (the `f08bf46e8` tip of `feat/scheduled-messages`) absorbed the gitlink advance and the register/guard sync (`c08c8c022`/74) that this PR's fast-gate chase first landed when upstream passed the registered head; the earlier `480bebf6`→`13ee4dfd2` advance is carried by the same stack.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Prompt-injection mass-creating sessions and flooding the list | Required-sender audit trail + timeline visibility + the feature switch (hides the tool and pauses creation) + the pending-file ceiling; the attended→created chain's first hop is tool-name-blocked at the delivered turn (round-9 M6 — channel scope disclosed), per-hop audits bound the rest (round-2 M2) |
| Duplicate creation (marker window) | The window spans the whole post-create sequence (binding/title/delivery, up to 30s) plus any retryable creator error retried ≤3 times (permanent validation classes poison at attempt 1, §2) — broader than messaging's marker-gap; bounded by the per-session audit lines and the ≤3 retry cap |
| A post-create step failing leaves a "half-configured" session | All best-effort + failure audits; a binding failure rolls back the creation (retryable); a failed first delivery can be re-sent by the user/model through the messaging channel |
| The background first turn auto-approving ordinary tools under default Yolo | Identical to the existing message-delivery behavior (the precedent already ships); L1 write tools carry latent Ask rules (no prompt today); the opening turn carries the unattended shield (round-9 M6 — recursion via create_session is blocked there); disclosed in §4 |
