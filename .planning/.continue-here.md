# Pinvou CLI TUI 跨机器续作检查点

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---|---|---|---|
| 未确认视觉合同就继续微调 | 实际 TUI 已明显偏离此前 HTML 视觉方向，单纯增加颜色或边框无法达到 Claude Code / Codex 级体验 | blocking | 恢复后先完成浏览器视觉稿与实际 TUI 的并排评审，冻结状态与组件合同后再写实现计划 |
| 把运行时初始化事件误判为协议错误 | 真实 Codex 会在 `turn.started` 前发送无 `turn_id` 的 `vendor`、`log.record`；旧逻辑因此提前断流 | advisory | 保留 `stream_accepts_codex_initialization_events_before_turn_started` 回归测试，新增 adapter 时按事件语义而不是到达位置分类 |
| 回到显式 `pinvou tui` 或附带控制台窗口 | 已与用户确认的默认启动方式冲突，且 Windows 子进程窗口破坏产品体验 | advisory | `pinvou` 默认进入 TUI；Windows Controller/Node 使用隐藏窗口创建标志 |

<current_state>

当前分支：`codex/distributed-node-runtime-stage1`。

TUI 已能通过真实 Codex runtime 连续聊天，用户已在本机确认收到回复。最新修复处理了 Codex 首回合前的初始化事件，避免 TUI 在真正答案到达前把连接判为协议错误。当前主要问题已从“功能不可用”转为“产品体验不达标”：等待期间没有清晰反馈，聊天流层级弱，`/agent`、`/mode` 等选择弹窗原始，整体与 Claude Code / OpenAI Codex CLI 差距很大。

技术判断：暂不替换 Ratatui。OpenAI Codex CLI 本身也采用 Ratatui/Crossterm，说明框架能达到目标；Pinvou 当前瓶颈是单体文本渲染、组件/主题/动效/焦点导航不足，以及没有视觉稿到终端快照的验收闭环。

</current_state>

<decisions_made>

- `pinvou` 默认启动 TUI；不把 `pinvou tui` 当正式入口。
- runtime 与 model 是两层选择：先选择/使用默认 runtime，再由 `/model` 切换该 runtime 当前可用模型。
- 权限模式由 Pinvou 提供统一产品语义，再映射到不同 runtime 的原生能力；不能只暴露某个 runtime 的特有术语。
- runtime 切换需要处理会话压缩/迁移，工具调用需要统一事件和审批语义；相关阶段 1 研究与规格文档已纳入本次提交。
- 当前不因 UI 粗糙直接更换 Ratatui；先用视觉合同和组件化重构验证。

</decisions_made>
