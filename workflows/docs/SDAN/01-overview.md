# 01 · SDAN 总览

> 架构层文档 · 通用，不绑任何具体 workflow

## 一句话

**SDAN（Software Defined Agent Network，软件定义 Agent 网络）**：把 agent 工作流的调度，从"写死在代码里的判断"抽象成 **一个固定的 Router + 一张数据路由表 + 三个旁挂模块 + 一群只认信封的 SubAgent**。换一个 workflow，只换路由表，不动引擎。

## 为什么要它（病根）

旧的做法（命令式控制核）把"某个 agent 干完后、该放行还是打回、打回给谁"这类**调度判断**，劈成好几份散落在不同地方——信号路由一处、gate/评审一处、依赖图一处、声明一处，各用不同形态（代码 if / 状态机 / 脚本 / JSON）写。后果三连：

- **描述不清**：它是代码控制流，不是一个能"读出来"的结构。
- **不可复制**：换个领域的 workflow，得重写控制核，而不是填一份声明。
- **不可扩展**：加一个 agent、改一条跳转，都要动控制核本身。

SDAN 的价值不是"换个时髦架构"，而是：**把调度从代码里抽出来，变成一份可读、可复制、可生成的声明——控制核退化成这份声明的纯执行器。**

## 三平面

| 平面 | 是谁 | 职责 |
|---|---|---|
| **控制平面** | **Router（固定产品，无状态）** | 加载·解析·执行路由表 + 按 SDAN 协议处理报文。定所有"下一跳"。 |
| **数据平面** | **SubAgent** | 只认信封：收 Task → 干活 → 交 Result。不知道全局。 |
| **旁挂** | **⚖️裁决 + 🧠State(记忆) + 📦Blackboard(资源)** | Router 读写/调用，但都**独立于 Router**，Router 不拥有它们。 |

详见 `02-router` / `04-subagent` / `05-judge` / `07-state` / `08-resources`。

## 命名 · 对标 SDN

名字取自 **SDN（软件定义网络）**：SDN 把"决策大脑"从每台设备里抽出来集中成控制器，干活的交换机又多又傻、只查转发表。SDAN 照搬这个分离：

- 一个集中的 **Router（大脑）** 握路由表、定所有下一跳；
- 一群 **SubAgent（傻腿）** 只认信封、只管干自己那摊。

> 区别：网络路由器看一眼就转发、不记事；SDAN 的 Router 也**无状态**，但它服务的是"有依赖、有回滚"的工作流，所以进度**记忆外置**到独立的 State 模块（更像 SDN 控制器握全局视图，但视图不长在 Router 身上）。

## 设计原则

1. **Router 是固定产品**：无状态、不存数据、不碰内容、不内置逻辑。换 workflow 不改它。
2. **数据驱动**：调度逻辑 = 路由表（数据）；Router = 不变的引擎。
3. **判断旁挂**：质量判断（代码规则 / LLM 裁决）不在 Router 肉身里，旁挂可插拔。
4. **SubAgent 傻腿**：隔离、只认信封、不知道全局——可独立替换、并行、复用。
5. **可复制 / 可生成**：新 workflow＝写一张新路由表；这张表可由上层（如 Pinvou3）生成。

## "不白绕"试金石

SDAN 跟"旧的命令式控制核"的本质区别**必须**是：

> 调度逻辑 = **统一引擎 + 声明式路由表 + 旁挂判断** —— 而**不是**换个名字、底下还是一堆写死的 if 散在多处。

区别对了，才真治了"四层散落"的病，也才轮得到"可复制、可生成"。做出来若还是 hardcode，就是白绕。

## 架构 vs 实例（关键定位）

- **SDAN 是一套通用架构**（本目录 01–09、11）。
- **任何具体工作流只是它的一个实例**——把角色、依赖、回滚、场景写成一张路由表喂给同一个 Router。
- 本仓库的 **PPT 工作流是 SDAN 的第一个实例**，集中在 `10-ppt-instance`。架构层文档**不写任何 PPT 专有细节**。
