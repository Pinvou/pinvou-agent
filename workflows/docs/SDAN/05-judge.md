# 05 · 裁决模块（旁挂）

> 架构层文档 · 通用

## 定位

裁决 = Router "定下一跳"的**依据**，**旁挂、可插拔，不在 Router 肉身里**。两层：**hard（代码，硬门，唯一定路由）→ soft（LLM，软建议，不定路由、不阻断）**。

## 顺序：确定性优先

- **hard 先跑**：代码规则，确定性最高、最便宜、可复现。**能用代码定死的，绝不惊动 LLM。**
- hard 通过、且节点配了 soft → **才调 soft**：LLM 裁决器，对代码兜不住的内容质量出**建议**（不阻断，见下）。
- 成本与确定性：`hard > soft`。

## hard 裁决

- 代码规则脚本（结构校验、质量规则等）；路由表声明每个节点调哪些。
- 输出 verdict：`PASS / WARN / FAIL`（FAIL 带 `rollback_scope: local | structural`）/ 以及检查类节点的 `violation_type`。
- **WARN**：放行但记账（给非阻塞节点用）。

## soft 裁决器（无人格）

- = **固定裁决提示词 + LLM + 无状态**。
- **无状态**：只吃"待裁决的交付物 + 该验收点的裁决标准"，**不吃任何对话历史**。每次裁决自包含、独立。
- **无人格**：它是从"人格化的品悟"里**剥离**出来的纯判断服务——**不叫品悟**，没有记忆、不参与对话。
- **KV-cache 友好（契合本地算力）**：固定提示词 → 前缀稳定 → vLLM prefix cache 高命中。
  - prompt 摆法：`[固定前缀：角色 + 该验收点裁决标准 + 输出格式]` 在前、`[可变的交付物内容]` 在后。
  - 一个验收点一段稳定 cache；同一验收点重试时命中自己那段。
- 输出：`建议 PASS / 建议 FAIL（+ 意见）`——**仅作建议，不改路由**。

## soft 不阻断（白浪 2026-05-29 改）

soft 裁决**不定路由、不打回、不回滚**——它的结果只上浮成一张**用户可见的建议卡片**（见 `09`），如「质检建议：第 3 页配色偏暗」。是否真重做，由**用户干预**决定（现阶段推迟）。

为什么降级成建议：

- **防死锁**：开放式 LLM 裁判（尤其本地弱模型）爱挑刺，给它阻断权 → 「总是不给过」死循环（历史坑：gate 曾被迫改 auto 堵死锁）。
- **本地模型当裁判可靠性有限**：让它出意见、不让它把关。
- **唯一硬门 = hard + 用户**：自动硬门只留 hard（确定性、可复现）；主观质量交人眼。

**降低误杀的提示词要求**（写进固定提示词）：① 关闭式清单（具体 yes/no），别问开放式「好不好」；② default-PASS 偏置——除非有具体、明确、阻断性缺陷，否则建议 PASS，模糊不满不算 FAIL。

> 跨节点 structural 回滚只由**检查类节点的 hard**（有全局产物视角、产出 `violation_type`）发起；soft 与回滚无关。见 `06` 回滚三源。

## verdict 三来源（裁决器是唯一产 verdict 的出口 · 白浪 2026-05-29 定）

Router 只从"裁决 → 信封头"这**一个口**拿 verdict，**永远不知道、也不需要知道**这条 verdict 背后是代码算的还是人点的。裁决器产 verdict 的来源有三种：

1. **hard 规则**（代码）→ 直接产路由 verdict（`PASS/WARN/FAIL`+`rollback_scope` / `violation_type`）。
2. **soft LLM** → **只产建议卡片，不产路由 verdict**（见上节）。
3. **用户决策 hook** → 用户在建议卡片上做的"通过 / 打回"决定，经 hook **回到裁决器**（**不直连 Router**——用户不是 Router 的边，Router 只跟 SubAgent + 旁挂模块打交道）；裁决器据此产出一个路由 verdict，**标注 `source=user`** 并**写入 🧠State 记忆**（可追溯、崩了不丢）。

要点：

- **用户从不直连 Router**。用户的意志通过"建议卡片 → hook → 裁决器 → verdict"这条链进入路由，**复用裁决器既有的 `verdict→信封头` 接口，Router 侧零新增入口**——模块功能统一、接口不乱。
- "唯一硬门 = hard + 用户"里的**用户硬门**，就是来源 3：经裁决器这个唯一出口生效，不是用户自己拨 Router。
- **来源 3（用户决策回路）现阶段推迟**（承 `09` 用户干预推迟）：v1 里 soft 卡片先是只读提醒、工作流照 hard 往下走；用户"通过/打回"让其回流生效是后续功能。

## verdict 上信封头

**hard** 裁决结果（`verdict` / `violation_type`）是 Router 转发要用的元数据 → **上浮信封头**（`header_signals`）。Router 据此查节点 `outcomes` 定下一跳，全程不拆信纸。**soft 的建议不进路由头**——它走另一条路（建议卡片 → UI，见 `09`），Router 路由只认 hard。
